# WeaponHero

두 자루의 무기를 실시간으로 바꿔 끼우며 싸우는 2D 액션 로그라이크입니다.

## 프로젝트 개요

- 장르: 2D 액션 로그라이크 (레퍼런스: Skul: The Hero Slayer)
- 개발 기간: 2026.07.28 ~ 2026.09.04 (6주, 약 120시간)
- 개발 인원: 1명
- 사용 엔진: Unity 6 (6000.3.15f1, URP 2D)
- 사용 언어: C#
- 출시 플랫폼: Windows
- 담당 역할: 기획, 프로그래밍, UI 구성, 사운드 배치, 테스트, 빌드

## 게임 설명

플레이어는 무기 두 개를 들고 전투 5칸 · 보상 4칸 · 보스 1칸, 총 10칸으로 이루어진 런을 진행합니다.  
무기를 바꾸는 스왑에는 짧은 대시와 무적 시간이 붙어 있어, 교체가 메뉴 조작이 아니라 회피이자 공격 리듬이 됩니다.  
보상방에서 새 무기 · 회복 · 강화 중 하나를 골라 매 런 다른 조합으로 성장하고, 적을 처치하면 체력이 조금씩 회복되어 적극적인 전투를 유도합니다.  
한 런은 5~10분 안에 끝나 짧게 반복 도전할 수 있도록 구성했습니다.

## 주요 기능

- 플레이어 이동 · 점프 · 무기별 콤보 공격, 코요테 타임과 점프 버퍼
- 무기 3종(검 · 창 · 활)과 2슬롯 스왑 — 대시 · 무적 · 스왑 쿨타임
- 적 2종(돌진형 · 원거리형)과 보스 1종(오우거, 공격 패턴 3개)
- 10칸 런 진행 — 전투 · 보상 · 보스 방, 낙하 시 복귀, 출구 포탈
- 보상 3택 1 — 가지지 않은 무기 · 회복 · 강화
- 사망 · 보스 처치 시 결과 화면과 재시작 · 타이틀 복귀
- HUD(체력 바 · 무기 슬롯 · 스왑 쿨타임 게이지)와 설정 화면(해상도 · 화면 모드 · 볼륨 · 언어)
- 한국어 · 영어 로컬라이즈, 효과음 · BGM, 히트스탑 · 화면 흔들림

## 조작법

- 이동: ← →
- 점프: Space
- 공격: F
- 무기 스왑: A
- 보상 선택: 1 · 2 · 3 또는 클릭
- 재시작: R 
- 일시정지 · 설정: Esc

## 기술적으로 신경 쓴 부분

- **확장 지점을 착수 전에 정했습니다.** 무기(데이터 + 런타임 래퍼) · 적과 보스가 함께 쓰는 상태머신 · 방 타입 핸들러를 먼저 고정했고, 그 결과 보스는 새 시스템이 아니라 공격 패턴 데이터 3개로 만들어져 계획 20시간이 6.5시간으로 줄었습니다. 원거리형 적은 새 스크립트 없이 데이터만으로 추가했습니다.
- **상태가 자기 조작 권한을 직접 선언합니다.** 좌우 조작 · 중력 · 점프 입력 · 방향 전환 · 무기 교체 5가지를 각 상태가 켜고 끄는 구조라, 상태를 추가해도 이동 · 점프 코드를 고치지 않습니다.
- **적의 공격 선택을 조건문이 아니라 데이터로 정했습니다.** 공격 패턴마다 사거리 · 높이차 · 가중치 · 쿨다운을 가진 `AttackPattern`(ScriptableObject)을 두었습니다. 근접 패턴은 높이차 0.5~1.0을 넘으면 선택이 취소되고 원거리 패턴은 제한이 없어서, "플레이어가 점프하면 원거리 공격으로 대응"하는 행동이 나옵니다. 판정 코드는 한 줄이고 경계값은 전부 데이터에 있어서, 패턴이 늘어도 분기가 늘지 않습니다.
- **무기 원본 데이터는 읽기 전용으로 두었습니다.** 강화 레벨은 런타임 인스턴스가 들고, 공격 수치는 값 복사본으로 꺼내 계산합니다. 원본 에셋이 플레이 모드를 넘어 오염되거나 같은 무기를 든 두 슬롯이 서로 간섭하는 것을 막았습니다.
- **의존 방향을 컴파일 단계에서 강제했습니다.** 스크립트를 `Game.Core ← Game.Gameplay ← Game.UI` 3개 어셈블리로 나눠, 규칙을 어기는 참조는 컴파일 자체가 되지 않습니다.
- **배선 누락을 초기화 시점에 알립니다.** 프리팹 연결이 빠졌을 때 한참 뒤 NullReferenceException으로 터지지 않도록, 시작할 때 필요한 컴포넌트를 검사하고 치명 · 경고로 나눠 무엇이 안 되는지까지 로그로 남깁니다.
- **기능 단위로 이력을 관리했습니다.** GitHub 이슈 → 브랜치 → PR 흐름으로 작업했고(이슈 74 · PR 66 · 커밋 322), 커밋 본문에 판단 근거를 남겼습니다.

## 문제 해결 경험

### 문제 1. 점프 입력이 가끔 씹히는 문제

- 원인: 한 프레임에만 참이 되는 `WasPressedThisFrame()` 입력을 물리 주기인 `FixedUpdate`에서 확인했습니다. `FixedUpdate`가 건너뛰는 렌더 프레임에 누른 입력은 아무도 보지 못했고, 측정해 보니 에디터에서는 렌더 프레임이 `FixedUpdate`보다 약 6.5배 많이 돌고 있었습니다.
- 해결: 입력은 `Update`에서 받아 붙잡아 두고, 실제 점프는 `FixedUpdate`에서 소비하도록 나눴습니다. Input System의 갱신 주기 자체를 물리 주기로 바꾸는 방법도 있었지만, UI 반응까지 함께 느려져 선택하지 않았습니다.
- 배운 점: 한 프레임짜리 이벤트와 "지금 눌려 있는가" 같은 상태 확인은 다르게 다뤄야 하고, 프레임레이트가 높은 기기일수록 이 문제가 더 심해집니다.

### 문제 2. 적이 죽은 뒤에도 0.35초 동안 공격 판정이 남는 문제

- 원인: 사망 처리가 피격 판정만 끄고 공격 루프는 멈추지 않았습니다. 오브젝트가 사라지기까지 0.35초 동안 공격이 계속 돌았고, 공격 판정을 끄는 코드가 취소 경로에 없어 판정이 켜진 채 남을 수도 있었습니다.
- 해결: 바로 땜질하지 않았습니다. 곧 적 AI를 상태머신 구조로 바꿀 예정이라 기존 클래스는 사라질 코드였기 때문에, 그 개편에서 사망을 `Dead` 상태로 만들고 진입 시 이동과 판정을 함께 끄도록 했습니다. 개편 PR에서 문제가 실제로 사라진 것을 확인한 뒤 이슈를 닫았습니다. 이 과정에서 `?.` 연산자가 Unity의 파괴된 오브젝트를 null로 인식하지 못한다는 것도 확인해 `!= null` 비교로 바꿨습니다.
- 배운 점: 곧 교체될 구조에 들인 수정은 함께 버려집니다. 그리고 같은 구조가 한쪽에는 처리돼 있고 다른 쪽에는 빠질 수 있으므로, 정상 흐름뿐 아니라 취소 경로까지 확인해야 합니다.

### 문제 3. 한 런에 같은 방이 자꾸 반복되는 문제

- 원인: 난수 자체는 문제가 없었습니다. 같은 난수 알고리즘으로 시드 10만 개를 돌려 보니 방마다 등장 확률이 20.0%로 균등했습니다. 문제는 뽑는 방식이었습니다. 매번 무작위로 뽑고 직전 방만 피하다 보니 A B A C B 같은 순서가 정상이었고, 다섯 방이 모두 다른 런은 9.4%뿐이었습니다.
- 해결: 방 목록을 섞은 뒤 앞에서부터 하나씩 꺼내는 셔플 방식으로 바꿨습니다. 한 런에 모든 방이 정확히 한 번씩 나오고, 같은 시드는 같은 순서를 유지합니다. 덤으로 런마다 적 수가 41마리로 고정되어 런 길이의 편차도 사라졌습니다.
- 배운 점: "균등하게 나온다"와 "반복되지 않는다"는 서로 다른 문제입니다. "뭔가 이상하다"는 체감은 수치로 재현해서 원인을 분리해야 합니다.

### 문제 4. 영어로 바꾸면 안내 문장이 상자를 넘치는 문제

- 원인: 영어 문장이 한국어보다 1.4~1.9배 길어서, 줄바꿈으로 줄 수가 늘어나며 상자 높이를 넘었습니다. 빌드를 영어로 실행해 보고서야 발견했습니다.
- 해결: 글자 크기 자동 조절(Auto Size)을 켜되 최대 크기를 현재 글자 크기와 같게 두었습니다. 한국어는 원래 크기 그대로 그려지고, 영어일 때만 글자가 줄어듭니다.
- 배운 점: 로컬라이즈가 들어가면 언어별로 빌드를 확인해야 하고, 자동 크기 조절은 최댓값을 함께 정해야 기존 디자인이 유지됩니다.

## AI 활용 내용

이 프로젝트에서는 AI(Claude)를 다음 작업에 활용했습니다.

- 기획서 · 로드맵 · 학습 로그 문서 정리
- 설계 방향 논의 (개념과 의사코드 수준)
- 직접 작성한 코드의 리뷰와 오류 원인 분석
- GitHub 이슈 · PR · 커밋 메시지 정리
- 빌드 체크리스트와 빌드 노트 작성

학습과 포트폴리오 목적인 프로젝트라, AI가 게임 코드를 대신 작성하지 않도록 작업 규칙([CLAUDE.md](CLAUDE.md))을 먼저 정해 두었습니다. AI는 문제를 지적하되 코드를 고쳐주지 않고, 구현은 직접 했습니다.  
AI의 설명이나 제안도 바로 따르지 않고, 실제 코드와 데이터로 확인한 뒤 반영했습니다.

## 실행 방법

1. 빌드 파일을 다운로드합니다.
2. 압축을 해제합니다.
3. 실행 파일을 실행합니다.
4. 시작 화면의 조작 버튼에서 조작법을 확인한 뒤 플레이합니다.

Unity 에디터에서 열 경우 Unity 6000.3.15f1로 열고 `Assets/_Project/Scenes/StartScene`에서 실행합니다.  
유료 에셋(`Assets/Imported/`)은 재배포할 수 없어 별도 비공개 저장소로 분리했기 때문에, 저장소만 클론하면 스프라이트와 사운드 참조가 비어 있습니다.

## 회고

이번 프로젝트를 통해 6주 · 120시간이라는 정해진 예산 안에서 기획부터 최종 빌드까지 한 사이클을 완성했습니다.  
가장 잘한 판단은 무엇을 자를지 미리 정해 둔 것이었고, 착수 전에 정한 확장 지점 덕분에 보스를 계획보다 훨씬 빨리 넣을 수 있었습니다.  
반대로 폰트를 미리 굽는 방식의 유지 비용(문구를 바꿀 때마다 다시 굽기)을 계획에 넣지 않아 예정에 없던 시간을 썼고, 밸런스를 마지막 주에 잡는 바람에 런 전체의 난이도가 평평하게 남았습니다. 처음 세운 기획서를 끝까지 그대로 지키려 하기보다, 진행 상황에 맞춰 고쳐 나가는 것이 중요하다는 것도 배웠습니다.  
다음 프로젝트에서는 난이도 곡선을 콘텐츠가 아닌 구조로 보고 더 일찍 세우고, 무기와 보스 종류를 데이터 추가만으로 늘려 확장 지점이 실제로 작동하는지 검증할 계획입니다.
