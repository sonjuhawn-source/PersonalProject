## 2. 레퍼런스 분석 — 스컬에서 무엇을 가져오는가

### 가져올 것

- **교체가 곧 조작 리듬** — 스왑이 단순 메뉴 조작이 아니라 전투 중 계속 눌러야 하는 액션.
  스왑 자체에 이동/회피 성능을 부여해 "교체를 아끼면 손해"인 구조를 만든다.
- **짧고 밀도 높은 전투** — 방 하나당 10~30초. 적은 수가 아니라 밀도로 압박.
- **강한 히트 피드백** — 히트스탑, 화면 흔들림, 넉백, 이펙트. 스컬 손맛의 8할.
- **런마다 달라지는 빌드** — 무기 조합 + 유물 시너지로 매 판 다른 플레이.

### 버릴 것 / 바꿀 것

- **머리 교체 → 무기 교체** (아래 3장 참조)
- **방대한 캐릭터 수** — 스컬은 캐릭터 수십 종이 셀링포인트. 포트폴리오 규모에서는 불가능하고,
  소수를 깊게 파는 편이 오히려 평가에 유리하다.
- **복잡한 메타 성장 트리** — 최소한으로 축소 (7장 참조)

## 3. 핵심 시스템 — 무기 교체

> **작업 가정:** 스컬의 "2슬롯 실시간 교체" 구조는 유지하되, 교체 대상을 **머리 → 무기**로 바꾼다.
> 재검토 가능하나, 아래 근거로 현재는 무기안을 기준으로 설계를 진행한다.

### 왜 무기인가 (포트폴리오 관점)

머리 교체는 캐릭터 1종당 **전신 스프라이트 + 애니메이션 풀세트**가 필요하다. 1인 개발에서 이건
콘텐츠 1종 추가 비용이 가장 비싼 구조다. 무기 교체는 **공용 캐릭터 리그 하나**를 쓰고 무기별
공격 모션만 추가하면 되므로, 같은 기간에 3~4배 많은 빌드 다양성을 만들 수 있다.
"시스템 설계 능력"을 보여주는 게 목적이라면 물량보다 조합의 깊이가 낫다.

### 규칙

- 무기 슬롯 **2개**. 언제든 `스왑` 키로 즉시 교체.
- **스왑에 이동 성능 부여** — 스왑 순간 짧은 전진 대시 + 무적 프레임(i-frame).
  즉 스왑은 회피기이기도 하다. 쿨타임 `TBD`(스컬 기준 3~4초 감각).
- **대기 중인 무기는 쿨타임이 회복된다** — 스킬을 다 쓴 무기를 내려두고 다른 무기로 싸우다
  다시 돌아오는 순환이 기본 리듬.
- 무기마다: **평타 콤보 1종 + 고유 스킬 2종**.
- 무기 등급 `TBD` (일반/희귀/유니크 등 — 등급제를 둘지 자체가 미결정)

### 무기 아키타입

1차 3종. **에셋 파츠에 맞춰 확정했다** ([10.1](#101-확정--pixem-파츠-조합형-픽셀-캐릭터)).

| 아키타입 | 클립 | 성격 | 스왑 시너지 예시 |
|---|---|---|---|
| **검** (기본) | `AttackSlash` | 균형, 넓은 범위 | 무엇과 짝지어도 무난한 기준점 |
| 창 | `AttackPrick` | 중거리 리치, 찌르기 | 검보다 먼 거리에서 견제 |
| 활 | `AttackShoot` | 원거리 견제 | 근접 무기와 짝지어 거리 관리 |

**캐릭터는 6개를 미리 구웠다** — 검 · 단검 · 창 · 지팡이 · 활 + 무기 없는 **기본형**.
1차 구현은 위 3종만 한다. 로드맵 W2 가 "무기 3종 8h"인데 무기 하나당 평타 + 스킬 2종을
설계해야 해서 그 이상은 초과한다.

기본형(`Character_Base`)은 게임에 쓰지 않는다. **새 무기 캐릭터를 구울 때 시작점**으로
남겨둔 것이다. 파츠를 손으로 다시 고르면 외형이 미묘하게 어긋나므로 이 기준에서
무기 필드만 바꿔 굽는다.

미리 구워둔 덕에 **후속 추가 비용이 갈린다.**

| 후속 후보 | 남은 작업 |
|---|---|
| 단검 | 캐릭터 있음 · 클립 `AttackPrick` · 발사체 없음 → **SO 하나** |
| 지팡이 | 캐릭터 있음 → SO + 마법 발사체 (활과 다르게 동작하면 별도 작업) |
| 대검 | 굽기 + SO. 클립·컨트롤러가 검과 같아 수치만 다르게 넣으면 된다 |
| 도끼 등 | 파츠에는 있으나 아직 굽지 않았다 |

**단검이 가장 싸다.** W2 에 여유가 생기면 첫 후보다.

#### 아키타입은 스프라이트가 아니라 타이밍이 만든다

무기 파츠는 20종이 넘는데 **공격 클립은 4종뿐**이다. 여러 무기가 같은 클립을 공유할
수밖에 없다 — 검·대검·도끼가 전부 `AttackSlash` 다. 그래서 **무게감은 그림이 아니라
타이밍에서 온다.**

| 요소 | 무겁게 | 가볍게 |
|---|---|---|
| 클립 재생 속도 | 느리게 | 빠르게 |
| 선딜 / 후딜 | 길게 | 짧게 |
| 히트박스 크기 | 넓게 | 좁게 |
| **히트스탑** | 길게 | 짧게 |
| 넉백 | 강하게 | 약하게 |

히트스탑이 0.15초인 무기와 0.04초인 무기는 같은 스프라이트라도 손맛이 완전히 다르다.
[#12](../../issues/12) 에서 히트스탑을 이미 만들어뒀으므로 무기 SO 에 이 값들을 넣으면
9장 확장 지점 1이 그대로 동작한다 — 무기 추가가 데이터 작성이 된다.

**활은 유일하게 슬롯이 다르다.** `RightHandWeapon` 이라 손 위치까지 바뀌어서 근접/원거리
구분이 그림으로 드러난다. 조립할 때 왼손을 `Empty` 로 비워야 검과 활을 동시에 들지 않는다.

**이펙트는 `SlashEffect.png` 하나뿐이다.** 무기별 이펙트가 필요하면 W2 에서 별도로
확보해야 한다. 없어도 위 타이밍 차이로 구분은 된다.

#### 후속 — 같은 계열 안에서 무기를 늘린다

아키타입은 3~4개로 두고, **같은 계열 안에서 수치·상태이상·부가효과를 달리한 무기**를
추가한다. 검 계열에 검이 세 자루 있어도 하나는 화상, 하나는 고데미지·저속, 하나는
연타 특화면 각각 다른 선택이 된다.

목적은 **플레이 스타일 선택 유도**다. 같은 계열이라 조작은 익숙한데 수치와 효과가
달라서, 플레이어가 "내가 어떻게 싸우고 싶은지"로 고르게 된다. 아키타입만 늘리면
조작을 새로 익혀야 해서 진입 장벽이 되고, 로그라이크의 반복 플레이와 맞지 않는다.

**1차에서 지킬 것 3개.** 이것만 지키면 후속이 데이터 작성 + 효과 클래스 추가로 끝난다.

| 지킬 것 | 안 지키면 |
|---|---|
| 공격력·선딜·히트스탑·넉백을 **무기 SO 필드로** 둔다 | 값이 코드에 박혀서 무기를 늘릴 때마다 분기가 생긴다 |
| `DamageInfo` 에 **상태이상 정보를 실을 자리**를 남긴다 | 화상·빙결을 넣을 때 피격 경로 전체를 고쳐야 한다 |
| 타격 시점에 **이벤트 훅**을 둔다 | 부가효과를 무기별 `if` 로 처리하게 된다. 9장 확장 지점 4(유물)와 같은 훅을 쓰면 코드가 재사용된다 |

**아키타입 SO 와 무기 SO 를 지금 분리하지 않는다.** 1차에서는 아키타입과 무기가 1:1
이라 분리해도 이득이 없다. 계열 안에 무기가 둘 이상 생겨서 컨트롤러 참조가 실제로
중복될 때 나누면 된다 — 추상화는 중복이 보인 다음에 넣는다.

> 최종 무기 수는 8장 콘텐츠 물량 참조.

### 미결정

- 같은 무기 2개를 들 수 있는가? (중첩 강화 vs 금지)
- 스왑에 **공격 판정**을 넣을 것인가? (넣으면 공격적, 안 넣으면 순수 회피기)
- 무기 강화/합성 시스템 존재 여부

## 4. 코어 게임플레이 루프

```
런 시작 (기본 무기 1종)
  └→ 방 진입 → 전투 (10~30초) → 클리어
        └→ 보상 선택 (무기 / 유물 / 재화 중 택1)
             └→ 다음 방 …  (스테이지당 8~12방)
                  └→ 보스전
                       └→ 클리어 → 다음 스테이지 / 사망 → 메타 재화 정산 → 런 시작
```

**1런 목표 플레이타임:** 20~30분 (풀 클리어 기준)

## 5. 전투 시스템

### 조작

| 입력 | 동작 |
|---|---|
| 좌/우 | 이동 |
| 점프 | 점프 (1단 — 2단 점프는 넣지 않는다, 12.1) |
| 공격 | 평타 콤보 |
| 스킬 1 / 2 | 현재 무기 고유 스킬 |
| 스왑 | 무기 교체 + 대시 + i-frame |
| 상호작용 | 아이템 획득, 문 진입 |

Unity **Input System** 사용 (`Assets/InputSystem_Actions.inputactions` 기존 에셋 활용).

### 액션 감각 (가장 먼저 프로토타이핑할 영역)

- **코요테 타임 / 점프 버퍼** — 플랫포머 조작감의 기본. 초기부터 넣는다.
- **히트스탑** — 타격 시 수 프레임 정지. 무기 무게감을 만드는 핵심.
- **넉백 / 경직** — 적 반응. 슈퍼아머 적은 경직 무시.
- **선입력(input buffer)** — 콤보 중 다음 입력 선접수.
- **피격 무적 + 무적 시각화**

> 위 항목들은 "나중에 추가"가 가장 안 되는 것들이다. 프로토타입 단계에서 확보한다.

### 적 설계 원칙

- 적은 **역할**로 분류: 근접 돌진형 / 원거리 견제형 / 방패(정면 방어) / 광역 압박형
- 각 적은 **공격 전 예고 모션**을 반드시 가진다 (패턴 학습 가능해야 함)
- 방 구성은 단일 종류가 아니라 **역할 조합**으로 압박을 만든다

## 6. 로그라이크 구조

### 스테이지 / 방

- 스테이지 = 방 8~12개 + 보스방 1개
- 방은 **수제작 프리팹 풀에서 랜덤 추출** (완전 절차적 생성 아님)
  → 1인 개발에서 절차 생성은 품질 관리 비용이 너무 크다. 수제작 방 + 랜덤 배치가 현실적.
- 방 타입: 전투 / 보상 / 상점 / 휴식 / 이벤트(`TBD`) / 보스

### 보상 설계

방 클리어 시 **선택지 3개 중 1개** — 선택이 곧 빌드 방향 결정.
"강해지는 느낌"보다 "무엇을 포기했는가"가 기억에 남게 설계한다.

### 유물 / 시너지

- 유물 = 패시브 효과. 런 종료까지 유지.
- **무기 아키타입과 연동되는 유물**을 일부 배치해 빌드 방향성을 만든다
  (예: "근접 무기 피격 시 반격", "스왑 직후 3초간 공격속도 +30%")
- 스왑 시스템과 엮인 유물이 이 게임의 정체성 — 최소 3~4종은 확보

## 7. 메타 성장 (사망 후)

> **1차 범위(6주) 밖 — 후속 단계로 이연.**

메타 성장은 여러 런을 반복해야 체감되는 시스템이라, 런 하나가 겨우 완성되는 규모에서는
투자 대비 회수가 가장 나쁘다. 1차에서는 사망 시 결과 화면만 띄우고 즉시 재시작한다.

**나중에 붙일 자리는 지금 남겨둔다:**
- 런 종료 시 `RunResult`(획득 재화, 처치 수, 도달 방, 사용 무기)를 반환하는 구조로 만든다.
  1차에서는 결과 화면 표시에만 쓰지만, 그대로 메타 성장의 입력값이 된다.
- 저장/로드는 1차에서 구현하지 않되, **세이브 대상이 될 데이터는 한 곳에 모아둔다**
  (런타임 상태와 영구 상태를 섞지 않는다). 이것만 지키면 나중 추가가 하루 작업이다.

## 8. 콘텐츠 물량

**1차(6주 / 120시간)는 아래 "1차" 열까지만 만든다.** 나머지는 잘라내는 게 아니라
**데이터만 추가하면 되는 상태**로 남겨둔다 (9장 확장 지점 참조).

| 항목 | **1차 (6주)** | 후속 |
|---|---|---|
| 스테이지 | 1 | 2~3 |
| 방 프리팹 | 6~8 | 20+ |
| 무기 | **3종** (검 / 창 / 활) | 8종 (단검 · 지팡이 · 대검 · 도끼 등) |
| 적 | **3종** (돌진 / 원거리 / 방패) | 8종 |
| 보스 | 1 | 2~3 |
| 유물 | 8종 | 20종+ |
| 방 타입 | 전투 / 보상 / 보스 | +상점 / 휴식 / 이벤트 |

무기 3종 · 적 3종이면 조합이 9가지라 "매 판 다르다"는 감각은 1차에서도 충분히 나온다.

### 1차 범위 밖 (이연 — 설계에는 자리를 남긴다)

| 이연 항목 | 나중에 붙이는 방법 |
|---|---|
| 메타 성장 | `RunResult` + 영구 상태 분리 (7장) |
| 런 중간 저장 (이어하기) | `RunState` 순수 데이터 + 시드 기반 생성 (11.3) |
| 키 설정 (리바인딩) | Input System `SaveBindingOverridesAsJson` — UI만 추가 (11.4) |
| 언어 추가 (3개국어 이상) | String Table 에 열 추가 — 한/영은 1차 포함 (11.2) |
| 스테이지 2~3, 보스 2~3 | 스테이지도 데이터(SO)로 정의 → 방 풀·보스만 교체 |
| 상점 / 휴식 / 이벤트방 | 방 타입을 enum이 아닌 **데이터 + 핸들러**로 → 타입 추가가 파일 추가 |
| 같은 계열 안의 무기 변형 (수치·상태이상·부가효과) | 무기 SO 필드 + `DamageInfo` 확장 자리 + 타격 이벤트 훅. 셋만 지키면 데이터 작성 + 효과 클래스 추가로 끝난다 (3장) |
| 무기 등급제 | 무기 SO에 `rarity` 필드만 미리 두고 1차에서는 전부 동일 등급 |
| 무기 강화·합성 | 무기 인스턴스를 SO 직접 참조가 아닌 **런타임 래퍼**로 → 수치 변형 여지 확보 |
| 자체 아트 | 스프라이트·애니메이터를 무기/적 데이터에서 참조 → 에셋 교체가 데이터 수정 |
| 업적 | **후속에 넣는 쪽으로 기운다.** 유물과 같은 이벤트 버스를 구독 (9장 확장 지점 4번) + 영구 저장은 메타 성장에 얹음 |
| 2인 온라인 코옵 (UGS) | **여지만 남긴다** — 아래 8.1. 계획이 아니라 "막지 않는다"는 뜻이다 |

### 8.1 2인 코옵 — 여지만 남긴다

UGS(Relay + Lobby) 와 Netcode for GameObjects 로 **2인 온라인 코옵**을 붙일 여지를
남겨둔다. **후속 계획이 아니다.** 1차에서 무심코 막아버리는 것만 피한다는 뜻이다.

PvP 와 달리 코옵은 이 게임의 전제를 깨지 않는다. 협력 플레이라 화면 정지·흔들림 같은
전역 연출을 **양쪽에 함께 걸어도 이상하지 않고**, 호스트 권위 방식이면 롤백 넷코드가
필요 없다. 반면 PvP 는 히트스탑·화면 흔들림이 전부 "시간이 한 명의 것"을 전제하므로
D 에픽 전체를 다시 설계해야 한다 — 이연이 아니라 다른 게임이다.

**1차에서 지킬 것은 둘뿐이고, 둘 다 지금 공짜다.**

| 지킬 것 | 안 지키면 |
|---|---|
| 플레이어를 **static·싱글턴으로 참조하지 않는다** | 플레이어가 둘이 되는 순간 "그 플레이어"가 누구인지 정해지지 않는다 |
| 방·보상·유물 생성을 **시드 기반**으로 (11.3 에서 이미 결정) | 두 클라이언트가 다른 맵을 본다. 동기화 비용이 통째로 생긴다 |

전역 연출(`HitStop` 등)이 `static` 인 것은 무방하다 — **연출은 하나여도 되지만 플레이어는
아니다.**

붙일 때 실제로 드는 비용은 따로 있고, 그건 그때 낸다: 네트워크 계층, 카메라(둘 추적),
부활 규칙, 히트스탑을 누구 기준으로 걸지.

**판단 시점은 1차 완성 후다.** 로드맵 후속 표의 1~2번(콘텐츠 물량, 스테이지 2)을 마친
시점에 여유를 보고 정한다. 그 전에 착수하면 콘텐츠가 빈 채로 넷코드만 있는 상태가 된다.

### 일정이 밀릴 때 절단 순서

**유물 수 → 방 프리팹 수 → 3번째 적** 순으로 줄인다.
**무기 교체 시스템과 보스는 마지막까지 지킨다** — 이 둘이 포트폴리오의 핵심이다.

## 9. 기술 설계 방향

설치된 패키지 기준 (`Packages/manifest.json`):

- **입력**: Input System 1.19 — 액션 맵 기반, 키보드/패드 동시 지원
- **2D 애니메이션**: `com.unity.2d.animation` (스켈레탈) + `com.unity.2d.aseprite` (프레임)
  → 1차에서는 **구매한 에셋이 제공하는 방식을 그대로 따른다** (10장 참조)
- **레벨**: Tilemap + Tilemap Extras, SpriteShape
- **렌더링**: URP 2D Renderer — 2D 라이트/노멀맵은 1차 범위 밖 (나중에 켜도 무방)

### 아키텍처 방향 (초안)

- 무기 = **ScriptableObject 데이터 + 런타임 behaviour** 분리.
  데이터 주도 설계여야 무기 추가가 싸진다.
- 상태 머신 기반 플레이어 컨트롤러 (Idle / Move / Jump / Attack / Swap / Hit)
- 전투 이벤트(피격, 사망, 스왑)는 이벤트 버스로 느슨하게 연결 → 유물이 여기 훅을 건다
- 유물 = 이벤트 훅 + 효과 조합. 유물마다 클래스를 파지 않는다

### 확장 지점 — 1차에서 반드시 지킬 것

기간이 짧다고 하드코딩하면 후속 작업이 재작성이 된다. 아래 네 가지만 지키면
**이연한 항목 대부분이 "데이터 추가"로 붙는다.** 구현 비용은 거의 늘지 않는다.

| 지점 | 지킬 것 | 안 지키면 |
|---|---|---|
| **무기** | SO 데이터 + 런타임 래퍼. 무기 목록은 배열/풀로 관리 | 무기 추가마다 코드 수정 |
| **적 / 보스** | 판단·실행 분리 (아래 9.1). 보스도 일반 적과 같은 틀 | 보스 2 추가 시 통째로 재작성 |
| **방** | 방 = 프리팹 + 메타데이터(타입, 난이도). 타입은 **핸들러 매핑** | 상점·이벤트방 추가가 분기문 지옥 |
| **유물** | 이벤트 훅 구독 + 효과 데이터. 유물별 클래스 금지. **이벤트 이름을 유물 전용으로 짓지 않는다** (`OnRelicTrigger` ❌ / `OnEnemyKilled` ⭕) | 20종으로 늘릴 때 클래스 20개. 업적이 붙을 때 버스를 다시 판다 |

> 반대로 **1차에서 하지 말 것**: 런 중간 저장, 메타 성장 세이브, 오브젝트 풀링 최적화,
> 난이도 스케일링, **에셋 로딩 파이프라인으로서의 Addressables**.
> 나중에 붙여도 재작업이 발생하지 않는 영역이다.
> (설정 저장과 로컬라이즈는 **1차에 포함한다** — 11장 참조)

> **Addressables 주의:** Localization 패키지가 테이블 로딩에 Addressables 를 쓰기 때문에
> `Assets/AddressableAssetsData/` 가 자동 생성된다. 이건 정상이며 **그대로 둔다**
> (그룹 설정이 빠지면 클론 시 로컬라이제이션이 붙지 않으므로 커밋 대상이다).
> 1차 범위 밖인 것은 "우리가 직접 에셋을 Addressables 로 로딩하는 것"이지, 이 자동 생성분이 아니다.

> 상세 설계는 프로토타입에서 실제 문제를 만난 뒤에 확정한다. 지금 과설계하지 않는다.

### 9.1 적 / 보스 AI 구조

일반 적과 보스는 **같은 틀**을 쓴다. 차이는 패턴 수와 페이즈 유무뿐이다.
W3에서 일반 적으로 이 틀을 잡아두면, W5의 보스는 새 시스템이 아니라 **패턴 데이터 추가 작업**이 된다.

```
EnemyBrain                          ← 일반 적 · 보스 공용
├─ IPatternSelector   판단 층 — "다음에 무엇을 할지"   ★교체 가능 지점
├─ StateMachine       실행 층 — Idle / Chase / Telegraph / Attack / Recover / Stagger / Dead
└─ AttackPattern (SO) 내용물 — 예고 시간, 히트박스 타이밍, 이동, 후딜, 사용 조건

Boss = EnemyBrain + PhaseController (HP 임계값 → 패턴 풀 교체 + 페이즈 전환 연출)
```

**핵심 원칙: 상태머신은 "무엇을 할지" 결정하지 않는다.**
상태는 `Telegraph → Attack → Recover` 사이클을 돌리는 껍데기이고, 그 안에서 재생되는 내용물은
`AttackPattern` 데이터가 들고 있다. 패턴을 10개 추가해도 상태 수는 변하지 않는다.

**안티패턴 — 공격마다 상태를 만드는 것**
`Attack_Slam` / `Attack_Dash` / `Attack_Summon` … 이렇게 가면 패턴이 늘 때마다 상태와 전이가
같이 늘어난다. 보스 2 추가 시 상태머신을 통째로 다시 짜게 되는 전형적인 원인이다.

**패턴 실행은 코루틴 타임라인으로.**
"0.4초 예고 → 0.1초에 히트박스 On → 0.25초에 Off → 0.5초 후딜" 같은 시퀀스는
상태를 더 쪼개는 것보다 코루틴이 훨씬 읽기 쉽고 수정도 빠르다.

#### 판단 층 — 1차는 가중치 셀렉터, BT는 후속 옵션

`IPatternSelector` 를 인터페이스로 두어 **판단 층만 통째로 갈아끼울 수 있게** 한다.
실행 층(상태머신 + `AttackPattern`)은 어느 쪽을 쓰든 그대로다.

| 구현 | 시점 | 방식 |
|---|---|---|
| `WeightedPatternSelector` | **1차** | 거리·쿨타임·페이즈 조건 + 가중치 추첨 |
| `BehaviorTreeSelector` | 후속 (검토) | BT가 패턴을 고르고, 실행은 기존 층에 위임 |

**1차에 BT를 쓰지 않는 이유:** 2D 액션 보스는 "거리 보고 패턴 하나 골라 끝까지 재생"이
대부분이라 가중치 셀렉터로 충분하다. 120시간 예산에 BT 프레임워크 학습·구축 비용을 넣을 자리가 없다.

**BT로 넘어갈 가치가 생기는 신호:**
- 패턴 선택 조건이 중첩되기 시작할 때 (조건문이 3단 이상 겹침)
- 적이 **동시에 여러 판단**을 해야 할 때 — 아군과의 협조, 지형 활용, 자원 관리, 후퇴/재접근
- 보스 페이즈가 3개 이상이 되고 페이즈마다 행동 성향이 크게 달라질 때
- 패턴 수가 적 1종당 6~7개를 넘어 가중치 테이블이 관리 불가능해질 때

위 신호가 없다면 BT는 순수 오버엔지니어링이다. **인터페이스만 지금 분리해두고,
실제 도입은 신호가 관측된 뒤에 판단한다.**

> 도입하게 되면 자체 구현보다 검증된 에셋(Behavior Designer 등) 또는 Unity 공식
> `com.unity.behavior` 검토가 우선이다. 1인 개발에서 BT 프레임워크 자체 구현은 배보다 배꼽이 크다.

## 10. 아트 / 사운드

**1차에서는 자체 아트를 제작하지 않는다.** 120시간 예산에서 아트 제작은 들어갈 자리가 없다.
유료 에셋을 그대로 쓰고, **에셋이 픽셀이면 픽셀·스켈레탈이면 스켈레탈로 간다.**
→ 기존 미결정 항목이던 "아트 파이프라인 선택"은 이렇게 해소된다.

- 에셋 위치: `Assets/Imported/` (별도 저장소, 부모에서 gitignore 처리됨)
- **0주차에 에셋을 먼저 확정한다.** 개발 중 에셋을 찾아다니면 일정이 무너진다.
  필요 최소: 캐릭터 1 + 적 3 + 무기 이펙트 3 + 타일셋 1 + 타격음 몇 종
- 사운드: 타격음 우선. 액션 게임에서 히트 사운드는 이펙트만큼 손맛에 기여한다

교체 가능성을 위해 스프라이트·애니메이터 참조는 **무기/적 데이터(SO)에 둔다.**
나중에 자체 아트로 갈아탈 때 코드를 건드리지 않아도 된다.

### 10.1 1차 아트 — Pixem (파츠 조합형 픽셀 캐릭터)

에디터에서 파츠(몸·머리·옷·무기·방패)를 조합해 캐릭터를 굽는 도구형 에셋이다.

> **1차 한정이다.** 실제로 넣어보니 의도한 방향과 어긋나는 부분이 있어, 여유가 생기면
> 다른 에셋으로 교체한다. 다만 **W1~W6 중에는 바꾸지 않는다** — 로드맵 리스크 표의
> "개발 중 에셋 쇼핑 금지"가 그대로 적용된다. 손맛 검증에 룩은 변수가 아니다.
>
> 교체 비용은 위 원칙(참조를 데이터에 둔다)을 지키는 한 낮다. 지킬 것은 하나다 —
> **클립 이름 문자열을 코드 여러 곳에 흩뿌리지 않는다.** `"Hit"` / `"Death"` 같은
> 이름은 에셋마다 다르고, W2 에서 무기 SO 로 옮겨갈 때 함께 데이터가 된다.

| | 값 |
|---|---|
| PPU | 32 |
| 프레임 | 64 × 64 → **월드 2 유닛** |
| 필터 | Point |
| 애니메이션 | Idle / Run / Jump / Hit / Death + **공격 4종** |
| 무기 파츠 | 왼손 23종 · 활 8종 · 방패 10종 |

공격 4종이 `AttackSlash` / `AttackPrick` / `AttackMagic` / `AttackShoot` 라 3장의 무기
아키타입(검·창·활)이 그대로 대응하고 단검·지팡이가 후속 확장으로 남는다. 적 3종(돌진·원거리·
방패)도 같은 파츠로 조합할 수 있어 9장 확장 지점 2(적·보스 공용 상태머신)와 맞는다.

**단, 무기 파츠는 전부 한손 무기다.** 실루엣으로 아키타입을 구분할 수 없어서 타이밍과
판정으로 나눈다. 근거는 3장 "아키타입은 스프라이트가 아니라 타이밍이 만든다".

**아직 없는 것: 타일셋.** W3 전까지 확보해야 하고, 캐릭터가 PPU 32 이므로 **타일도
32px 기준**이어야 한다. 16px 타일을 섞으면 디테일 밀도가 어긋난다.

#### 아트 제약 — 낙하 전용 포즈가 없다

시트의 스프라이트를 전부 확인한 결과 이 목록이 전부다.

```
Idle 4장 · Run 4장 · Jump 2장 · Hit 2장 · Death 3장
AttackSlash 3장 · AttackPrick 4장 · AttackShoot 4장 · AttackMagic 3장
```

`Jump` 가 **2장뿐**이다 — 이륙과 체공. 하강 포즈가 없어서 `FallState` 가 체공 프레임을
붙잡아 쓴다. 상승과 하강이 같은 그림이 된다.

넣으려면 프레임을 직접 그려야 하고(6종 × 1장), 컨트롤러에 `Fall` 상태도 추가해야 한다.
**베이스 컨트롤러는 6종이 공유**하므로 오버라이드마다 클립을 지정하는 작업이 붙는다.
1차에서는 넣지 않고 W6 폴리시 항목으로 둔다 — 되돌리기가 싸고 레벨 전제에 안 박힌다.

#### 클립이 전부 루프로 설정돼 있다

`Death` 만 빼고 9개 클립 모두 `m_LoopTime: 1` 이다. 일회성 클립(공격 4종 · `Hit` · `Jump`)
까지 루프라서, 모션이 코드 타임라인과 무관하게 자기 주기로 돈다.

**굽고 나면 루프 플래그를 끈다** — 굽기 절차의 일부다 (10.2). 다시 구우면 초기화된다.
`Idle` 과 `Run` 은 루프가 맞으므로 그대로 둔다.

### 10.2 무기 교체는 파츠가 아니라 프리팹 단위로 한다

`PixemCharacter` 의 조립 코드는 **전체가 `#if UNITY_EDITOR`** 로 감싸져 있다.
`AnimationUtility` 가 에디터 전용 API 이기 때문이다. 즉 **런타임에 무기 스프라이트만
갈아끼우는 것은 불가능하다.**

대신 조립 결과가 독립적인 에셋 세트로 떨어진다.

```
Modified/Resources/CharacterPrefabs/Character_N.prefab
Modified/Resources/CharacterResources/Character_N/
    Animations/  구워진 클립 9개 + 컨트롤러
    CharacterData_N.asset
    Character_N_Sheet.png        ← 파츠가 통합된 시트
```

스프라이트가 시트로 합쳐져 원본 `Pixem/Resources/Items/` 에 의존하지 않는다. 그래서
**무기별로 캐릭터를 미리 구워두고, 런타임에는 프리팹·애니메이터를 교체한다.**

이 방식이 3장의 의도에 오히려 더 맞는다. 무기가 바뀌면 클립 세트가 통째로 바뀌므로
베기와 찌르기가 모션으로 갈린다. 무기 SO 에 프리팹·컨트롤러 참조를 넣으면 9장 확장
지점 1(무기 SO 래퍼)이 그대로 커버한다.

**대가**: 대기 중인 무기를 등에 멘 모습처럼 **두 무기를 동시에 보여줄 수 없다.**
1차에서는 UI 로 표시한다.

#### 굽기 절차

도구가 만들어주는 데서 끝나지 않는다. **아래 셋은 매번 손으로 해야 한다.**

1. `Assets/Pixem/Resources/` 에 떨어진 결과물을 `Assets/Imported/Modified/Resources/` 로 옮긴다
   (`CharacterPrefabs` 는 `Resources.LoadAll` 대상이므로 `Resources` 아래를 벗어날 수 없다)
2. 프리팹과 리소스 폴더 이름을 **무기명으로 바꾼다.** 도구는 `Character_N` 번호로 만드는데,
   번호로는 어느 무기인지 열어봐야 알 수 있다 — 실제로 프리팹 목록에서 잘못 집는 사고가 났다
3. **일회성 클립의 루프를 끈다** — 공격 4종 · `Hit` · `Jump`. 안 끄면 콤보에서 모션이
   판정과 어긋난다 (10.1)

무기를 늘릴 때마다 반복된다. 1차에서는 검만 필요하므로 나머지 5종은 W2 에서 해당 무기를
붙이는 시점에 처리한다.

#### 재생 속도는 파생값이다

콤보 단계마다 클립 재생 속도를 다르게 줘야 타격 프레임이 히트박스와 맞는다. 이 값을
직접 넣지 않고 **치켜드는 프레임의 길이 ÷ `startup`** 으로 계산한다.

맞춰야 할 대상이 클립 전체 길이가 아니라 `startup` 이라는 게 핵심이다. 클립을 단계 길이에
맞추면 멈춤은 사라지지만 치켜드는 프레임이 늘어나 **히트박스가 나갈 때 아직 칼을 들고
있다.** `recovery` 구간에 마무리 자세가 떠 있는 건 후딜의 무게로 읽히므로 문제가 아니다.

W2 에서 클립 길이는 무기 SO 로 옮긴다. 무기마다 클립이 달라 값도 달라지고
(`AttackPrick` 은 4프레임), 클립 이름과 같은 자리에 있는 게 맞다. 3장의 "무겁게 =
느린 재생"이 이 필드다.

## 11. 설정 / 언어 / 저장

"세이브"를 한 덩어리로 다루면 판단이 꼬인다. **성격이 완전히 다른 세 가지**로 나눈다.

| 종류 | 대상 | 1차 포함 | 비용 |
|---|---|---|---|
| **설정 저장** | 볼륨, 해상도, 전체화면, 키 바인딩, 언어 | ✅ 포함 | 낮음 |
| **런 중간 저장** | 진행 중인 런을 중단·재개 | ❌ 이연 (자리는 남김) | 높음 |
| **메타 진행 저장** | 영구 강화, 해금 (7장) | ❌ 이연 | 중간 |

---

### 11.1 설정 (1차 포함)

포트폴리오에서 **옵션 화면이 없는 게임은 미완성으로 읽힌다.** 비용도 낮아 1차에 넣는다.

- 항목: 마스터/BGM/SFX 볼륨, 해상도, 전체화면, 언어
  (**키 설정은 1차 제외** — 11.4 참조)
- 저장 위치: JSON 파일 (`Application.persistentDataPath`). PlayerPrefs 는 항목이 늘면 관리가 어렵다
- **런타임 상태와 영구 상태를 섞지 않는다** — 설정은 `GameSettings` 하나에 모으고,
  이후 메타 성장 세이브가 붙어도 파일을 분리해 둔다

### 11.2 언어 / 로컬라이즈 — **1차: 한국어 + 영어**

> **앞선 판단 정정:** 로컬라이즈를 "나중에 붙여도 재작업 없는 영역"으로 분류했으나 이는 틀렸다.
> UI 문자열을 하드코딩해두면 나중에 전부 찾아 교체해야 한다. **나중에 하면 비싸지는 축**이다.

- **1차 지원 언어: 한국어 + 영어** (확정)
- 모든 UI 문자열을 **키로 참조**하고, 두 언어 테이블을 채운다
- **후속: 언어 추가 = 테이블에 열 추가.** 코드 수정 없음
- 방식: Unity Localization 패키지(`com.unity.localization` 1.5.12) 의 **String Table**
- 무기·유물·적 이름/설명도 SO에 직접 문자열을 박지 말고 **키를 들고 있게** 한다

**테이블 구성** (`Assets/_Project/Localization/`)

| 테이블 | 담을 것 | 쓰는 쪽 | 상태 |
|---|---|---|---|
| `UI` | 메뉴, 버튼, 설정 화면, 결과 화면 | `Game.UI` | 생성됨 |
| `Content` | 무기·유물·적 이름과 설명 | `Game.Core` (SO 정의) | SO 작성 시 생성 |

문자열의 **주인이 누구인지**로 나눈다. 하나로 몰아도 동작하지만 100개를 넘어가면 찾기 어려워진다.

> 1차 텍스트 분량이 적을 때(50~100개) 구조를 잡는 게 가장 싸다. 콘텐츠가 늘어난 뒤엔 몇 배가 된다.

### 11.3 런 중간 저장 — 로그라이크에 필요한가

**결론: 상용 기준으로는 필요하다. 다만 1차 범위 밖으로 이연하고, 붙일 자리만 남긴다.**

필요한 이유는 흔히 오해하는 "세이브 스커밍"이 아니라 **중단**이다. 1런이 20~30분이면
플레이어가 중간에 자리를 떠야 하는 상황이 반드시 생긴다. 그래서 상용 로그라이크
(하데스, 슬레이 더 스파이어, 스컬)는 거의 예외 없이 **이어하기**를 제공한다.

동시에 스커밍은 막아야 하므로, 업계 표준 방식은 이렇다:

- **슬롯 1개만** 유지
- **저장 = 게임 종료**, **로드 = 세이브 삭제** (delete-on-load)
- 즉 "중단 지점"이지 "체크포인트"가 아니다

**1차에서 빼는 이유:** 저장 시점을 방 안까지 허용하면 적 위치·체력·AI 상태·투사체까지
전부 직렬화해야 한다. 120시간 예산에서 감당할 작업이 아니다.

**나중에 싸게 붙이기 위해 1차에서 지킬 것:**

| 지킬 것 | 이유 |
|---|---|
| 런 상태를 `RunState` **하나의 순수 데이터**로 모은다 (MonoBehaviour 참조 금지) | 그대로 직렬화 대상이 됨 |
| `RunState` 에 담을 것: 플레이어 스탯, 무기 2슬롯, 유물 목록, 현재 방 인덱스, **RNG 시드** | 이것만으로 런 복원 가능 |
| 방 구성을 **시드 기반**으로 결정 | 방 배치를 저장할 필요가 없어짐 |
| 저장 지점을 **방 경계로만** 상정하고 설계 | 방 내부 상태를 직렬화할 필요가 사라짐 |

이 네 가지를 지키면 후속 작업은 **`RunState` JSON 덤프 + 로드 시 복원**이 전부다.
반대로 런 상태가 여러 MonoBehaviour에 흩어져 있으면 그때 가서 전면 재작성이 된다.

> `RunState` 는 7장의 `RunResult` 와 짝을 이룬다. 런 종료 시 `RunState` → `RunResult` 정산.

### 11.4 입력 — 장치 지원과 키 설정은 별개다

혼동하기 쉬우나 완전히 다른 작업이다.

| 항목 | 내용 | 1차 | 비용 |
|---|---|---|---|
| **키보드 + 게임패드 지원** | 두 장치를 모두 받는 것 | ✅ 포함 | 낮음 (~1h) |
| **키 설정 (리바인딩)** | 플레이어가 옵션에서 키를 바꾸는 것 | ❌ 이연 | 2~3h |

**장치 지원 (1차 포함)**
Input System 의 Control Scheme 으로 처리한다. 액션 맵 하나에 키보드·게임패드 바인딩을
두 벌 등록하면 끝이라 실질 추가 비용이 거의 없다. 숫자 키패드 등 추가 키도 바인딩 한 줄이다.

**키 설정 (이연)**
`PerformInteractiveRebinding` + 전용 UI + 중복 바인딩 충돌 검사 + 저장/로드가 필요하다.
1차 예산에서는 빼지만, **아래 한 가지만 지키면 후속 추가가 저렴하다.**

> **UI에 키 이름을 하드코딩하지 않는다.**
> `"E 키를 누르세요"` 처럼 박아두면 리바인딩을 붙일 때 전부 찾아 고쳐야 하고,
> 게임패드로 전환해도 키보드 표기가 그대로 남는다.
> `InputBinding.ToDisplayString()` / `GetBindingDisplayString()` 으로 **현재 바인딩에서 표시
> 문자열을 가져온다.** 그러면 장치 전환과 리바인딩이 자동 반영된다.
>
> 로컬라이즈와도 엮인다 — String Table 에는 `"{0} 키를 누르세요"` 형태로 넣고
> 키 이름은 런타임에 주입한다 (11.2).

후속 추가 시 저장은 Input System 이 제공하는
`SaveBindingOverridesAsJson()` / `LoadBindingOverridesFromJson()` 한 쌍으로 끝난다.

## 12. 미결정 사항 정리

| # | 항목 | 영향 | 결정 시점 |
|---|---|---|---|
| 1 | 타일셋 확보 (32px 기준) | 방 프리팹 치수 | **W3 착수 전** |
| 2 | 지상 공격 중 전진 여부·거리 | 콤보 리듬 · 적과의 간격 | **[#17](../../issues/17) 완료 후** |
| 3 | 화면 흔들림을 피격에만 둘지 | 타격감 · 접근성 | **[#17](../../issues/17) 중** |
| 4 | 스왑에 공격 판정 부여 여부 | 전투 성격 | W2 중 |
| 5 | 동일 무기 2개 장착 허용 | 빌드 다양성 | W2 후 |
| 6 | 업적을 실제로 넣을지 | 저장 포맷 · UI 물량 | **후속 5번(메타 성장) 착수 직전** |
| 7 | 2인 코옵(UGS) 착수 여부 | 후속 일정 전체 | **후속 1~2번(콘텐츠·스테이지 2) 완료 후** |

2번은 **되돌리기 비용이 대칭**이라 지금 정하지 않는다. 넣는 것도 빼는 것도 값 하나이고
레벨 전제에 박히지 않는다. 판단 근거가 될 상황 — 적이 추격하고 물러나는 것 — 이 #17
전에는 없으므로, 지금 감으로 정하면 필요 이상으로 넣게 된다.

**단 [#13](../../issues/13) 이 통로는 만들어야 한다.** `HandleHorizontal` 이 매 `FixedUpdate`
마다 수평 속도를 다시 쓰기 때문에, 넉백이든 전진이든 **코드가 부여한 속도가 눌리지 않는
구간**이 필요하다. 이게 없으면 넉백 5 가 `groundDecel` 35 에 0.14초 만에 깎인다.
값은 나중에 정해도 되지만 통로는 넉백과 공유하므로 #13 에서 함께 선다.

3번은 **피격 흔들림을 아직 느껴본 적이 없어서** 지금 정하지 않는다. #14 시점에는 적이
공격하지 않으므로 타격 흔들림만 겪은 상태이고, 그 상태에서의 선호는 관찰이 아니라 예측이다.

기울어진 방향은 **피격에만 두는 쪽**이다. 근거가 있다 — **피격 흔들림은 정보고 타격
흔들림은 연출이다.** "내가 맞았다"를 알리는 건 취향으로 뺄 수 없는 기능이지만, 타격 쪽은
없어도 게임이 성립한다. 접근성 측면에서도 흔들림 총량이 줄어드는 게 낫다.

바꾸는 비용은 **값 두 개**다. 강도가 `DamageInfo` 를 타고 오므로 코드 변경이 없다.

```
플레이어 3타  shakeStrength  0.02 → 0
적 공격       shakeStrength  0    → 0.03 쯤
```

#17 에서 실제로 맞아본 뒤, 타격을 0 으로 두고 한 번 돌려서 "밋밋한지 깔끔한지"로 정한다.

6·7 번은 1차 범위 밖이라 지금 정하지 않는다. 다만 **결정 시점이 오면 그때 물어야 한다** —
그 전에 착수하면 콘텐츠가 빈 채로 시스템만 있는 상태가 되고, 지나쳐 버리면 이미 짜둔
저장·이벤트 구조를 다시 손대게 된다. 판단 근거는 8장(업적)과 8.1(코옵)에 있다.

| 유료 에셋 | **Pixem** (파츠 조합형 픽셀 캐릭터). PPU 32 · 2유닛 | 10.1 |
| 무기 교체 표현 | 파츠 교체가 아니라 **무기별 프리팹·애니메이터 교체** | 10.2 |

### 12.1 2단 점프를 넣지 않는다 ([#8](../../issues/8))

W1 시점에 1단 점프의 체감을 확인한 결과 체공 시간과 낙하 속도가 충분했다. 도달 범위가
부족하면 `jumpHeight` 를 올려 해결한다 — 점프 파라미터를 속도가 아니라 **높이 단위**로
노출해뒀기 때문에 레벨 치수와 직접 비교할 수 있다.

**되돌리기 비용이 비대칭이라는 게 결정적이었다.**

| | 비용 |
|---|---|
| 1단으로 설계 → 나중에 2단 추가 | 싸다. 기존 방이 전부 통과 가능해지고 난이도만 내려간다 |
| 2단으로 설계 → 나중에 제거 | 비싸다. "2단으로만 닿는 높이"가 레벨 전체의 전제가 되어 방을 다시 그려야 한다 |

**대가: 공중 기동이 스왑 대시 하나로 몰린다.** W3 방 설계에 제약이 생긴다 —
**스왑 쿨다운 중에도 통과 가능해야 한다.** 어기면 쿨다운 동안 갇히는 방이 나온다.

#### 나중에 추가한다면 (이연 방법)

1. `PlayerMovement` 에 남은 점프 횟수 카운터. 접지 시 리셋
2. `TryJump` 의 거부 조건에서 **접지·코요테 검사와 횟수 검사를 분리**한다.
   공중에서 첫 점프를 쓴 경우(코요테 소진 후 낙하 중)를 어떻게 셀지가 실제 쟁점이다
3. **`machine.Change(Jump)` 가 무시된다** — 이미 `Jump` 상태면 `StateMachine` 의
   같은-상태-무시 규칙에 걸려 `Enter()` 가 다시 돌지 않는다. 공중 점프 모션이 재생되지
   않는다. `DoubleJumpState` 를 별도로 두거나 `Change(state, force: true)` 경로가 필요하다.
   학습 로그 5절에서 예외로 언급한 `force` 가 실제로 필요해지는 첫 사례다

> 무기 등급제·이벤트방 등 나머지 항목은 8장에서 **이연**으로 정리했으므로
> 1차에서는 결정할 필요가 없다. 확장 지점만 남겨두면 된다.
