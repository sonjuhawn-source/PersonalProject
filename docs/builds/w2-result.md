# W2 빌드 결과 — v0.2

> 2026-08-14 · Windows x64 · 태그 `w2` · 상세: [빌드 노트](w2.md) · [빌드 계획](w2-plan.md)

## 결과

**W2 구현이 빌드에서 문제없이 실행됨** (플레이 확인).

**빌드는 한 번에 통과했다.** W1 과 갈린 지점이다 — 그때는 컴파일이 깨졌고, 원인이던 Pixem
스크립트의 `using` 가드가 이번에는 그대로 살아 있었다. W2 에서 캐릭터를 다시 굽지 않아서다.

계획서대로 두 번 눌렀고 둘 다 통과했다.

| 시점 | 목적 | 결과 |
|---|---|---|
| [#45](../../issues/45) 직후 | `Content` String Table 이 빌드에 들어가는가 | 통과 — 무기 이름이 `검` 으로 읽혔다 |
| W2 종료 | 회귀 확인 + 정산 | 통과 |

## 검증 범위

| | |
|---|---|
| 확인한 것 | 빌드 산출 · 실행 · W1 회귀 · W2 신규 기능의 플레이 동작 |
| 확인 방식 | 직접 플레이 |
| 확인 안 한 것 | 게임패드 · 다른 해상도 · 다른 PC · **창(무기) 동작** · **빌드 크기 비교** |

**창은 이 빌드에 없다.** 슬롯을 검 + 활로 맞바꿨기 때문이다(아래 참조). 창의 리듬과
사거리는 [#62](../../issues/62) 에서 에디터로 확인했다.

**빌드 크기는 비교하지 못했다.** 계획서에 "W1 과 비교"로 적어뒀는데 [W1 노트](w1.md)에
크기가 기록돼 있지 않다. 기준이 없어서 이번에는 넘어가고, **W3 부터 비교가 가능해진다.**

### W1 회귀 — 이상 없음

[#45](../../issues/45) 가 `PlayerMovement` 에서 `combo` 와 `clipWindup` 을 들어냈으므로
콤보가 가장 위험했다.

좌우 이동 · 가변 높이 점프 · 코요테 타임 · 점프 버퍼 · 3타 콤보와 선입력 · 콤보 타임아웃 ·
히트스탑 · 넉백 · 화면 흔들림 · 피격 무적과 깜빡임 · 적 추격과 예고·공격·경직.

**[W1 노트](w1.md)의 수치와 체감이 어긋난 곳은 없었다.**

### W2 신규 — 이상 없음

무기 이름이 로컬라이즈 키가 아니라 실제 문자열로 나옴 · 스왑으로 외형과 모션이 함께 바뀜 ·
스왑 대시가 적 공격을 흘림(i-frame) · 쿨타임 중에는 안 바뀜 · 검과 활의 사거리와 리듬이
서로 다르게 느껴짐 · 화살이 날아가 맞고 사라지며 발사자를 안 때림 · 지상 공격 중 전진 ·
스왑 순간 한 프레임 옛 그림이 보이지 않음.

몇 분 돌려도 프레임이 떨어지지 않았다 — 계획서 5번(화면 밖 화살이 안 죽고 쌓이는 문제)은
**나타나지 않았다.** `Projectile.lifetime` 2초가 일하고 있다.

## 빌드에서만 드러난 문제 — 0건

**실행 후 문제는 없었다.** 대신 **빌드 전에 하나를 잡았다.**

### 활이 빌드에 안 들어갈 뻔했다

계획서 2번이 경고한 그대로다.

```
startingWeapons  [0] Weapon_Sword
                 [1] Weapon_Spear

Weapon_Bow       씬·코드 어디서도 참조 안 됨
```

**`ScriptableObject` 는 누가 참조해야 빌드에 포함된다.** 에디터에서는 인스펙터로 끌어다
놓으면 되니 증상이 전혀 없다. 그대로 빌드했다면 활이 통째로 빠졌고, **계획서 5번(투사체
수명)을 검증할 방법 자체가 없었다.**

**검 + 활로 맞바꿔 빌드했다.** 창을 빼는 대신 투사체를 검증하는 쪽을 택했다 — 창은
에디터에서 방금 확인했고 투사체 수명은 빌드에서만 드러나는 축이기 때문이다.

근본 대응(무기 목록 SO 하나에 3종 담기)은 **W4 로 미뤘다.** 보상 시스템이 무기 풀을 만들
때 정면으로 만나므로 그때 실제 소비자와 함께 짓는 게 맞다.

### 계획서 체크 항목 하나가 낡아 있었다

> `AttackState` 를 한 줄도 안 고쳤다

[#45](../../issues/45) 시점의 기대였다. 이후 [#48](../../issues/48)·[#49](../../issues/49)
에서 공격 방식 분기(`AttackKind`)가 들어가며 실제로 수정됐다. **틀린 체크였다.**

계획서는 주차 착수 전에 쓰므로 주차 안에서 설계가 바뀌면 어긋난다. 계획을 고칠 일은
아니지만 **결과 문서에서 정정해두지 않으면 나중에 "안 고쳤다"로 읽힌다.**

## 이번 빌드에서 배운 것

**빌드를 두 번 나눠 누른 것이 값을 했다.** [#45](../../issues/45) 직후 빌드가 없었다면
로컬라이즈 문제와 활 참조 문제를 W2 종료 시점에 함께 만났을 것이고, 그러면 어느 쪽이
원인인지 가르는 데 시간이 든다.

> **위험이 새로 생기는 지점마다 누른다.** 주차 끝은 최소 기준이지 유일한 시점이 아니다.

**빌드는 참조 그래프를 검사하는 도구이기도 하다.** W1 에서 배운 것이 "컴파일이 에디터와
다르다"였다면, 이번에 배운 것은 **"에디터에서 손으로 끌어다 놓을 수 있는 것과 빌드에
포함되는 것은 다르다"** 이다. 둘 다 에디터에서는 증상이 없다는 공통점이 있다.

이 축은 W4 보상 시스템에서 정면으로 다시 만난다. 무기·유물을 런타임에 고르려면 풀이
있어야 하고, 풀이 없으면 **에디터에서만 되는 게임**이 된다.

않았고, 대신 각각이 어느 주차로 가는지가 정해졌다.

## 주말 산출물 판정

로드맵의 W2 주말 산출물은 **"무기 2개를 번갈아 쓰며 싸운다"** 였다.

계획서가 절단을 대비해 판정 기준을 미리 적어뒀다.

> [#51](../../issues/51)·[#52](../../issues/52)를 이연했다면 (…) **주말 산출물은 그래도
> 성립해야 한다** — 스왑의 대시와 i-frame 이 회피기 역할을 하기 때문이다.
> 빌드에서 그 문장이 성립하지 않으면 **절단 판단이 틀린 것**이므로 노트에 남긴다.

**성립했다.** 검과 활이라 거리 관리가 들어가면서 오히려 스왑의 값어치가 잘 보였다.
근접에서 밀리면 스왑으로 빠져나와 활로 견제하고, 다시 붙을 때 스왑으로 파고든다.

**절단 판단은 유지한다.**
