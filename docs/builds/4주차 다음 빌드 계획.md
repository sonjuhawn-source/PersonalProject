# 4주차 다음 빌드 계획 — 최종 빌드 (제출물)

> 작성 2026-08-27 (v0.4 빌드 직후) · 관련: [W4 결과](4주차%20빌드%20결과.md) · [로드맵](../roadmap.md)

**다음 빌드가 제출물이다.** 마감 2026-09-04(금).

v0.4 에서 루프가 완성됐으므로 남은 것은 **"동작하는가"가 아니라 "남에게 넘길 수 있는가"** 다.
[W4 결과](4주차%20빌드%20결과.md)에서 나온 문제 둘이 전부 "모르겠는" 종류였던 것이 그 신호다.

| 시점 | 왜 |

| **[#120](../../issues/120) 이 들어간 날** | **빌드 씬이 2개가 된다.** 씬 전환은 빌드에서 처음 도는 경로다 |
| **마감 하루 전 (09-03)** | 고칠 시간이 남는 마지막 날 |

**중간 것이 핵심이다.** W1 은 첫 빌드에서 컴파일이 깨져 있었고 W2 는 활이 빠질 뻔했다.
**마지막 날 처음 누르면 고칠 시간이 없다.**

v0.4 가 한 번에 통과한 것이 방심의 근거가 되면 안 된다 — 이번에 통과한 이유는
**누르기 전에 정적으로 다 확인했기 때문**이지 위험이 없어서가 아니다.

**1 — [#102](../../issues/102) 보상방 3택 1** (2~2.5h)

남은 것 중 **유일하게 게임플레이를 바꾼다.** 나머지 둘은 표현이다.

- [ ] 무기를 고르면 슬롯 교체

- [ ] 선택지 종류를 열거형으로 고정하지 않는다

**2 — [#103](../../issues/103) 보상 · 결과 UI** (2h)

`#104` 가 `RunResultView` 를 만들어서 **결과 화면은 이미 끝났다.** 남은 것은 3택 1 화면,

유일한 안내인데, 제출물은 문서를 안 읽어도 플레이할 수 있어야 한다.

**4 — 밸런스** (1h)

`#102` 가 서고 나서 한 번에 잡는다. 지금 값으로 덮으면 판단 재료가 사라진다.

spawnCount     difficulty 와 따로 논다 — Room_2 가 난이도 1 인데 8마리, Room_4 가 12마리

## 새로 생기는 위험

### 1. 빌드 씬이 2개가 된다 — 가장 큰 것

[#120](../../issues/120) 이 새 씬을 만든다. **지금까지 씬은 하나뿐이었고 씬 전환이 없었다.**

```
EditorBuildSettings   시작 씬이 index 0 이어야 한다. 순서를 확인한다
static                씬 전환에서 살아남는다 — HitStop · Shake
Restart()             SceneManager.LoadScene(GetActiveScene().buildIndex) 는 그대로 맞다
```

**타이틀 → 게임 → 타이틀** 이 생기면 `static` 이 두 방향으로 넘어간다. v0.4 에서 재시작
(같은 씬 리로드)은 통과했지만 **다른 씬으로 갔다 오는 것은 아직 안 돌았다.**

`Shake.instance` 는 `OnDestroy` 에서 `instance == this` 일 때만 비운다. 씬 전환 순서에 따라
**새 `Shake` 의 `Awake` 가 옛 것의 `OnDestroy` 보다 먼저 돌면 instance 가 null 로 남는다** —
화면 흔들림이 조용히 죽는다. 로드에서 확인할 항목이다.

### 2. String Table 에 문자열이 늘어난다

`#103` 이 보상 화면 문자열을 넣고 `#120` 이 시작 화면 문자열을 넣는다.

**W2 에서 겪은 것** — 참조 사슬이 없으면 빌드에 안 들어간다. 새 테이블을 만들거나
새 항목을 추가하면 **빌드에서 한 번 확인해야 한다.**

그리고 결과 화면이 지금 **문자열을 하드코딩**하고 있다 (`StageRunner.EndRun` 이 한국어를
직접 조립). `#103` 이 String Table 로 옮기면 그때 처음 로케일을 탄다.

> 영어는 절단됐다(한국어만). 다만 **로케일이 영어로 잡히면 빈 문자열이 나올 수 있다** —
> 폴백이 한국어로 걸려 있는지 확인한다.

### 3. 폰트가 런타임에 굽는다

[#124](../../issues/124) — Dynamic 폰트라 새 글자가 나올 때마다 아틀라스에 굽는다.
문자열이 늘어나면 **빌드에서 첫 표시 때 히칭**이 생길 수 있다.

Static 으로 굽는 것은 **String Table 이 확정된 뒤**가 적기다. 시간이 남으면 마지막에 한다.

### 4. `#102` 의 `internal` 벽

지금까지 UI 는 한 방향이었다 — `Gameplay` 가 이벤트를 쏘고 `UI` 가 듣는다.
**보상 선택은 왕복이 필요하다.**

asmdef 가 `Core ← Gameplay ← UI` 단방향이고 `IRoomHandler`·`RewardRoomHandler` 가
`internal` 이라 `Game.UI` 에서 안 보인다. 답을 돌려줄 창구를 `StageRunner`(`public`) 에
내야 한다.

**여기서 뚫으면 [#112](../../issues/112) 도 싸진다** — `WeaponHolder.Current` 가 같은 벽이다.

## 빌드 전 에디터에서 거를 것

**v0.4 에서 이 목록으로 왕복이 0 이었다.** 그대로 쓰고 두 항목을 더한다.

```
□  컴파일 에러 0
□  빌드 씬 목록 — #120 이후 2개 · 시작 씬이 index 0        ← 새 항목
□  Pixem 의 using UnityEditor 셋에 #if UNITY_EDITOR 가드
□  테스트 값 잔류 — roomCount · seed · maxHealth · healAmount
□  씬 저장 (git status 로 확인)
□  UI 배선 — HealthBar · RunResultView · 새 보상 화면 · 시작 화면   ← 확장
□  bundleVersion 을 0.5 로
```

**테스트 값 잔류가 반복 실수다.** 로드맵 메모에 *"오늘 seed 가 세 번, roomCount 와 보스
maxHealth 가 한 번씩 남았다"* 고 적혀 있다. `#102` 검증은 보상방까지 가야 해서
**`maxHealth` 를 올릴 일이 확실히 생긴다.**

## 제출물 구성

빌드만으로는 부족하다. 예산 3h 안에 셋이다.

| | 담을 것 |
|---|---|
| **빌드** | Windows x64 · v0.5 |
| **README** | 무엇을 만들었나 · 조작 · 구조(확장 지점 4개) · 무엇을 안 넣었고 왜 |
| **시연 영상** | 런 한 판 완주 — 전투 · 스왑 · 보상 · 보스 · 결과 |

**README 에서 절단 근거를 적는 것이 포트폴리오로서 값이 크다.** 유물·무기 스킬·보스 페이즈 2
가 왜 빠졌는지가 로드맵과 학습 로그에 남아 있고, 그것이 "못 만든 것"이 아니라 "판단한 것"
이라는 증거다.

시연 영상은 **한 판을 끊지 않고** 찍는 것이 낫다. 편집한 영상은 루프가 실제로 도는지를
증명하지 못한다.

## 기록

이번 빌드에서 배운 것을 다음에도 쓴다.

> **빌드는 확인하는 자리가 아니라 확인한 것을 증명하는 자리다.**

그리고 루프가 완성되면서 판단 기준이 바뀌었다.

> **동작하는가 → 알 수 있는가**

`#120` 이 원래 계획에 없다가 생긴 것, `#96` 적 구분, `#102` 보상방 인지가 전부 후자다.
최종 빌드의 검증 항목도 그 기준으로 짠다 — **처음 켠 사람이 문서 없이 한 판을 돌 수 있는가.**
