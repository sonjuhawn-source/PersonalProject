## 1. Git / 저장소

### push가 거부됐다

```
! [rejected]  master -> main (fetch first)
```

**원인** 로컬 `master` 와 원격 `main` 이 **공통 조상이 없는 별개의 히스토리**였다.
GitHub이 저장소 생성 시 `.gitignore` 커밋 하나를 만들어 뒀고, 로컬은 별도로
`Initial commit` 을 만들어서 fast-forward가 불가능했다.

**해결** 원격 커밋에 보존할 게 없었으므로 브랜치명을 `main` 으로 맞추고
`--force-with-lease` 로 덮어썼다.

**교훈** `failed to push some refs` 는 요약 줄일 뿐이고, 진짜 원인은 그 위의 힌트 줄에 있다.
용량·인증 문제로 착각하기 쉽다.

### `.git` 이 885MB였다

`git count-objects -vH` 로 확인하니 pack이 885MB인데, 그 안의 29,421개 객체가
**전부 unreachable(고아)** 이었다. HEAD에서 도달 가능한 객체는 56개뿐.

과거에 `git add .` 로 Unity `Library/` 를 통째로 스테이징했다가 되돌린 흔적이었다.
`reflog expire` + `gc --prune=now` 로 **885MB → 188KB**.

**교훈** git은 한 번 만들어진 객체를 스스로 지우지 않는다. 스테이징만 해도 객체가 생긴다.

### 빈 저장소에 push가 안 됐다

```
error: src refspec main does not match any
```

**원인** 커밋이 0개라 `main` 이라는 ref가 아예 존재하지 않았다. "브랜치가 없다"는 뜻.

**교훈** 폴더가 비어 있으면 push할 대상이 없다. 저장소만 clone해 둔 상태와 커밋이 있는
상태는 다르다.

### Git LFS를 왜 쓰는가

git은 **모든 버전의 모든 파일을 영구 보존**한다. 텍스트는 델타 압축이 잘 되지만
바이너리는 거의 안 된다. 80MB `.unitypackage` 를 10번 수정하면 저장소에 800MB가 쌓이고,
**파일을 지워도 히스토리에는 남는다.**

LFS는 실물을 별도 서버에 두고 git에는 130바이트 포인터만 남긴다. 체크아웃할 때
현재 필요한 버전만 받는다.

| | LFS 없음 | LFS |
|---|---|---|
| 80MB × 10회 수정 | 저장소 800MB | 저장소 1.3KB + LFS 800MB |
| 클론 | 전부 | 최신 버전만 |
| GitHub 100MB 제한 | 푸시 거부 | 통과 |

**핵심: 순서를 되돌릴 수 없다.** LFS 없이 커밋된 파일은 나중에 LFS를 걸어도 히스토리에
남아 용량이 줄지 않는다. 고치려면 히스토리 전체 재작성이 필요하다.
→ 그래서 에셋을 넣기 **전에** `.gitattributes` 를 먼저 커밋했다.

주의: GitHub 무료 LFS는 저장 1GB / 월 대역폭 1GB.

### `.meta` 를 gitignore하면 안 된다

자동 생성되니 빌드 산출물처럼 보이지만 **원본 데이터**다.

1. **GUID** — Unity의 모든 참조는 경로가 아니라 GUID로 연결된다. `.meta` 가 없으면
   임포트 시 새 GUID가 발급되고, 그 에셋을 참조하던 프리팹·머티리얼·스크립트 연결이
   전부 끊긴다.
2. **임포트 설정** — 스프라이트 슬라이싱 좌표, 텍스처 압축, 리그 본 매핑 등이 여기 있다.

**단 하나의 예외** 폴더 자체를 무시할 때는 그 폴더의 `.meta` 도 무시한다
(`Assets/Imported.meta`). 다른 곳에서 클론하면 폴더가 없어서 Unity가 고아 메타를
삭제하고, 그게 매번 변경으로 잡힌다.

씬을 옮길 때 `.meta` 를 함께 옮겨 GUID를 유지한 것도 같은 원리다.

### 커밋 메시지를 한국어로 일괄 변경

`filter-branch --msg-filter` 로 9개 커밋 메시지를 교체. 내용은 그대로(트리 diff 없음).

대가: **모든 해시가 바뀌고 force push가 필요하다.** 이미 머지된 PR의 머지 커밋 참조가
끊긴다. 백업 브랜치를 먼저 만들어 두고 진행했다.

**교훈** 히스토리 재작성은 커밋이 적고 혼자 쓸 때가 가장 싸다.

## 2. Unity 프로젝트 구조 (asmdef)

### asmdef가 뭐고 왜 쓰는가

asmdef가 없으면 Unity는 모든 스크립트를 `Assembly-CSharp` 하나에 쓸어담는다.
그러면 한 줄만 고쳐도 전부 재컴파일되고, 아무 코드가 아무 코드나 참조할 수 있다.

asmdef는 **"이 폴더 이하를 별도 DLL로 컴파일한다"** 를 선언한다. 별도 어셈블리가 되면
다른 어셈블리를 쓰려면 참조를 명시해야 한다.

**목적 4가지**
1. 증분 컴파일 — 바뀐 어셈블리와 그것에 의존하는 것만 재컴파일
2. **의존 방향 통제** ← 이 프로젝트에서 쓰는 실질적 이유
3. 조건부 포함 (`includePlatforms: ["Editor"]`)
4. 배포 단위

우리 구조. 화살표가 역류하지 않는 것을 컴파일러가 보증한다.

```
Game.Core  ←  Game.Gameplay  ←  Game.UI
```

Gameplay가 UI를 참조하지 못하므로, UI를 갈아엎어도 게임 로직은 안전하다.
순환 참조는 Unity가 아예 에러로 막는다.

### 반드시 알아야 할 규칙 — 참조는 단방향

> asmdef 어셈블리는 `Assembly-CSharp` 를 **참조할 수 없다.** 반대는 가능하다.

이유는 **컴파일 순서**다. Unity는 asmdef 어셈블리들을 먼저 컴파일하고
`Assembly-CSharp` 를 맨 마지막에 컴파일한다. 먼저 만들어지는 쪽이 나중 것을 볼 수 없다.

**실전에서 걸린 곳** Input System의 `Generate C# Class` 기본 생성 경로는 에셋과 같은
폴더 = `Assets/` 루트 = `Assembly-CSharp`. 그대로 두면 `Game.Gameplay` 의
`PlayerInputReader` 에서 쓸 수 없다.
→ 생성 경로를 `Scripts/Gameplay/Player/` 로 지정해서 같은 어셈블리에 들어가게 했다.

### 유료 에셋에 asmdef가 필수인가

아니다. **우리 코드에서 `using` 으로 직접 호출할 때만** 필요하다.

| 상황 | 필요? |
|---|---|
| 코드 없는 에셋 (아트·사운드) | 무관 |
| 코드는 있지만 프리팹 컴포넌트로만 동작 | 불필요 |
| 우리 코드에서 이름으로 호출 | 필요 |

asmdef 없는 에셋 코드는 `Assembly-CSharp` 안에서 잘 돌아간다. 막히는 건 우리가
부를 때뿐이다.

에셋에 asmdef를 새로 넣으면 그 코드가 참조하던 것들에서 컴파일 에러가 연쇄로 날 수 있다.
→ 순서: ①그냥 써본다 ②호출을 피할 방법을 찾는다(인스펙터 연결) ③그래도 안 되면 추가

### `autoReferenced: false`

켜두면 `Assembly-CSharp` 가 우리 어셈블리를 자동 참조한다. 끄지 않으면 의존 방향이
은근슬쩍 무너진다.

### asmdef 밖의 코드에는 그 방어가 없다

6절에 "IDE 가 `using Unity.VisualScripting...` 을 넣었는데 **asmdef 덕분에 컴파일 시점에
잡혔다**"고 적어뒀다. 그 문장의 범위를 좁혀야 한다.

W1 빌드에서 Pixem 스크립트 세 개가 `using UnityEditor;` 를 `#if UNITY_EDITOR` 밖에 두고
있어 빌드가 깨졌다. 이 스크립트들은 `Assets/Imported/Pixem/Scripts/` 에 있고 **asmdef 가
없어서 `Assembly-CSharp` 로 들어간다.** 우리 어셈블리가 아무리 잘 닫혀 있어도, 같은
빌드에 들어가는 다른 어셈블리가 깨지면 빌드는 안 나온다.

**asmdef 는 우리 코드가 남의 것을 잘못 참조하는 걸 막을 뿐, 남의 코드가 깨지는 건 못
막는다.** 유료 에셋이 `Assets/` 루트에 코드를 두면 그 코드는 항상 플레이어 빌드 대상이다.

`Game.*` 가 `Assembly-CSharp` 를 참조할 수 없다는 제약(CLAUDE.md)과 같은 뿌리인데
방향이 반대다 — 참조는 못 하지만 **빌드 운명은 공유한다.**

### 참조에 안 적으면 "그런 타입이 없는" 것처럼 보인다

`WeaponData` 에 `LocalizedString` 을 넣으려는데 **자동완성에 아무것도 안 떴다.** 패키지가
설치돼 있는데도 그랬다.

`Game.Gameplay` 의 참조 목록에 `Unity.Localization` 이 없었다. `autoReferenced: false` 라
**적지 않은 어셈블리는 아예 존재하지 않는 것처럼 보인다** — `using` 이 안 걸리는 게 아니라
타입 자체가 안 보인다.

W0 에서 로컬라이즈를 붙일 때 `UI` 테이블만 있어 `Game.UI` 에만 넣었다. **그때는 맞는
판단이었고**, `Content` 테이블이 생기면서 소비자가 하나 는 것이다. 참조 목록은 한 번 정하고
끝나는 게 아니라 소비자가 늘 때마다 다시 본다.

증상이 "패키지가 안 깔린 것 같다"로 보이는 게 함정이다. **패키지 설치와 어셈블리 참조는
다른 층이다.** Package Manager 에서 설치돼 있는데 안 보이면 asmdef 를 먼저 본다.

외부 패키지는 어느 층에서 참조해도 `Core ← Gameplay ← UI` 방향과 무관하다.
`Unity.InputSystem` 을 `Game.Gameplay` 가 이미 참조하고 있는 것과 같다.

### 에디터에서 도는 것과 빌드가 되는 것은 다르다

`using UnityEditor;` 가 가드 밖에 있으면 **에디터에서는 아무 증상이 없다.** 에디터에는
`UnityEditor` 어셈블리가 있으니까. 플레이어 빌드에만 없어서 `CS0246` 이 난다.

즉 **에디터 콘솔이 깨끗한 것은 빌드가 된다는 증거가 아니다.** 이 축의 오류는 빌드를
눌러야만 드러난다.

GDD 에 "`PixemCharacter` 의 조립 코드는 **전체가 `#if UNITY_EDITOR` 로 감싸져 있다**"고
적어뒀는데, 감싸진 건 **클래스 본문**이었고 `using` 은 아니었다. "감싸져 있다"를 확인할 때
**어디부터 어디까지인지를 안 봤다.**

## 3. Input System

### 개념 모델

```
Device  →  Control(경로)  →  Binding  →  Action  →  Action Map  →  Asset
```

**핵심: 액션이 장치를 모른다.** `Jump` 는 스페이스바인지 A버튼인지 신경 쓰지 않는다.
그래서 리바인딩과 패드 지원이 공짜로 따라온다. 이게 Input System 존재 이유의 전부.

### 액션 타입과 페이즈

| 타입 | 언제 |
|---|---|
| `Value` | 연속 값, 매 프레임 읽음 (`Move`) |
| `Button` | 눌림/떼임 순간 (`Jump` `Attack` `Swap`) |
| `PassThrough` | 필터 없이 전부 통과 |

폴링으로 가면 페이즈(`Started`/`Performed`/`Canceled`)를 몰라도 된다.
`WasPressedThisFrame()` / `IsPressed()` / `WasReleasedThisFrame()` / `ReadValue<T>()` 만 쓴다.

함정: **`Value` 타입은 값이 0으로 돌아갈 때 `Canceled`** 가 뜬다. 콜백으로 `Move` 를
받으면 손을 뗐을 때 0을 넣어주지 않으면 계속 걷는다.

### Pause를 어느 맵에 둘까

처음엔 "Player 맵에 두면 일시정지 때 그 맵을 끄니까 해제할 수 없다"고 판단했다.
**틀렸다.** 진입과 해제를 같은 액션이 할 필요가 없다.

```
게임플레이 중:  Player ON,  UI ON   →  Esc = Player.Pause  → 진입, Player OFF
일시정지 중:    Player OFF, UI ON   →  Esc = UI.Cancel     → 해제, Player ON
```

같은 Esc지만 활성화된 맵이 다르니 충돌하지 않는다. W5에서 일시정지 안에 설정 화면을
중첩할 때 `Cancel` 이 한 단계씩 뒤로 가는 게 자연스럽다.

**맵 단위 Enable/Disable** 이 여기서 필요하다. `actions.Enable()`(전체)이 아니라
`actions.Player.Enable()`. 전체를 끄면 UI까지 죽는다.

### 장치 지원 ≠ 키 설정

혼동하기 쉬운데 완전히 다른 작업이다.

| | 내용 | 비용 |
|---|---|---|
| 키보드 + 게임패드 지원 | 두 장치를 모두 받음 (Control Scheme) | ~1h |
| 키 설정 (리바인딩) | 플레이어가 옵션에서 키를 바꿈 | 2~3h |

리바인딩을 이연했는데, 그게 싸게 유지되는 조건이 하나 있다.
**UI에 키 이름을 하드코딩하지 않는 것.** `"E 키를 누르세요"` 로 박으면 리바인딩 붙일 때
전부 찾아 고쳐야 하고, 게임패드로 전환해도 키보드 표기가 남는다.
`GetBindingDisplayString()` 으로 현재 바인딩에서 가져오면 자동 반영된다.

### 생성 클래스 (`Generate C# Class`)

`.inputactions` 는 JSON 데이터 파일이다. 문자열로 찾으면
(`FindAction("Jump")`) 오타가 런타임에만 드러난다. 생성 클래스를 켜면
`actions.Player.Jump` 로 타입 안전하게 접근한다.

생성물의 구조:
```
InputSystem_Actions : IInputActionCollection2, IDisposable
├─ Enable() / Disable() / Dispose()
├─ struct PlayerActions   (액션별 프로퍼티 + 맵 단위 Enable/Disable)
├─ struct UIActions
└─ interface IPlayerActions   (콜백 방식용 — 폴링이면 안 씀)
```

- `@` 접두사는 액션 이름이 C# 예약어와 충돌할 경우를 대비한 이스케이프. 쓸 때는 생략.
- `partial class` 라 다른 파일에서 확장 가능 (재생성해도 그 파일은 유지).
- **`IDisposable`** — 내부에 에셋의 **런타임 사본**을 들고 있어 해제하지 않으면 누수.
- 손으로 수정 금지(재생성 시 덮어써짐), 하지만 **커밋은 필수**(없으면 클론 시 컴파일 실패).

### 라이프사이클 3단 분리

| 시점 | 호출 | 이유 |
|---|---|---|
| `OnEnable` | `Player.Enable()` | 입력 받기 시작 |
| `OnDisable` | `Player.Disable()` | 입력 중단 (일시정지·컷신) — 되돌릴 수 있음 |
| `OnDestroy` | `Dispose()` | 에셋 사본 해제 — **되돌릴 수 없음** |

생성은 `Awake` 에 둔다. 생성자가 `InputActionAsset.FromJson` 으로 `ScriptableObject` 를
만들고, Unity는 MonoBehaviour의 생성자·필드 초기화 시점에 이걸 금지한다.

### Input System은 Addressables를 쓰지 않는다

`Assets/AddressableAssetsData/` 가 갑자기 생긴 게 Input System 때문인 줄 알았는데,
패키지 의존성을 보면 **Localization이 끌고 온 것**이었다.

두 패키지가 같은 문제를 다르게 풀었다. 문제: **에디터에서 만든 에셋은 빌드에 안 들어간다.**
(씬 참조 / `Resources/` / Addressables / Preloaded Assets 중 하나여야 포함된다.)

| | Input System | Localization |
|---|---|---|
| 에셋 개수 | 1 | N (로케일 × 테이블) |
| 항상 필요? | 예 | 아니오 (활성 언어만) |
| **해법** | **Preloaded Assets** (빌드 시 임시 주입 후 원상복구) | **Addressables** (주소로 필요한 것만 로드) |

`AddressableAssetsData/` 는 그룹 정의(= 무엇이 어떤 주소로 로드되는지의 명세)라
**커밋 대상**이다. 빠지면 클론한 쪽에서 로컬라이제이션이 런타임에 아무것도 못 찾는다.

## 4. 2D 플랫포머 구현

### 상태머신이 필요해진 근거는 코드에 먼저 나타났다

`#1` 을 일부러 뒤로 미뤘다. 제네릭 상태머신을 먼저 만들면 추상적으로만 느껴지기 때문이다.
`PlayerMovement` 를 다 만든 뒤에 보니 근거가 코드에 보였다.

```
접지 + 입력 있음 → groundAccel      (HandleHorizontal)
접지 + 입력 없음 → groundDecel
공중             → airAccel
상승 + 버튼      → 중력 1            (ApplyGravity)
상승 + 뗌        → 중력 4
하강             → 중력 2.5
상승 중          → 점프 거부          (TryJump)
```

**같은 "상태"를 세 메서드가 각자 다른 조건으로 재구성하고 있다.**
`linearVelocityY > 0` 이 두 곳에, 접지 여부가 세 곳에 나온다.

#10 에서 "공격 중 이동 제한", #11 에서 "콤보 중 점프 불가" 가 얹히면 이 분기가
곱셈으로 늘어난다. 상태로 쪼개면 각 상태가 자기 규칙만 알면 된다.

**교훈: 추상화는 중복이 실제로 보인 다음에 넣는다.** 먼저 넣으면 무엇을 추상화해야
하는지 모르는 상태에서 구조를 정하게 된다.


### 접지 판정 — 왜 영역 질의인가

`OnCollisionStay2D` 로도 가능하지만, 그 방식은 "무엇에 닿았는가"만 알려주고
"어디에 닿았는가"는 알려주지 않는다. 벽과 바닥을 구분하려면 **접촉 법선 각도**를
직접 검사하고 여러 접촉점을 누적 관리해야 한다. 상태가 생기니 버그도 늘어난다.

`Physics2D.OverlapBox` 는 **이벤트가 아니라 질의**다. "지금 이 영역에 뭐 있어?"를
매번 새로 묻는다. 상태를 안 들고 있으니 enter/exit 추적이 없고 답이 바로 `bool` 이다.

Raycast는 광선 하나가 가장자리에서 빗나간다. 여러 개 쏘면 결국 영역 질의와 같아진다.

### 판정 위치는 `bounds` 기준

`transform.position` 은 **오브젝트의 원점**이고, 스프라이트 피벗이나 콜라이더
오프셋에 따라 발바닥이 아닐 수 있다.

`Collider2D.bounds` 는 실제 콜라이더에서 계산된 월드 AABB다.
`b.center.x`, `b.min.y - offsetY` 로 잡으면 캡슐을 박스로 바꿔도 판정이 따라온다.

`offsetY` 는 박스를 발바닥보다 살짝 아래로 밀어 바닥에 파고들게 만든다. 정확히 발바닥
높이에 두면 부동소수점 오차로 판정이 깜빡인다.

### 박스 크기가 각각 막는 버그

| | 값 | 안 지키면 |
|---|---|---|
| `boxSize.y` | 0.1 (얇게) | 공중에서도 지면을 잡아 **무한 점프** |
| `boxSize.x` | 0.8 (콜라이더보다 좁게) | 벽에 붙었을 때 **벽을 지면으로 오인** |

`LayerMask` 의 기본 직렬화 값은 `0` = **Nothing**. 인스펙터에서 안 건드리면
아무것도 안 걸려서 `IsGrounded` 가 영원히 false다. **바닥에 서 있는데 접지가 안 잡히면
99% 이것.**

### 기즈모는 선택이 아니다

접지 판정은 눈에 안 보이는 로직이다. 박스가 콜라이더에 파묻혔는지, 떠 있는지,
너무 넓은지 — 코드만 봐서는 모른다.

`OnDrawGizmosSelected` 로 그리고 접지 상태에 따라 색을 바꾸면, 플레이 중에 실시간으로
확인된다.

두 가지 주의:
- **`FootCenter` 계산을 판정과 기즈모가 공유해야 한다.** 각자 계산하면 그림이
  거짓말을 하고, 그게 최악이다.
- `OnDrawGizmosSelected` 는 **플레이 중이 아닐 때도 호출된다.** `Awake` 에서 캐싱한
  참조가 `null` 이라 지연 초기화가 필요하다.

### 에디터 콜백에서 직렬화 필드를 쓰면 안 된다 ← 위 항목의 해법이 사고를 냈다

지연 초기화를 **필드에 대입**하는 방식으로 짰던 것이 문제였다.

```
ResolveCollider():
    if (bodyCollider == null)
        bodyCollider = GetComponent<Collider2D>();   // ← 대입
    return bodyCollider;
```

`OnDrawGizmosSelected` 가 이걸 부르므로, **에디터에서 Player 를 클릭하기만 해도**
`[SerializeField] bodyCollider` 가 채워진다. 그러면:

```
에디터에서 Player 클릭 → 기즈모 그리기 → bodyCollider 자동 채워짐
                                          ↓
                     다음 플레이에서 Awake 의 폴백 경고가 뜨지 않음
                                          ↓
                            #21 에서 만든 안전장치 무력화
```

→ 대입을 없애고 **읽기 전용**으로 바꿨다. `return bodyCollider ?? GetComponent<...>()`
형태면 필드가 절대 변하지 않는다. ([#28](../../issues/28))

**대가**: 폴백 경로에서 `GetComponent` 가 매 프레임 돈다. 하지만 그건 **경고가 뜨는
비정상 상태**이고, 인스펙터를 지정한 정상 상태에서는 호출조차 되지 않는다. 런타임
캐시 필드를 따로 두는 방법도 있지만 필드 두 개를 관리하는 복잡성이 더 크다.

**일반 원칙: `OnDrawGizmos` / `OnDrawGizmosSelected` / `OnValidate` 는 읽기만 한다.**
플레이 중이 아닐 때도 도는 메서드이고, Undo 시스템을 거치지 않은 직렬화 필드 변경은
저장될지 여부가 불확실하다. 인스펙터에 보이는 값과 디스크의 값이 어긋날 수 있다.

### 속도와 가속도를 구분하지 못했다 ← 가장 크게 막힌 곳

세 가지가 다른 값이다.

| | 의미 | 단위 |
|---|---|---|
| 목표 속도 | 어디로 가고 싶은지 (`MoveInput × maxSpeed`) | 유닛/초 |
| 현재 속도 | 지금 얼마나 빠른지 (`linearVelocityX`) | 유닛/초 |
| 가속도 | 목표로 얼마나 빨리 접근하는지 | 유닛/초² |

`MoveTowards` 의 세 인자가 정확히 이 순서로 대응한다.

```
Mathf.MoveTowards( 현재 속도, 목표 속도, 가속도 × Time.fixedDeltaTime )
                   어디서      어디로     이번 스텝의 최대 변화량
```

`가속도 × dt` 인 이유: 가속도는 "초당" 변화량이므로, 한 물리 스텝(0.02초)에 실제
변할 수 있는 양은 `60 × 0.02 = 1.2`.

**당시 실수 3종** — 전부 이 혼동에서 나왔다.
1. `MoveTowards(가속도, maxSpeed, dt)` — 가속도를 최대속도로 접근시킴
2. `linearVelocity = new Vector2(position.x + 가속도, position.y)` — **위치를 속도에 대입**
3. `targetSpeed` 를 만들어놓고 안 씀

읽고 → 조금 옮기고 → 다시 쓴다. 이게 관성이 생기는 원리다. 손을 떼도 현재 속도가
남아 있어 감속도만큼씩 여러 프레임에 걸쳐 0으로 내려간다.

Unity 6에서는 `linearVelocityX` / `linearVelocityY` 를 개별 대입할 수 있어서
"y를 읽어 그대로 돌려주는" 단계가 필요 없다. (`velocity` 는 deprecated. 인터넷 예제는
대부분 구버전이다.)

### 점프 — 높이에서 속도를 역산

정점에서 y 속도는 0이므로, `v² = v₀² - 2gh` 에서 `v₀ = √(2gh)`.

인스펙터에 속도가 아니라 **높이**를 노출하면 "3.5 유닛"처럼 레벨 디자인 단위로
튜닝할 수 있다.

**역산에는 상승 중력(`gravityScale = 1`) 기준값을 쓴다.** 현재 `gravityScale` 을
끼우면 직전 상태(하강 배수 2.5)에 따라 점프 높이가 흔들린다.

**`=` 로 대입하고 `+=` 하지 않는다.** 코요테 타임으로 낙하 중 점프할 때 남아 있던
음수 속도가 상쇄해 점프가 낮아진다.

### 중력 배수 — 상태를 저장하지 말고 파생시킨다

```
상승 중 + 버튼 누름 → 1
상승 중 + 버튼 뗌   → 4    (lowJumpGravityMult)
하강 중             → 2.5  (fallGravityMult)
```

"버튼 떼면 올리고 착지하면 되돌린다"로 짜면 복원을 빼먹는 경로가 생긴다.
**매 프레임 `linearVelocityY` 에서 다시 계산하면 복원이라는 개념 자체가 사라진다.**
`IsGrounded` 를 매번 새로 묻는 것과 같은 발상.

부수 효과 두 개:
- **가변 점프가 별도 로직 없이 나온다.** 버튼을 떼면 다음 프레임부터 중력이 4배가
  되어 상승이 꺾인다. `JumpReleased`(한 프레임 이벤트) 대신 `JumpHeld`(지속 상태)를
  쓰게 되는 이유.
- 점프인지 발판에 튕긴 건지 구분할 필요가 없다. y 속도가 곧 상태다.

하강 중력을 상승보다 세게 주는 건 물리적으로 틀리지만 체감이 낫다. 대칭 포물선은
공중에 붕 떠 있는 느낌을 준다.

### `Update` vs `FixedUpdate` — 입력이 씹혔다

```
렌더 프레임   │──1──│──2──│──3──│──4──│   (60fps, 16.7ms)
FixedUpdate   │─────────│─────────│─────│   (50Hz, 20ms)
                  ↑ 여기서 눌렀다 뗐다 → 사라짐
```

`WasPressedThisFrame()` 은 **눌린 그 렌더 프레임에만** true다. 점프 처리는
`FixedUpdate` 에서 도는데, `FixedUpdate` 가 건너뛰는 렌더 프레임에 눌린 입력은
아무도 관측하지 못한다.

**해법** `Update` 에서 받아 플래그로 붙잡고 `FixedUpdate` 에서 소비한다.

Input System의 Update Mode를 Fixed Update로 바꾸는 방법도 있으나, 프로젝트 전체
입력이 50Hz로 내려가 UI 반응까지 둔해진다. 게임플레이 한 곳의 문제를 전역 설정으로
푸는 셈이라 대가가 크다.

**`IsPressed()` 는 무관하다.** 현재 눌려 있는지 묻는 **상태 질의**라서 언제 물어도
정확하다. 씹힘은 `WasPressedThisFrame()` 처럼 **한 프레임짜리 이벤트**에만 생긴다.

### 두 주기의 실제 비율을 측정했다

#28 에서 `machine.Tick()` 호출을 검증하려고 `IdleState` 에 카운터를 넣어봤다.

```
Idle 상태를 유지한 구간:  Tick 1331 / FixedTick 204
```

**`FixedTick` 이 시계다.** 주기가 고정(0.02초)이므로 경과 시간을 역산할 수 있다.

```
204 × 0.02초 = 4.08초         ← 실제 경과 시간
1331 ÷ 4.08초 ≈ 326 fps       ← 그동안의 렌더 프레임레이트
```

에디터에서 VSync 없이 단순한 씬을 돌리면 300fps 대가 나온다. 60fps 를 가정하면 6:5
정도일 거라 예상했는데 **6.5:1** 이었다.

이 숫자가 두 가지를 확인해준다.

- **`Tick` 에서 시간을 다루려면 `Time.deltaTime` 이 필수다.** 프레임당 일정량을 더하는
  코드는 326fps 기기에서 60fps 기기의 5배 속도로 돈다. `FixedTick` 은 주기가 고정이라
  그 문제가 없다
- **고프레임일수록 입력 씹힘이 심해진다.** 326fps 면 `FixedUpdate` 한 번 사이에 렌더
  프레임이 6~7개 지나간다. `WasPressedThisFrame` 을 `FixedUpdate` 에서 보면 그중
  대부분이 통째로 안 보인다. 위의 버퍼 설계가 프레임레이트와 무관하게 동작하는 이유다

### 코요테 타임 + 점프 버퍼 — 같은 형태다

`bool` 을 **시각 기록**으로 바꾸면 "얼마나 오래 유효한가"를 값으로 조절할 수 있다.

| | 무엇을 기억 | 판정 |
|---|---|---|
| 버퍼 | 누른 시각 | 경과 시간이 창 안인가 |
| 코요테 | 마지막으로 지면에 있던 시각 | 경과 시간이 창 안인가 |

둘 다 성공 시 `float.NegativeInfinity` 로 소진해 한 입력이 한 점프만 만들게 한다.
`TryJump()` 가 `bool` 을 반환해 **성공했을 때만** 소비하는 것이 버퍼가 작동하는 핵심이다.

**버퍼 창에 하한이 필요했다.** `Time.time` 은 `Update` 에서 렌더 시각,
`FixedUpdate` 에서 물리 시각(`fixedTime`)이다. 밀린 물리 스텝을 먼저 돌리고 `Update` 를
부르므로 누른 직후 스텝의 시각은 항상 누른 시각보다 크다. → `jumpBufferTime = 0` 이면
조건이 성립할 수 없어 점프가 아예 막힌다.

`Mathf.Max(jumpBufferTime, Time.fixedDeltaTime)` 로 최소 폭을 물리 스텝 하나로 잡아서,
0이 "점프 불가"가 아니라 "관용 없음"이 되게 했다.
(제약: 저프레임에서는 경과 시간이 `fixedDeltaTime` 을 넘을 수 있다. 0으로 두고 비교할
때만 60fps 이상이 필요하다.)

### 타이머는 기준점을 고정하는 것이다

버퍼와 코요테를 붙이면서 같은 실수를 형태만 바꿔 세 번 했다. 전부 **기준점이 고정되지
않아** 경과 시간이 자라지 못한 경우다.

**1. 기록과 판정이 한 자리에 있었다**

```
jumpPressedTime = Time.time;
if (Time.time - jumpPressedTime < jumpBufferTime)   // 항상 0
```

지역변수를 필드로 올려도 그대로였다. 필드냐 지역변수냐가 아니라 **기록 시점과 판정
시점이 달라야** 그 사이에 시간이 흐른다. 기록은 `Update`(눌린 순간), 판정은
`FixedUpdate`(점프를 시도하는 순간)로 떨어뜨려야 한다.

**2. 갱신 조건이 반대였다**

코요테에서 `!IsGrounded` 일 때 갱신했다. 공중에서 매 프레임 기준점이 "지금"으로 밀려
경과 시간이 항상 0 근처였고, 공중에서 누르면 언제든 점프하는 **무한 점프**가 됐다.

타이머를 만드는 것은 갱신하는 코드가 아니라 **갱신이 멈추는 조건**이다. 지면에 있을 때
갱신하면 떠나는 순간 멈추고, 그때부터 경과 시간이 자란다.

**3. 소진과 창 열기를 헷갈렸다**

점프 성공 시 `leaveGroundTime = Time.time` 을 넣었다. 소진이 아니라 **창을 새로 여는**
코드이고, 그래서 2단 점프가 됐다. 소진은 기준점을 무한히 먼 과거로 미는 것
(`float.NegativeInfinity`)이다.

같은 이유로 초기값도 `0` 이면 안 된다. 플레이 시작 직후엔 `Time.time` 도 0 근처라
누르지 않아도 창이 열려 있어 자동으로 점프한다.

### 버퍼는 `Time.time` 을 쓴다 — unscaled 가 아니라

위 문제들을 `realtimeSinceStartup` 으로 바꾸면 풀리는지 확인해봤는데 셋 다 그대로였다.
시계 종류가 아니라 기준점 문제였기 때문이다.

그래도 어느 시계를 쓸지는 정해야 한다. `Time.time` 은 `timeScale` 의 영향을 받는다.
[#12](../../issues/12) 히트스탑에서 `timeScale` 을 낮추면 버퍼도 같이 멈추는데, 그게 맞다.
unscaled 를 쓰면 화면이 멈춰 있는 동안 버퍼만 혼자 흘러가 만료된다.

### 착지를 속도로 추론하지 않는다

`FallState` 에서 착지를 처음엔 `!IsFalling`(y 속도가 0 이상)으로 잡았다. 착지하면 물리
엔진이 y 속도를 0으로 만들기 때문에 **결과는 맞았다.** 그래도 `IsGrounded` 로 바꿨다.

- "떨어지는 게 멈췄다"와 "지면에 닿았다"는 다른 말이다. 지금 일치하는 건 우연이다
- 넉백이나 점프대가 들어오면 깨진다. y 속도가 0을 지나가는 순간에 지면이 아닌데도
  `Idle` 로 간다

`IsGrounded` 는 `OverlapBox` 로 직접 묻는 값이라 추론이 아니다. **우연히 맞는 조건은
언제 틀리는지 모른다**는 게 문제다.

### `JumpState` 는 접지를 볼 수 없다

`JumpState` 에 `IsGrounded → Idle` 을 넣으면 **점프가 즉시 취소된다.** 점프 첫 프레임엔
y 속도가 양수인데도 `GroundChecker` 의 박스가 발밑 `0.02` 아래를 보고 있어서 아직 지면을
감지한다.

접지 판정을 발바닥보다 아래로 내린 것(`offsetY`)이 여기서 부작용으로 돌아온 셈이다.
판정을 관대하게 만든 대가는 "떠났는데도 아직 붙어 있다고 보는 한두 프레임"이고,
그 프레임에 의존하는 조건을 쓰면 안 된다.

→ `JumpState` 는 `IsFalling` 하나만 본다. 지면 복귀는 `FallState` 가 판단한다.

### `FixedUpdate` 실행 순서는 보장되지 않는다

`GroundChecker` 와 `PlayerMovement` 둘 다 `FixedUpdate` 에서 도는데 순서가 미지정이다.
`PlayerMovement` 가 먼저 돌면 **한 물리 스텝 낡은 `IsGrounded`** 를 읽는다.

좌우 이동에서는 20ms 지연이 체감되지 않았다. 점프에서 드러났고, 두 곳을 막아야 했다.

1. **코요테 창 재충전** — 낡은 접지 값으로 갱신되면 소진해둔 값이 덮어써져 2단 점프가 된다
   → 갱신 조건에 `linearVelocityY <= 0f` 추가
2. **`TryJump` 의 접지 경로** — 낡은 `IsGrounded(true)` 면 `!IsGrounded` 가 false라
   코요테 조건이 **단락되어** 소진된 창과 무관하게 점프가 성립한다
   → 상승 중(`> 0f`)이면 먼저 거부

실행 순서를 명시(Script Execution Order)하는 방법도 있으나, 다른 스크립트에 영향을
주지 않는 쪽을 택했다.

### 트리거가 겹치면 양쪽 모두 콜백을 받는다

두 트리거가 겹치면 Unity 는 `OnTriggerEnter2D` 를 **양쪽 컴포넌트 모두에게** 보낸다.
`HitBox` 와 `HurtBox` 에 각각 두면 한 번의 접촉이 두 번 처리된다.

감지 주체를 한쪽으로 정해야 한다. 중복 방지 캐시를 들고 있는 쪽이 `HitBox` 이므로 판단도
그쪽에 모았다. 그 결과 `HurtBox` 는 Unity 콜백을 하나도 쓰지 않는다 — 컴포넌트인 이유는
`HitBox` 가 콜라이더를 통해 찾아낼 수 있어야 해서지 콜백을 받기 위해서가 아니다.

### 트리거 콜라이더는 충돌 반응을 만들지 않는다

`EnemyDumy` 에 `Rigidbody2D` 를 붙이자 **바닥을 뚫고 떨어졌다.** 콜라이더가 하나뿐이고
그게 트리거였다.

트리거는 겹침을 **알려주기만** 하고 밀어내지 않는다. 그전까지는 `Rigidbody2D` 가 없어서
정적 콜라이더로 취급돼 이 사실이 드러나지 않았다.

플레이어는 처음부터 갈라져 있었다.

```
Player            CapsuleCollider2D  몸통 (트리거 아님)
├ HitBox          트리거
└ HurtBox         트리거
```

더미는 `BoxCollider2D` 하나가 몸통과 피격 판정을 겸했다. **판정용 트리거와 몸통 콜라이더는
같은 것이 될 수 없다** — 하나는 통과해야 하고 하나는 막아야 한다.

#13 에서는 `gravityScale` 을 0 으로 두고 넘겼다. 넉백 거리가 중력·마찰과 무관해서
(속도를 직접 대입하므로) 체감 판단이 왜곡되지 않기 때문이다. 구조 분리는 #16 이다.

### 넉백 거리는 계산으로 나온다

`linearVelocityX` 를 직접 대입하고 선형 감쇠하면 거리가 적분으로 정해진다.

```
선형 감쇠   거리 = force × time / 2
제곱 감쇠   거리 = force × time / 3
```

그래서 **"멀리 간다"를 감으로 고치지 않아도 된다.** 3타가 12 × 0.2 / 2 = 1.2 유닛이었고,
히트박스 사거리가 0.75 라 적이 완전히 벗어났다. 8 로 내려 0.8 을 만들었다.

곡선을 바꾸는 것과 세기를 바꾸는 것은 **다른 축**이다. 곡선은 끝에서 미끄러지는 느낌을
바꾸고(거리도 3분의 2로 줄지만 비율은 유지), 세기는 특정 공격의 크기를 바꾼다. 3타만
과할 때는 세기가 맞다.

`force` 와 `time` 이 곱으로 엮여 거리는 같이 움직이지만 의미가 다르다.

| | 뜻 | 어디에 |
|---|---|---|
| `knockbackForce` | 이 **공격**이 얼마나 세게 밀어내나 | `AttackData` |
| `knockbackTime` | 이 **대상**이 얼마나 오래 밀려나나 | `Knockback` |

`time` 을 줄이면 모든 공격이 같이 줄고, 나중에 무게가 다른 적(방패병)에게 쓸 값을 미리
소모하게 된다.

### 속도는 덮어써도 위치는 누적된다

겹친 넉백을 덮어쓰기로 처리했으니 속도는 안 쌓인다. 그런데 3타 콤보를 이어치면 적이
0.5 → 1.0 → 1.8 로 **위치가 누적된다.** 플레이어는 지상 공격 중 `AllowsHorizontalControl`
이 `false` 라 제자리에 있다.

지금은 3타가 아슬아슬하게 맞는데, 그건 더미 콜라이더가 1×1 로 실제보다 커서 앞면이
사거리에 걸치기 때문이다. **#16 에서 크기를 줄이면 깨진다.**

여기서 값을 조정하지 않았다. 1×1 은 실제 전제가 아니므로 지금 여유를 만들면 틀린 기준에
맞추는 것이 된다 — #35 에서 임시 도형으로 히트박스를 잡았다가 다시 잡은 것과 같은 실수다.
GDD 미결정 2번(지상 공격 전진)의 근거가 여기서 나올 가능성이 크다.

### 레이어는 GameObject 단위다

히트박스와 허트박스를 자식 GameObject 로 나눈 실제 이유가 이것이다. 레이어는 콜라이더가
아니라 GameObject 에 붙으므로, 한 오브젝트에 콜라이더 둘을 달면 매트릭스로 구분할 수 없다.

태그 비교로도 거를 수 있지만 그 방식은 물리 엔진이 접촉을 만들고 콜백까지 보낸 뒤
코드에서 버리는 셈이다. 레이어로 막으면 접촉 자체가 생기지 않는다.

`Ground` 와 `Default` 까지 전부 해제하는 것이 중요하다. 루트 `Player` 가 `Default` 라
켜두면 자기 허트박스와 자기 콜라이더가 서로 감지한다. `Ground` 를 켜두면 히트박스가
지면에 닿을 때마다 콜백이 온다 — `HurtBox` 가 없어 첫 줄에서 걸러지지만 부를 이유가 없다.

### GameObject 를 끄면 `Awake` 가 돌지 않는다

히트박스를 처음부터 꺼두려고 GameObject 를 비활성화했더니 `Awake` 가 실행되지 않아
콜라이더 폴백도 초기 비활성화도 걸리지 않았다. 그 상태에서는 `enabled = true` 를 해도
물리에 참여하지 않는다.

**활성 구간 제어는 GameObject 가 아니라 콜라이더의 `enabled` 로 한다.** GameObject 를
껐다 켜면 그때마다 `Awake`/`OnEnable` 이 다시 도는 것도 예측을 어렵게 만든다.

### 비동기 타임라인 — 줄 순서가 곧 시간 순서

공격의 `선딜 → 판정 On → Off → 후딜` 을 `await` 로 이었다. 단계 필드와 타이머를 두고
매 프레임 진행도를 세는 방식과 비교하면, 코드를 위에서 아래로 읽는 것이 그대로 시간
흐름이 된다. 이슈에 적은 시퀀스와 코드가 한 줄씩 대응한다.

**취소를 상태의 수명에 묶는다.** `Enter` 에서 `CancellationTokenSource` 를 만들고 `Exit`
에서 취소한다. 상태를 벗어나는 경로가 무엇이든 타임라인이 죽으므로, 나중에 피격·사망
같은 중단 경로가 늘어나도 각각에 정리 코드를 넣지 않는다.

**`Cancel` 이 `Dispose` 보다 먼저다.** `Dispose` 는 자원 정리일 뿐 진행 중인 `await` 를
깨우지 않는다. 순서를 바꾸면 취소가 전달되지 않고, 정리된 객체에 `Cancel` 을 불러
`ObjectDisposedException` 이 난다.

**토큰을 `Delay` 마다 넘긴다.** 하나라도 빠지면 그 구간에서 취소가 먹지 않는다. CTS 를
만들어두는 것과 그것이 실제로 전달되는 것은 다른 문제다.

**`catch` 를 좁게 잡는다.** `Exception` 을 통째로 삼키면 `null` 참조나 배선 누락이 조용히
사라져 "공격만 안 나가는" 증상만 남는다. `OperationCanceledException` 만 잡고 나머지는
콘솔에 올라오게 둔다.

**`finally` 로 정리한다.** 어느 `await` 에서 끊기든 히트박스가 켜진 채 남지 않는다.
`catch` 가 예외를 삼켜도 `finally` 는 실행된다.

**복귀 전환은 `try` 안에 둔다.** 밖에 두면 취소된 경우에도 실행되어, 이미 다른 상태로
갔는데 뒤늦게 `Idle` 이나 `Fall` 로 끌고 간다. 안에 두면 취소 시 `await` 에서 예외가 나
거기까지 도달하지 않으므로 "정상 종료일 때만 복귀"가 저절로 성립한다.

### 목표를 바꿔야 방향이 바뀐다

공격 중 이동을 막을 때 감속도(`groundDecel`)를 손대는 것으로는 안 된다. `MoveTowards` 에서
감속도는 **"얼마나 빨리 가느냐"**일 뿐이고 **"어디로 가느냐"**는 목표 속도가 정한다.
목표가 `입력 × maxSpeed` 인 이상 느려질 뿐 결국 최고 속도에 도달한다.

`targetSpeed` 를 0 으로 두면 기존 감속 경로를 그대로 타면서 멈춘다. 그리고 목표 쪽에서
처리하면 접지·공중 분기 양쪽에 자동으로 걸린다 — 감속도 분기에 넣으면 공중 경로가 빠진다.

### 부작용이 있는 함수는 조건식 뒤에 둔다

```
if (TryJump() && CurrentState.AcceptsJumpInput)   // ✗
if (CurrentState.AcceptsJumpInput && TryJump())   // ✓
```

`&&` 는 왼쪽부터 평가한다. `TryJump()` 는 판정만 하는 함수가 아니라 성공 시 `linearVelocityY`
를 바꾸고 코요테 창을 소진한다. 왼쪽에 두면 `AcceptsJumpInput` 이 `false` 여도 이미 점프
속도가 적용되어, 상태만 안 바뀌고 실제로는 튀어오른다.

값싸고 부작용 없는 검사를 앞에, 상태를 바꾸는 호출을 뒤에 둔다.

### 방향은 값 하나를 근거로 삼는다

`facing`(+1 / -1)을 두고 스케일과 넉백 벡터를 거기서 파생시킨다.

`flipX` 를 근거로 삼으면 게임플레이 판정이 렌더링 컴포넌트에 매달린다. 애니메이터를
붙이거나 아트가 왼쪽을 기본으로 그려져 있으면 매핑이 뒤집히고, `flipX` 를 읽는 코드가
전부 틀린다.

더 직접적인 이유도 있다. 히트박스 오프셋이 오른쪽으로 고정돼 있어서 **스프라이트만
뒤집으면 왼쪽을 보면서 오른쪽을 때린다.** 루트 `localScale.x` 를 쓰면 자식인 히트박스가
함께 미러링되어 코드가 필요 없다.

**갱신 조건은 "입력이 있을 때"이지 "값이 바뀌었을 때"가 아니다.** 후자면 손을 뗄 때
`1 → 0` 도 변화라 0 이 저장되어 방향이 사라진다.

갱신 조건에 `AllowsHorizontalControl` 을 포함시키면 공격 중 방향도 고정된다. 그러지
않으면 선딜에 오른쪽을 보고 시작했는데 판정 순간 히트박스가 왼쪽으로 순간이동한다.

### `localScale.x` 에 대입할 수 없다

```
transform.localScale.x = facing;   // CS1612
```

`localScale` 은 필드가 아니라 **프로퍼티**다. 읽으면 `Vector3` 복사본이 나오고, `Vector3`
는 구조체라 그 복사본을 고쳐봐야 원본에 반영되지 않는다. C# 이 아예 막는다.

`new Vector3(facing, 1f, 1f)` 를 통째로 대입해야 setter 가 실제 트랜스폼을 갱신한다.

곱셈(`localScale * facing`)으로 처리하면 안 되는 이유는 따로 있다. **누적이라 매 프레임
부호가 뒤집히고**, y·z 까지 반전된다. `facing` 은 "얼마나 바꿀까"가 아니라 "지금 어느
쪽인가"라는 현재 상태이므로 대입이 맞다.

### 상태 재진입이 막혀 있으면 반복은 안에서 돈다

3타 콤보를 "1타 끝 → `Change(Attack)` → 2타"로 짜려 했으나 성립하지 않는다.
`StateMachine.Change` 가 `Current == next` 이면 무시하기 때문이다 — #7 에서 근거를 갖고
넣은 규칙이다.

선택지가 셋이었다. 타마다 상태를 따로 두거나(`Attack1`/`Attack2`/`Attack3`), `Change` 의
무시 규칙을 완화하거나, 타임라인 안에서 루프를 돌거나.

세 번째를 택했다. 첫째는 상태가 늘어나고, 둘째는 **콤보 하나 때문에 다른 상태 전체에
영향을 주는** 변경이다. 이미 갖춰진 타임라인과 취소 위에 `while` 하나를 얹는 쪽이 건드리는
범위가 가장 좁다.

### 콤보가 이어지는 경로가 둘이다

| | 동작 |
|---|---|
| 선입력 | 후딜 중에 눌렀다 → 루프가 그대로 이어져 다음 타로 |
| 타임아웃 내 재입력 | 상태를 나갔다가 리셋 시간 안에 다시 눌렀다 → `Enter` 가 리셋을 건너뜀 |

두 번째가 성립하려면 **상태를 나가기 전에 인덱스가 이미 올라가 있어야 한다.** 그래서
`comboIndex++` 가 `break` 보다 앞에 온다. 뒤에 두면 재진입할 때 같은 타를 반복한다.

`comboIndex` 를 상태의 필드로 둘 수 있는 이유는 **상태 객체가 `Awake` 에서 한 번 만들어져
계속 살아 있기** 때문이다. 상태를 벗어나도 값이 남고, 그게 콤보에 필요한 성질이다.

### 선입력을 언제부터 받느냐가 리듬을 만든다

수용 구간을 판정 시작 이후로 제한했다. 선딜 중 입력까지 받으면 **버튼을 누른 횟수만큼
콤보가 자동으로 흘러간다.** 그러면 연타가 최적해가 되고 "리듬감 있게 이어진다"가 성립하지
않는다.

`acceptingInput` 을 매 타 시작에서 내리고 `HitBoxActivate` 직후에 올린다. `comboQueued` 도
같은 자리에서 내려야 한다 — 안 내리면 이전 타의 입력이 남아 다음 타가 저절로 이어진다.
#9 캐시의 `Clear()` 와 같은 자리다. "새로 세기 시작하는 지점"이 어디인지가 매번 문제가 된다.

후딜을 `Delay` 로 기다리기만 하면 그 사이 입력을 볼 수 없다. `AttackPressed` 는 한 프레임
짜리라 `await` 가 깨어난 시점엔 사라져 있다. 그래서 관측은 `Tick()` 이 하고 타임라인은
결과만 읽는다 — 기록과 판정의 분리가 여기서도 같은 형태로 나온다.

### 하나의 플래그가 두 가지를 통제하고 있었다

`AllowsHorizontalControl` 이 이동과 방향 전환을 함께 막고 있었다. 지상 공격에서는 둘 다
막는 게 맞아 문제가 드러나지 않았다.

공중 공격에서 갈라졌다 — **이동은 열고 방향은 막고 싶다.** 공중에서 제어를 열면 `facing`
갱신도 함께 열려, 판정 도중 방향이 바뀌면 히트박스가 반대편으로 순간이동한다. 오른쪽을
벴는데 왼쪽 적이 맞는다.

`AllowsFacingChange` 를 추가하되 **기본값을 `AllowsHorizontalControl` 에 연동**했다. 그러면
기존 상태 넷은 손댈 필요가 없고, 구분이 필요한 `AttackState` 만 재정의한다. 플래그를 늘릴 때
기본값을 기존 것에 연동하면 이미 있는 코드를 건드리지 않아도 된다.

그리고 상태 전체를 잠그지 않고 **판정 구간에만** 잠갔다(`=> !hitboxActive`). 선딜·후딜에는
히트박스가 꺼져 있어 방향이 바뀌어도 판정에 영향이 없다. 0.08초만 잠기므로 공중에서 방향을
틀며 싸우는 조작은 살아 있다. 프로퍼티가 상황에 따라 다른 답을 하는 형태다.

### 감속도가 같아도 상황에 따라 결과가 다르다

공중 공격에서 `AllowsHorizontalControl` 을 `false` 로 두었더니 조작이 끊기는 느낌이 났다.
`targetSpeed` 가 0 이 되는 것은 지상과 같은데, **감속도가 다르다.**

```
지상   groundDecel 60   →   8 → 0 까지 0.13초
공중   airAccel 30      →   8 → 0 까지 0.27초
```

공격 1타가 0.40초라 공중에서도 도중에 완전히 정지한다. "천천히 감속하니 관성이 남겠지"라고
생각했지만 공격 시간이 더 길어서 결국 멈춘다. **감속이 느린 것과 멈추지 않는 것은 다르다.**

입력을 살리는 쪽(`true`)으로 바꿨다. 입력을 놓으면 평소 점프처럼 감속하므로 나머지 동작과도
일관된다.

### 멈춘 시계로는 자기 해제 시각을 잴 수 없다

히트스탑은 `Time.timeScale` 을 0 으로 내리고 잠깐 기다렸다 되돌린다. 그런데 `UniTask.Delay`
의 기본값은 **timeScale 이 곱해진 시간**이다. 0 인 동안에는 시간이 흐르지 않으니 영원히
깨어나지 못한다.

시간을 멈추는 쪽만 unscaled 로 재야 한다. 반대로 `AttackState` 의 `Delay` 셋은 **scaled
그대로 두는 것이 맞다.** 히트스탑 동안 공격 타임라인이 계속 흐르면 판정 구간이 실제로
깎여나간다.

같은 API 인데 한쪽은 unscaled 여야 하고 다른 쪽은 scaled 여야 한다. 기준은 **"이 대기가
게임 안의 시간인가, 게임을 멈춘 장치의 시간인가"**다.

`Time.time` 도 timeScale 을 따르므로 점프 버퍼·코요테·콤보 리셋 창이 히트스탑 동안 함께
멈춘다. 이쪽은 손대지 않는 편이 일관된다 — 게임 안 시간이 멈췄으니 게임 안 타이머도 멈추는
게 맞다.

### 호출 횟수와 실행 횟수를 떼어놓으려면 몸통이 따로 있어야 한다

처음에는 `Play` 자체를 `async` 로 두고 그 안에서 `timeScale` 을 0 으로 내렸다 되돌렸다.
한 스윙이 적 둘을 때리면 `Play` 가 두 번 불리고 루틴도 둘 생긴다. **각자 자기 대기가 끝나면
`timeScale` 을 1 로 되돌리므로, 길이가 다르면 짧은 쪽이 긴 쪽을 잘라먹는다.** 공유 자원을
여럿이 각자 복구하는 구조 자체가 문제다.

그런데 `Play` 가 `async` 인 한 "이미 돌고 있으면 값만 갱신하고 돌아간다"를 쓸 자리가 없다 —
**async 메서드는 불리는 순간 무조건 몸통이 시작된다.** `if (running) return` 을 넣으려면
몸통이 별도 메서드여야 한다.

| | 역할 | 횟수 | |
|---|---|---|---|
| `Play` | 요청을 받는다 | N | 동기 `void` |
| `RunAsync` | 정지를 집행한다 | 1 | 비동기 |

`AttackState.Enter` 가 `RunTimeline().Forget()` 을 부르는 것과 같은 구조다. 그때는 상태
머신이 `Enter` 의 즉시 종료를 기대해서였는데, **이유가 달라도 형태는 같다** — 동기 진입점 +
비동기 몸통.

`RunAsync` 는 `private` 이어야 한다. `internal` 이면 바깥에서 직접 불러 `running` 가드를
우회할 수 있어, 창구를 하나로 만든 의미가 없어진다.

겹칠 때는 `Max` 로 긴 쪽을 남긴다. 먼저 온 것을 우선하거나 나중 것으로 덮어도 되지만 둘 다
강타가 손해를 본다.

경합을 걱정했으나 일어나지 않는다. `OnTriggerEnter2D` 는 물리 단계에서 돌고 `RunAsync` 의
재개는 Update 단계라 **한 프레임 안에서 물리가 항상 먼저**다. `Play` 가 `remaining` 을
올려두면 `while` 이 그것을 보고 계속 돈다.

부수 효과로 `Play` 가 `void` 가 되면서 호출부의 `.Forget()` 이 사라졌다. **비동기라는 것은
내부 구현 사정이지 부르는 쪽이 알 일이 아니다.**

### 한 번 건 대기는 길이를 못 바꾼다

`Delay` 를 프레임 루프로 바꿔야 했던 이유다. 대기 도중에 목표가 늘어날 수 있으려면 매 프레임
깨어나 남은 시간을 직접 깎는 수밖에 없다. `await` 한 줄이 `while` 로 늘어나는 대신
"대기 중에도 조건이 바뀔 수 있다"를 표현할 수 있게 된다.

대가로 정밀도가 프레임 단위가 된다. 실측이 목표보다 2~3ms 짧았는데, `OnTriggerEnter2D` 는
물리 단계에서 도는데 첫 `Yield` 는 같은 프레임의 Update 에서 깨어나므로 **프레임 중간부터
시작해놓고 프레임 전체의 `unscaledDeltaTime` 을 뺀다.** 히트스탑에서 3ms 는 체감되지 않아
그대로 뒀다.

`finally` 에서 남은 시간을 0 으로 되돌리는 것도 같은 이유에서 필요하다. 루프가 정상 종료하면
남은 시간은 음수인데, 지우지 않으면 다음 히트스탑이 빚을 지고 시작한다.

### 도메인 리로드는 `Awake` 를 건너뛴다

플레이 중에 `.cs` 를 고쳤더니 `PlayerInputReader` 의 `OnEnable`·`OnDisable`·`OnDestroy`
에서 `NullReferenceException` 이 났다. Unity 가 도메인을 다시 로드할 때는 **`Awake` 를
다시 부르지 않고 `OnEnable` 부터 부른다.** `actions` 는 직렬화되지 않는 필드라 그 사이에
`null` 이 된다.

빌드에는 없는 증상이라 고칠 대상이라기보다 "플레이 중에 코드를 고치지 않는다"는 워크플로
문제다. 다만 콘솔에 계속 쌓이면 진짜 에러가 묻힌다.

`HitStop` 의 `static` 필드도 같은 사정에 놓여 있다. 지금은 도메인 리로드가 켜져 있어
(`m_EnterPlayModeOptions: 0`) 매 Play 마다 초기화되지만, **반복 속도를 위해 `Reload Domain`
을 끄면 `running` 이 `true` 로 굳어 히트스탑이 영영 안 걸린다.** static 을 고른 대가다.

확인하지 못한 것이 하나 남아 있다. **히트스탑 도중에 Play Mode 를 멈추면 `finally` 가 돌지
않아 `timeScale` 이 0 인 채 남을 수 있다.** 증상이 나면 다음 Play 가 통째로 얼어붙으므로 바로
알아차릴 수 있어, 지금 막지 않고 뒀다.

### 애니메이션은 클립 이름이 아니라 상태 이름으로 지목한다

`Animator.Play("Idle")` 의 `"Idle"` 은 클립 파일명(`Idle_Modified`)이 아니라 **Animator
Controller 안의 상태 이름**이다. 처음에 클립 이름을 넘길 생각을 했는데, 이 구분이
W2 무기 교체의 비용을 좌우한다.

`AnimatorOverrideController` 는 **상태·전이·파라미터를 그대로 두고 클립만 갈아끼운다.**
그래서 `Character_Sword` 와 `Character_Bow` 는 클립이 서로 다른데 상태 이름은 같다.
상태 이름으로 지목하면 무기가 늘어도 코드가 그대로다. 클립 이름으로 지목했다면
무기마다 문자열이 달라져서 **무기 추가가 데이터 작업이 아니라 코드 수정**이 됐다.

GDD 9장 확장 지점이 "붙일 자리를 남긴다"는 이야기인데, 여기서는 자리가 아니라
**지목하는 방식**이 확장성을 결정했다.

**정정 (#46) — 절반만 맞았다.** 위 문단의 "상태 이름으로 지목하면 무기가 늘어도 코드가
그대로다"는 `Idle` · `Run` · `Jump` 에만 해당한다. 실제로 창을 껴보니 **베기 모션이
나왔다.**

베이스 컨트롤러에 공격 상태가 **네 개 따로** 있었다 — `AttackSlash` · `AttackPrick` ·
`AttackShoot` · `AttackMagic`. `PlayerState.clipAttack` 이 `"AttackSlash"` **상수**라,
오버라이드가 그 상태의 클립을 창 캐릭터 것으로 바꿔줄 뿐 **상태 자체는 그대로**였다.

**"상태 이름을 쓴다"와 "그 이름을 어디서 가져오는가"는 별개의 문제다.** 앞은 시그니처
이야기고 뒤는 데이터 출처 이야기인데, 하나로 봤다. 상태 이름을 쓰는 건 필요조건이었지
충분조건이 아니었다.

고치는 방향은 `attackStateName` 을 `WeaponData` 필드로 올리는 것이고, `AttackData` 를
무기 SO 로 옮긴 것과 같은 형태다. **무기마다 갈리는 건 공격뿐**이므로 나머지 상수는
그대로 둔다.

이걸 [#35](../../issues/35) 시점에 알 수 있었을까. 컨트롤러를 열어 상태 목록을 봤다면
공격이 넷인 게 보였다. **"상태 이름은 6종이 같다"를 확인한다면서 상태 목록을 세지 않았다** —
`clipWindup` 을 프레임 수에서 추론한 것과 같은 종류다 (5절).

### `Animator.Play` 는 없는 이름을 조용히 무시한다

`Play("Jupm")` 은 예외도 경고도 없이 아무 일도 하지 않는다. 오타 하나가 컴파일을 통과하고
런타임에도 침묵한다 — 증상은 "애니메이션이 안 바뀐다" 하나뿐이라 원인 후보가 전환·클립·
배선 세 곳으로 갈린다.

그래서 상태 이름 문자열을 `PlayerState` 의 `const` 로 모았다. **틀릴 수 있는 자리를 5곳에서
1곳으로 줄이는 것**이 목적이다 (5절 참고).

`SetTrigger` 를 쓰지 않은 것도 같은 계열의 판단이다. 에셋의 컨트롤러는 Any State 전이 +
트리거 방식이고 `m_TransitionDuration: 0` 이라 `Play` 와 결과가 같다. 그런데 **트리거는
소비되지 않으면 큐에 남아** 나중에 엉뚱한 시점에 발동한다. 코드 상태머신이 이미 전이를
결정하므로 Animator 쪽 전이는 중복이고, 중복인 쪽을 안 쓰는 게 원인 추적이 쉽다.

전이를 지울 필요는 없었다. 트리거를 아무도 세팅하지 않으면 Any State 전이는 발동하지
않는다. **에셋 원본을 건드리지 않고 끝났다** — 별도 저장소라 손대는 비용이 더 크다.

### 자식에 붙은 컴포넌트는 `GetComponent` 로 안 잡힌다

`animator` 폴백을 `GetComponent<Animator>()` 로 썼는데 **항상 `null` 이었다.** Animator 는
Player 가 아니라 자식 `Character_Sword` 에 있다.

```
Player              ← PlayerMovement, Rigidbody2D, GroundChecker
└ Character_Sword   ← Animator
  └ Model
    └ Body          ← SpriteRenderer
```

`GetComponent` 는 자기 GameObject 하나만 본다. `GetComponentInChildren` 이어야 내려간다.

**경고를 띄우는 코드가 있는데도 원인을 못 알려주는 상태였다.** 안전장치를 넣었다는
사실이 안전장치가 동작한다는 뜻이 아니다 — 5절 "안전장치를 무력화하는 코드가 따로 있을
수 있다"와 같은 자리인데, 이번엔 무력화한 게 다른 코드가 아니라 그 안전장치 자신이었다.

### `Awake` 안에서도 줄 순서가 계약이다

```
if (animator == null) animator = GetComponentInChildren<Animator>();
machine.Change(Idle);     // ← Enter() → PlayClip → animator.Play
```

`Change(Idle)` 이 곧바로 `IdleState.Enter()` 를 부르고, 그게 `animator.Play` 까지 내려간다.
두 줄의 순서가 뒤바뀌면 **시작 프레임에 `NullReferenceException`** 이 난다.

`Awake` 를 "초기화를 모아두는 곳"으로만 보면 순서가 무의미해 보인다. 하지만 `Change` 는
초기화가 아니라 **실행의 시작**이다. 4절 "부작용이 있는 함수는 조건식 뒤에 둔다"와 같은
원칙이고, `Change` 가 마지막이어야 하는 이유가 여기서도 나온다.

### 스케일이 바뀌면 다시 잡을 값과 그대로 둘 값이 갈린다

임시 도형(1×1)에서 실제 캐릭터(몸통 0.7유닛)로 바꾸면서 튜닝값을 다시 잡았다. 전부 다시
잡는 게 아니라 **차원이 있는 값만** 다시 잡는다.

| | 값 |
|---|---|
| 스케일 의존 — 다시 잡는다 | `maxSpeed` `groundAccel` `groundDecel` `airAccel` `jumpHeight` `maxFallSpeed` · 콜라이더 · 히트박스 · 카메라 `size` |
| 시간 기반 — 그대로 둔다 | `jumpBufferTime` `coyoteTime` `fallGravityMult` `lowJumpGravityMult` · 히트스탑 · 콤보 타임아웃 |

중력 배수는 **비율**이라 스케일과 무관하다. 코요테 타임도 "사람이 인지하는 여유"라 월드
크기와 관계없다.

빠뜨리기 쉬운 건 **비율로 묶여 있던 값**이다. `maxSpeed` 만 8→5 로 줄이고 `groundAccel` 을
그대로 두면 최고속 도달 시간이 짧아져서 조작감이 달라진다. 원래 비율(0.14초)을 맞추려고
`groundAccel` 을 35 로 잡았다.

`maxFallSpeed` 도 독립 값이 아니다. `GroundChecker` 의 박스 두께가 0.1 인데 한 스텝에
그보다 많이 내려가면 접지를 건너뛴다. 8 이면 스텝당 0.16 — 두께보다 크지만 박스가
`offsetY 0.02` 로 몸통에 겹쳐 있어 안전하다. **접지 판정 두께가 낙하 속도의 상한을 정한다.**

### 최소 점프 높이는 별도 값이 아니라 파생값이다

"점프 버튼을 짧게 눌렀을 때의 높이"를 조절할 필드를 찾다가, 그런 값이 없다는 걸 알았다.

```
최소 점프 높이 ≈ jumpHeight / lowJumpGravityMult
```

상승 중 버튼을 떼면 `gravityScale` 이 `lowJumpGravityMult` 로 바뀌므로, 최고점이 그 배수만큼
낮아진다. 4절 "중력 배수 — 상태를 저장하지 말고 파생시킨다"의 결과다. 값을 하나 더 만들지
않은 대가로 **두 값이 연동된다** — `jumpHeight` 를 올리면 최소 점프도 같이 올라간다.

`lowJumpGravityMult` 를 3 으로 잡아 몸통 높이의 67% 로 맞췄다.

### 파츠로 조립한 캐릭터는 `flipX` 로 뒤집을 수 없다

Pixem 캐릭터는 베이스 스프라이트가 **왼쪽을 보고** 있어서 뒤집어야 했다. `SpriteRenderer.flipX`
는 렌더러 하나만 뒤집으므로, 파츠가 여럿이면 각 파츠의 **위치는 그대로 두고 그림만** 뒤집혀
무기가 반대편에 남는다.

`transform.localScale.x = -1` 은 계층 전체를 거울반사하므로 위치까지 따라온다. 이미
`PlayerMovement` 가 `facing` 으로 Player 의 `localScale.x` 를 쓰고 있었으므로, **자식
`Character_Sword` 의 `localScale.x` 를 -1 로 고정**해서 해결했다. 두 스케일이 곱해져
오른쪽을 볼 때 스프라이트가 오른쪽을 본다.

`facing` 자체를 뒤집지 않은 게 중요하다. `facing` 은 넉백 방향·투사체·대시가 공유하는
**논리값**이고 "오른쪽 = +1" 이어야 한다. 스프라이트가 왼쪽을 본다는 건 에셋의 사정이므로
**에셋 쪽에서 흡수**해야 한다. 논리값을 아트에 맞추면 나중에 다른 방향 소비자가 생길 때마다
부호를 뒤집게 된다.

(구운 결과물은 파츠가 합쳐져 `SpriteRenderer` 가 하나뿐이라 `flipX` 로도 됐을 것이다.
다만 그러면 무기 프리팹을 조립형으로 바꾸는 순간 깨진다.)

### 클립이 루프면 모션이 코드와 다른 시계로 돈다

에셋의 클립 9개 중 `Death` 만 빼고 전부 `m_LoopTime: 1` 이었다. 일회성이어야 하는
공격·`Hit`·`Jump` 까지 루프였다.

`AttackSlash` 는 0.317초 루프다. 3타 콤보가 1.31초이므로 **1.31 / 0.317 ≈ 4.1** —
세 번 치는데 네 번 휘두르고, 주기가 안 맞아 매 타마다 위상이 달라진다. 히트박스가 나가는
순간 칼이 어디 있는지가 타마다 다르다.

처음 진단은 "클립이 끝난 자리에 멈춰 있다"였는데 틀렸다. **`m_StopTime` 과 `m_LoopTime` 을
안 보고 호출 구조만 보고 판단**했기 때문이다. 판정과 그림이 어긋날 때는 코드보다 클립
설정을 먼저 봐야 한다 — 클립이 자기 시계를 갖고 있으면 코드를 아무리 고쳐도 안 맞는다.

`Death` 만 루프가 꺼져 있던 게 단서였다. **제작자도 일회성은 끄는 게 맞다고 봤고 나머지를
빠뜨린 것**이다. 일관성이 없을 때는 다수가 아니라 이유가 있는 쪽이 맞다.

### `Animator.Play` 는 인자를 붙이지 않으면 되감지 않는다

```
animator.Play(name)                  이미 그 상태면 아무 일도 안 한다
animator.Play(name, -1, 0f)          항상 그 시각으로 되돌린다
```

콤보처럼 **같은 상태를 반복 재생**해야 할 때 첫 형태로는 안 된다. `-1` 은 레이어 미지정,
세 번째가 `normalizedTime` 이다.

같은 인자가 낙하에도 쓰였다. `FallState` 가 `normalizedTime: 1f` 로 클립 끝 프레임을
붙잡는다. 그냥 재생하면 정점에서 점프 모션이 한 번 더 나온다 — 루프를 끄고 나서야 보였던
증상이다. 루프였을 때는 어차피 돌고 있어서 가려져 있었다.

`FallState` 에서 `PlayClip` 을 아예 빼는 방법은 안 된다. **낙하로 들어오는 경로가 둘**이라
걷다가 발판을 벗어나는 경우에는 `Run` 이 재생 중이다.

### 맞춰야 할 대상을 잘못 잡았다 — 클립 길이가 아니라 `startup`

콤보 단계마다 재생 속도를 조절할 때 처음에는 **클립 길이를 단계 길이에 맞추려** 했다.
멈춤을 없애는 게 목표였기 때문이다.

```
AttackSlash 0.317s

_0  0      → 0.1167   치켜듦        ← startup 0.12 와 이미 맞는다
_1  0.1167 → 0.2167   휘두름        ← 히트박스가 여기 있어야 한다
_2  0.2167 → 0.3167   마무리
```

클립을 0.40초로 늘리면 `_0` 이 0.148초가 되어 **히트박스가 나갈 때 아직 칼을 들고 있다.**
멈춤을 없애려고 타격감을 버리는 셈이었다.

`recovery` 구간에 `_2`(마무리 자세)가 떠 있는 건 **멈춤이 아니라 자세를 붙잡고 있는 것**
이라 애니메이션으로는 정상이다. 오히려 후딜의 무게로 읽힌다.

**버려야 할 건 "판정과 그림이 어긋나는 것"이지 "정지"가 아니었다.** 증상 두 개가 같이
보일 때 어느 쪽이 실제 문제인지 정하지 않으면, 해결한 것처럼 보이면서 더 나쁜 걸 얻는다.

### 판정을 없애려면 콜라이더를 꺼야 한다

시체를 계속 때릴 수 있는 걸 막으려고 `HurtBox.TakeHit` 첫 줄에서 "죽었으면 return" 을
넣으려 했다. 참조도 안 늘고 제일 싸 보였는데, `HitBox` 를 보면 안 된다.

```
hurtbox.TakeHit(damageInfo);      ← 여기서 조용히 돌아와도
HitStop.Play(...);                ← 이 둘은 그대로 실행된다
Shake...
```

**히트스탑과 화면 흔들림은 `TakeHit` 밖에서 불린다.** 고치려던 증상(시체를 때리면 화면이
멈추고 흔들림)이 그대로 남는다.

`HurtBox` 컴포넌트만 `enabled = false` 하는 것도 안 된다. **`TryGetComponent` 는 비활성
컴포넌트도 찾아내고**, 찾은 뒤 메서드를 부르는 것도 막지 않는다. `enabled` 가 끄는 건
Unity 가 부르는 콜백(`Update`·`OnTriggerEnter2D` 등)이지 내가 부르는 호출이 아니다.

`OnTriggerEnter2D` 자체가 안 불려야 하고, 그러려면 **콜라이더**를 꺼야 한다.

`GameObject.SetActive` 는 쓰지 않는다 — 끄면 `Awake` 가 안 돌고 껐다 켜면 다시 돈다
(위 "GameObject 를 끄면 `Awake` 가 돌지 않는다"). #15 무적이 0.6초 껐다 켜는 동작이라
바로 걸린다.

### 속도를 직접 대입하는 쪽은 물리적으로 밀리지 않는다

적 몸통을 트리거에서 실제 콜라이더로 바꾸자 플레이어가 적을 **계속 밀어냈다.** 질량을
올려도 소용이 없다.

```
HandleHorizontal()   body.linearVelocityX = ...   ← 매 FixedUpdate 마다 대입
```

충돌로 속도가 깎여도 다음 프레임에 원래 값으로 되돌아간다. 물리적으로 플레이어는
**감속하지 않는 벽**이다. 힘 대결이 아니라 위치 대결이라 질량·마찰 어느 쪽도 개입할
자리가 없다.

`MoveTowards` 로 목표 속도를 향해 가는 구조 자체가 "외력을 무시한다"는 선언이었다.
#13 에서 넉백을 넣을 때 `Knockback.IsActive` 동안 대입을 건너뛰게 한 것이 같은 이유였는데,
그때는 자기 몸에만 해당하는 문제로 보였다.

### 레이어는 판정용과 몸통용이 따로다

한 오브젝트에 레이어는 하나뿐인데 필요한 건 둘이었다.

```
루트    Enemy(10)          지면과 부딪히고 플레이어는 통과
자식    EnemyHurtbox(9)    PlayerHitbox 하고만 반응
```

원래 루트가 `EnemyHurtbox` 였는데, 그 레이어는 #9 에서 히트박스 계열하고만 충돌하게
짜여 있어 **몸통을 실제 콜라이더로 바꾸는 순간 지면을 통과**한다. 판정 레이어를 몸통에
쓸 수 없다는 게 구조를 가르게 된 직접적인 이유다.

새 레이어의 매트릭스 기본값은 **"전부와 충돌"** 이다. 레이어만 옮기고 매트릭스를 안
건드리면 아무것도 달라지지 않는다.

`PlayerHitbox` 도 꺼야 한다. 안 끄면 적 **몸통**이 히트박스의 `OnTriggerEnter2D` 를 한 번
더 발생시킨다 — `HurtBox` 가 없어 첫 줄에서 걸러지지만 부를 이유가 없다.

프리팹 인스턴스는 함정이 하나 더 있다. **`m_Layer` 를 오버라이드해야** 유지된다. 프리팹
루트가 `Default` 면 씬에 놓는 순간 그대로 따라오고, 오버라이드 목록에 `m_Layer` 가 없으면
레이어 작업이 통째로 사라진 것이다.

### 넉백 값의 상한을 사거리가 정하고 있었다

허트박스를 1×1 에서 실물 크기로 줄이자 **3타가 빠졌다.** 원인은 3타의 사거리가 아니라
1·2타 넉백의 누적이었다.

```
히트박스 사거리 0.75 + 적 허트박스 반폭 0.25   →  적 중심이 1.0 이내여야 닿는다
넉백 이동거리 = 초기속도 × 0.1                  (0.2초 동안 선형 감쇠)

1·2타 넉백 5   →  0.5 씩 밀려 3타 시점에 정확히 1.0. 경계에서 스쳐 지나간다
```

지상 공격은 `AllowsHorizontalControl` 이 `false` 라 플레이어가 따라가지 못한다. 밀린 만큼
그대로 벌어진다 — **자기 콤보가 자기를 방해하고 있었다.**

값을 3 으로 낮춰 해결했지만, 요점은 **손맛으로 정해야 할 값이 기하학에 눌렸다**는 것이다.
넉백을 얼마나 줄지는 타격감의 문제인데 실제로는 사거리가 상한을 정하고 있었다. 증상이
"3타가 가끔 안 맞음"으로 나타나서 값 문제로 보이지 않는 것도 고약하다.

3타를 낮추는 쪽은 택하지 않았다. 마무리의 무게가 무너진다. 중간 타를 줄이는 쪽이
액션 게임의 일반적인 배분이기도 하다 — **중간 타는 제자리에 묶어두고 마무리에서 날린다.**
1·2타에는 히트스탑과 `Hit` 클립이 이미 붙어 있어 넉백이 유일한 피드백도 아니다.

### 논리 층과 보정 층을 나누는 규칙은 오브젝트마다 다시 세워야 한다

적에게 `HitBox` 를 붙였더니 **스프라이트가 보는 반대쪽에 생겼다.**

플레이어는 처음부터 두 층이었다.

```
Player                        논리 — facing 스케일 · HitBox/HurtBox 소유
└ Character_Sword  scale.x -1  에셋 보정 — 베이스 스프라이트가 왼쪽을 본다
```

적은 캐릭터 프리팹이 곧 루트였다. **두 역할이 한 트랜스폼에 겹쳐 있어서 보정할 자리가
없었다** — 루트 스케일이 `+1` 이면 스프라이트는 왼쪽을 보는데 히트박스 오프셋 `+0.4` 는
오른쪽이다.

히트박스 오프셋을 `-0.4` 로 뒤집어도 동작은 한다. 스케일을 뒤집으면 둘이 같이 뒤집히니
서로 어긋나지도 않는다. **문제는 부호의 의미가 플레이어와 반대가 된다는 것이다.**

```
플레이어   scale.x +1 = 오른쪽
적         scale.x +1 = 왼쪽
```

추격 코드를 쓸 때마다, 넉백 방향을 만들 때마다, 나중에 원거리 적의 투사체를 쏠 때마다
"이쪽은 부호가 반대였나"를 확인해야 한다. #35 에서 `facing` 을 아트에 맞추지 않은 것과
같은 이유다 — **규칙이 하나면 소비자가 늘어도 안 헷갈린다.**

빈 `Enemy` 래퍼를 만들어 두 층으로 나눴다. W3 에서 적 3종이 이 구조를 물려받으므로,
지금 반대로 두면 셋 다 반대 부호를 갖게 된다.

프리팹 기본값은 `+1` 로 둔다. 추격이 매 프레임 덮으므로 초기값은 곧 무의미해지지만,
사거리 밖에서 가만히 있는 적은 그 값으로 서 있는다. 방을 만들 때 방향을 바꾸고 싶으면
씬에서 스케일을 뒤집으면 된다 — **별도 `initialFacing` 필드를 만들 필요가 없다.**

### `Mathf.Sign(0)` 은 0 이 아니라 1 이다

추격 방향을 `Mathf.Sign(dx)` 로 잡았다. `dx` 가 정확히 0 이면 **오른쪽으로 판단한다.**

지금 구조에서는 `dx` 가 0 이면 사거리 안이라 추격 분기를 타지 않아 문제가 안 된다. 다만
"0 이면 안 움직인다"를 기대하고 쓰면 틀린다. `PlayerMovement` 가 `MoveInput > 0 ? 1 : -1`
로 삼항을 쓴 것도 입력 0 을 명시적으로 한쪽에 몰기 위해서였다.

### 중력을 끄려면 가속도만이 아니라 이미 붙은 속도도 눌러야 한다

스왑 대시를 수평으로 만들려고 `UsesGravity => false` 를 붙였다. `gravityScale = 0` 만으로는
**공중에서 대시할 때 대각선으로 흘렀다.**

`gravityScale` 은 **앞으로 더 붙을 가속도**를 막을 뿐이다. 이미 쌓인 `linearVelocityY` 는
그대로 남아 계속 아래로 민다. 낙하 중에 대시하면 그 속도가 고스란히 이어진다.

`linearVelocityY = 0` 을 같이 넣어야 수평이 된다. **"중력을 끈다"는 말이 두 가지를 뜻하고
있었다** — 새 힘을 안 받는 것과 지금 속도를 버리는 것.

`ClampFallSpeed` 가 이미 속도를 직접 누르고 있으니 같은 층의 처리다. 4절의 "속도는 덮어써도
위치는 누적된다"와 같은 결 — **한 층을 껐다고 다른 층이 따라 꺼지지 않는다.**

### 파생값의 분자가 0 이면 기능이 꺼지는 게 아니라 얼어붙는다

무기 SO 로 옮기면서 `clipWindup` 을 채우지 않아 0 이 남았다. 재생 속도가
`ClipWindup / startup` 이므로 **`animator.speed = 0`** 이 된다.

애니메이션이 "안 나오는" 게 아니라 **첫 프레임에서 멈춘 채 `startup + active + recovery`
동안 서 있는다.** 칼을 치켜든 자세로 굳는다.

기본값 0 이 기능을 끄는 사례(`knockbackTime`, `clipSpeed`)는 이미 겪었는데 이건 결이
다르다. **0 이 곱해지는 자리면 꺼지고, 나뉘거나 곱해서 배율이 되는 자리면 멈춘다.**
그리고 `animator.speed` 는 컴포넌트 전역이라 **공격이 끝날 때까지 이동·점프 모션도 같이
멈춘다** — 증상이 원인보다 넓게 퍼진다.

### 반전이 x 축에서만 일어나니 y 보정은 살아남는다

64×64 셀 안에서 캐릭터가 아래로 치우쳐 있어, `Character_Sword` 의 `localPosition.y` 를
`-0.35` 로 내려 보정했다. **x 로 어긋났다면 못 쓸 방법이다.**

facing 은 `Player` 의 `localScale.x` 로 만든다. 자식의 `localPosition` 도 부모 스케일을
같이 받으므로, x 오프셋은 방향을 바꿀 때마다 부호가 뒤집혀 그림이 `2 × 오프셋` 만큼 튄다.
y 는 뒤집히는 축이 아니라 그대로 남는다.

**보정을 트랜스폼에 둘 수 있는지는 "그 축이 뒤집히는 축인가"로 갈린다.** x 로 어긋난 건
스프라이트 피벗에서 고쳐야 한다 — 피벗은 반전의 축 자체라 뒤집혀도 어긋나지 않는다.

피벗을 고치는 쪽이 근본적이지만 이번엔 안 했다. 검과 창이 둘 다 `-0.35` 라 무기 6종이
같은 값을 쓰고, 피벗을 바꾸면 이미 구운 클립 7종 × 6무기를 다시 확인해야 한다.
**얻는 게 "필드 하나가 0 이 됨"뿐이면 근본적인 쪽이 이기지 않는다.**

29장 전부 셀 크기와 피벗이 같다는 걸 `.meta` 에서 먼저 확인했다. 프레임마다 다르면
애니메이션이 떨리는데 그게 아니었으므로, **다시 자르는 건 애초에 답이 아니었다.**

## 5. 설계 판단

### 접근자에 null 가드를 넣지 않는다

`MoveInput` 이 `actions == null` 일 때 `0f` 를 반환하게 만들면, 배선이 잘못됐을 때
**캐릭터가 조용히 안 움직인다.** 에러도 안 난다.

여기서 null은 "값이 없을 수도 있는 정상 상태"가 아니라 **"라이프사이클이 잘못됐다"는
버그 신호**다. 버그 신호는 숨기지 않고 크게 터뜨린다.

일반화: **접근자의 방어적 null 체크는 대개 냄새다.** "시끄러운 버그"를
"조용한 오작동"으로 바꾼다.

**예외** `OnDrawGizmosSelected` 의 지연 초기화는 가드가 맞다. 에디터에서 `Awake` 가
안 돈 것은 **정상 상태**이지 버그가 아니다. `Dispose` 도 정리라서 대상이 없으면
넘어가는 게 자연스럽다.

판단 기준: **null이 정상 상태인가, 버그 신호인가.**

### `GetComponent<T>()` 는 첫 번째를 반환한다

`GroundChecker` 가 `GetComponent<Collider2D>()` 로 몸통 콜라이더를 찾고 있었다.
콜라이더가 하나뿐이라 잘 동작했지만, #9에서 `Hurtbox`(역시 `Collider2D`)를 추가하면
엉뚱한 것을 집어올 수 있다.

**최악인 이유** 기즈모도 같은 `bounds` 를 쓰므로 **그림까지 함께 틀린다.** 그림과
판정이 일치하니 "기즈모는 맞는데 왜 안 되지" 상태가 되고, 기즈모를 신뢰 근거로
삼는 전제가 무너진다.

→ `[SerializeField] Collider2D` 로 명시 지정 + 폴백 시 `Debug.LogWarning`.
폴백이 조용히 넘어가지 않아야 나중에 원인이 드러난다. ([#21](../../issues/21))

### 인터페이스 · 추상 기반 클래스 · 제네릭이 각각 하는 일

상태머신을 세 타입으로 나눴는데, 각자 역할이 다르다.

| | 역할 | 필수? |
|---|---|---|
| `IState` | 상태머신이 호출할 메서드 목록 (계약) | 필수 |
| `StateMachine<TOwner>` | 현재 상태 보관, 전환, 위임 | 필수 |
| `BaseState<TOwner>` | 반복 제거 + 타입 안전한 `Owner` 제공 | **선택** |

**`BaseState` 가 왜 있는가** — `IState` 를 직접 구현하면 상태마다 이게 반복된다.
`Owner`/`Machine` 필드 보관, 생성자에서 주입, **안 쓰는 메서드 3개 구현**
(인터페이스는 전부 구현해야 한다).

`virtual` + 빈 몸통을 두면 필요한 것만 `override` 한다.
**`MonoBehaviour` 와 같은 구조다** — Unity가 부를 수 있는 콜백을 다 준비해두고
`Awake` 와 `FixedUpdate` 만 쓰는 것과 똑같다.

`abstract` 는 "이 클래스 자체는 쓸 수 없다"는 표시. `BaseState` 는 아무 행동도 하지
않으니 `new BaseState(...)` 를 컴파일러가 막는다.

**제네릭이 값을 내는 지점** — `Owner` 가 `TOwner` 로 잡혀 있어 파생 상태에서 캐스팅이
없다. `object` 나 `MonoBehaviour` 로 받으면 매번 캐스팅해야 한다.
적은 `BaseState<EnemyBrain>` 을 상속하면 **소유자 타입만 바뀐 같은 틀**이 된다.

**`StateMachine` 은 `BaseState` 를 모른다.** `IState` 만 본다. 그래서 누군가
`BaseState` 를 안 쓰고 `IState` 를 직접 구현해도 상태머신은 그대로 돌아간다.
계약과 편의를 분리한 결과다.

### 같은 상태로 전환 요청이 오면 무시한다

`Enter()` 는 **진입당 한 번** 도는 것이 계약이다. 재진입을 허용하면 그 계약이
조용히 깨진다.

| | 결과 |
|---|---|
| 무시 (`return`) | 진행 중인 상태가 이어짐. 세부 진행은 상태 내부에서 처리 |
| 재진입 | `Exit()` → `Enter()` → 타이머 리셋, 모션 처음부터 |

구체적 실패: `Attack` 의 `Enter()` 가 콤보 타이머를 초기화한다면, 공격 중 재입력마다
**1타로 되돌아가 콤보가 영원히 진행되지 않는다.** `Move` 상태라면 `Enter()` 가
초당 50번 돈다 — 발소리 재생이나 가속 초기화가 거기 있으면 다 망가진다.

호출 3번에 진입 3번, `Enter()` 3번. 가드가 없으면 `Enter()` 가 4번 돌아 어긋난다.

재시작이 필요하면 **상태 내부에서 처리**하거나 `Change(state, force: true)` 같은
명시적 경로를 둔다. 기본 경로를 모호하게 두면 부르는 쪽이 매번 "이게 재진입할까"를
고민하게 된다.

`force` 가 실제로 필요해지는 첫 사례는 **2단 점프**다. 공중에서 점프하면 이미 `Jump`
상태이므로 `Change(Jump)` 가 무시되고 공중 점프 모션이 재생되지 않는다. 1차에서는
2단 점프를 넣지 않기로 해서([GDD 12.1](GDD.md)) 아직 만나지 않았다.

### 선언과 호출 경로는 다르다 — 미루는 판단이 갈린 곳

허용 플래그 3개는 **빼기로** 했고, `machine.Tick()` 은 **지금 넣기로** 했다. 둘 다
"아직 아무도 안 쓴다"인데 판단이 반대였다. 차이는 이렇다.

| | 상태 | 나중에 쓰려 하면 |
|---|---|---|
| 허용 플래그 | 선언만 있고 **배선 없음** | 배선을 추가하면 동작한다 |
| `IState.Tick` | 계약은 있고 **호출 경로 없음** | 오버라이드해도 **조용히 안 돈다** |

플래그는 "안 쓰는 기능"이고, `Tick` 은 **"있다고 믿게 만드는 빈 구멍"** 이다.
`IState` 에 메서드가 보이니 당연히 돌 거라고 믿게 되는 점이 특히 나쁘다.

`machine.Change(Idle)` 을 빼먹었을 때와 같은 종류의 실패인데, 이번엔 인터페이스가
근거를 제공해서 의심조차 하지 않게 된다.

**판단 기준: 없어서 안 되는 것인가, 있는데 안 도는 것인가.** 후자가 더 위험하다.

### 안전장치를 무력화하는 코드가 따로 있을 수 있다

#21 에서 `bodyCollider` 폴백 경고를 넣었다. 그 자체는 잘 동작했다. 그런데 **다른 코드가
경고의 조건 자체를 없애버리고 있었다** — 기즈모가 필드를 채우니 `bodyCollider == null`
이 성립하지 않았다.

경고문을 아무리 잘 써도 조건이 성립하지 않으면 뜨지 않는다. **경고를 넣었다는 사실이
안전을 보장하지 않는다.**

검증 방법도 여기서 나왔다. #28 의 완료 조건을 "코드가 이렇게 생겼다"가 아니라
**"필드를 비우고 기즈모를 본 뒤에도 경고가 뜬다"** 로 잡았다. 안전장치는 발동 조건을
직접 만들어서 확인해야 한다.

### 되돌리기 비용의 비대칭으로 결정한다

2단 점프 유무를 판단할 때 "어느 쪽이 더 재미있는가"가 아니라 **어느 쪽이 틀렸을 때 더
비싼가**로 결정했다.

| | 나중에 바꾸는 비용 |
|---|---|
| 1단으로 설계 → 2단 추가 | 싸다. 기존 방이 전부 통과 가능해지고 난이도만 내려간다 |
| 2단으로 설계 → 제거 | 비싸다. "2단으로만 닿는 높이"가 레벨 전체의 전제가 된다 |

**판단이 어려울 때는 되돌리기 싼 쪽을 먼저 택한다.** 그러면 판단을 미룰 수 있고, 미루는
동안 정보가 쌓인다. GDD 의 이연 원칙과 같은 발상인데, 이연 대상이 기능이 아니라
**판단 자체**인 경우다.

전제가 코드가 아니라 **에셋(방 프리팹)** 에 박히는 항목이 특히 위험하다. 코드는 고치면
되지만 레벨은 다시 그려야 한다.

### 전환은 상태가 결정한다 (조건표를 두지 않았다)

`Machine.Change()` 를 상태 자신이 부른다. 상태머신은 전이 조건표를 들지 않는다.

이 규모에서는 `Idle` 이 "입력 들어오면 Move" 를 아는 게 자연스럽고 조건이 코드로 바로
읽힌다. 조건표 방식은 상태가 10개를 넘고 전이 규칙을 **데이터로 빼고 싶을 때** 값이 생긴다.

### 공통 물리 처리를 상태로 옮기지 않았다 ← #7 최대 판단

상태머신을 붙일 때 두 구조를 검토했다.

| | 공통 처리를 부르는 주체 | 상태가 하는 일 |
|---|---|---|
| **(A)** | `PlayerMovement` | 전환 판단만 + 허용 여부 선언 |
| **(B)** | 각 상태 | 호출 순서를 직접 짬 |

**(A) 를 택했다.**

```
PlayerMovement.FixedUpdate:
    코요테 갱신 → machine.FixedTick() → HandleHorizontal → 버퍼 점프
                                      → ApplyGravity → ClampFallSpeed
```

(B) 가 표현력은 높다. `AttackState` 가 `HandleHorizontal` 을 아예 안 부르면 "공격 중
이동 불가"가 코드에 그대로 드러난다. 그런데 대가가 세 개다.

1. **실행 순서가 상태마다 복제된다.** #6에서 부호로 4번 헤맨 건 사실 순서 문제였다.
   순서가 4곳에 흩어지면 한 상태에서만 틀리고, 그게 제일 찾기 어렵다
2. **호출 누락이 조용히 실패한다.** 새 상태에서 `ApplyGravity` 를 빼먹으면 컴파일
   에러도 예외도 없이 공중에 뜬 채로 공격한다
3. **전환 프레임에 물리가 한 번 빠질 수 있다.** #7 완료 조건이 "착지 시 1프레임
   깜빡임 없음" 이라 이게 그대로 요구사항이었다

**(B) 로 옮길 신호는 상태 개수가 아니다.** 상태가 8개여도 차이가 "이동 허용/불허"
하나면 (A) 로 충분하다. 신호는 **차이가 켜고 끄기가 아니라 순서·타이밍이 될 때**다.

> "공격 중엔 중력 절반, 처음 3프레임은 수평 고정, 그 후 감속"

이건 `bool` 로 표현되지 않는다. 그때 옮기면 되고, 상태 클래스는 그대로 두고
`FixedTick` 본문만 이동하므로 전환 비용이 낮다.

### 프로퍼티는 값이 아니라 질문이다

`CurrentState.AllowsHorizontalControl` 을 "어딘가에서 `false` 로 바뀌는 변수"로
이해하려다 막혔다. 그게 아니다.

```
프레임 100:  CurrentState → IdleState 객체   → "이동 허용?" → true   (기본값)
프레임 200:  CurrentState → AttackState 객체 → "이동 허용?" → false  (override)
```

**값이 변한 게 아니라 대답하는 객체가 바뀐 것이다.** `IdleState` 는 언제 물어도
영원히 `true` 를 대답한다. 그래서 "어디서 바뀌나"의 답은 런타임이 아니라
**새 상태 클래스에 `override` 를 쓰는 시점**이다.

`=>` 문법이 오해를 부추긴다. `bool X => expr;` 은 필드가 아니라
`get { return expr; }` 의 축약이라 **읽을 때마다 실행된다.** `IsGrounded` 를 매 프레임
새로 묻는 것과 같은 구조다.

이게 다형성으로 분기를 없애는 방식이다. `PlayerMovement` 는 `AttackState` 라는 클래스가
존재하는지도 모른 채 "지금 상태"에게 묻기만 한다. `if (state is AttackState)` 를 쓰면
새 상태마다 `PlayerMovement` 를 고쳐야 한다.

### 이해되지 않는 코드는 지금 넣지 않는다

허용 플래그 3개(`AllowsHorizontalControl` / `UsesGravity` / `AcceptsJumpInput`)를
"#10 이 편해진다"는 이유로 미리 배선했다가 **되돌렸다.** 세 곳에 읽는 코드를 넣었는데
아직 `false` 로 만드는 상태가 없어서 동작이 하나도 바뀌지 않았고, 그래서 왜 있는지
이해되지 않았다.

`추상화는 중복이 실제로 보인 다음에 넣는다` 는 4절의 교훈을 그대로 위반한 것이다.
#1 을 뒤로 미뤄서 `PlayerMovement` 의 분기 7줄을 먼저 본 것과 같은 순서를 지켜야 했다.

**이해 안 되는 코드를 안고 가는 비용 > 나중에 다시 넣는 비용.** 미리 넣은 코드는
동작하지 않으면서 자리를 차지하고, 다음에 읽을 때 "이거 살아 있나"를 다시 확인하게 만든다.

선언은 `PlayerState` 에 남기고 `#10 에서 사용 예정` 주석을 달았다. 배선은 실제 필요가
생길 때 한다.

**#47 에서 `UsesGravity` 가 첫 소비자를 얻었다.** #7 에 선언해두고 아무도 안 읽던 프로퍼티인데,
`SwapState` 가 수평 대시를 하려면 정확히 그게 필요했다. 미리 둔 게 값을 한 셈이다.

그런데 #49 에서는 반대 판단을 했다 — **스킬 거동을 조각으로 쪼개는 구조는 지금 만들지
않는다.** 둘의 차이는 **미리 두는 비용**이다.

| | 미리 둔 비용 | 판단 |
|---|---|---|
| `UsesGravity` | 프로퍼티 한 줄. 다른 넷과 같은 모양으로 함께 태어났다 | 둬도 된다 |
| 스킬 조각 시스템 | 인터페이스·조립 규칙·데이터 형식을 설계해야 한다 | 소비자를 기다린다 |

**"소비자가 생겨야 산다"는 비용이 있을 때의 규칙이다.** 비용이 0 에 가까우면 미리 둬도
잃을 게 없고, 오히려 나중에 그 자리를 찾느라 구조를 흔들지 않게 된다. 위 `AttackState`
사례가 비쌌던 건 **이해하지 못한 코드**였기 때문이지 미리 뒀기 때문이 아니다.

### 이연은 삭제가 아니다

1차 범위 밖 항목마다 "나중에 어떻게 붙이는지"를 함께 기록하고, 확장 지점을 지금
남겨둔다. 그러면 후속 작업이 재작성이 아니라 **데이터 작성**이 된다.

지금 지키는 확장 지점 4개는 [GDD 9장](GDD.md)에 정리돼 있다.

### 키는 "같은 콜라이더인가"가 아니라 "같은 적인가"

중복 방지 캐시의 키를 `Collider2D` 로 잡으면, 적이 허트박스를 둘 이상 가지는 순간
(몸통·머리) 서로 다른 콜라이더라 한 번의 공격에 두 번 맞는다.

물어야 하는 질문이 "같은 적인가"이므로 키도 그 단위여야 한다. `HurtBox.Owner` 를 공개한
이유가 이것이고, `DamageInfo.Source` 도 같은 기준(루트 GameObject)으로 맞췄다. 그래야
자기 타격 방지가 단순 비교 한 줄로 끝난다.

히트박스가 자식에 있으므로 여기서 `gameObject` 를 그대로 쓰면 자식이 출처가 된다.
자식끼리 비교하면 `Player/HitBox` 와 `Player/HurtBox` 가 서로 다른 오브젝트라 자기 타격
방지가 통과해버린다.

### `DamageInfo` 는 데이터가 아니라 사건이다

처음에 `ScriptableObject` 로 만들었다가 걷어냈다. SO 는 디스크에 저장되는 에셋이고
`CreateInstance` 를 거쳐야 하는데, 출처와 넉백 방향은 **때리는 순간** 정해지므로 미리
작성해둘 수 있는 값이 아니다.

W2 의 무기 SO 와 층이 다르다. 무기 SO 는 "대검의 기본 데미지 15" 같은 작성된 데이터고,
`DamageInfo` 는 그것을 재료로 매 타격마다 만들어지는 런타임 값이다. 여기서 SO 를 쓰면
두 층이 뒤엉킨다.

생성자에서만 채우고 이후 읽기만 하게 한 것도 같은 이유다. 한 번의 공격이 여러 대상을
때릴 때 중간에 값이 바뀌면 뒤에 맞는 대상만 다른 값을 받는다.

### 검증 수단이 없으면 완료 조건도 없다

#9 를 끝냈을 때 `HitBoxActivate` 를 부르는 곳이 아무데도 없었다. 활성 구간 제어는 #10 의
일이지만, 그대로 두면 "같은 적이 두 번 맞지 않는다"를 확인할 방법이 없다.

임시 드라이버를 **토글**로 만든 것이 판단이었다. 코루틴으로 자동 종료시키면 켜기와 끄기가
한 동작에 묶여 "켠 채로 두면 추가 히트가 없다"와 "껐다 켜면 다시 맞는다"를 각각 확인할 수
없다. **검증 도구는 검증하려는 것을 분해할 수 있어야 한다.**

### 선언만 있는 확장 지점은 소비자가 생겨야 산다

`PlayerState` 의 허용 플래그 세 개는 #7 에서 만들어졌지만 #10 까지 **아무도 읽지 않았다.**
그동안 값을 어떻게 바꿔도 게임은 똑같이 동작했다.

`AttackState` 가 `AllowsHorizontalControl` 을 `false` 로 재정의한 것만으로는 아무 일도
일어나지 않는다. `HandleHorizontal` 이 그 값을 읽어야 비로소 효과가 생긴다. 확장 지점을
미리 만들어두는 것과 그것이 실제로 동작하는 것은 별개다.

부작용도 있었다. 소비자가 없는 동안에는 기본값이 틀려도 드러나지 않는다. `PlayerState` 의
기본값을 실수로 `false` 로 바꿨을 때, 읽는 곳이 생긴 뒤에야 **모든 상태에서 이동이
막히는** 증상으로 나타났다.

**기본값은 "제약 없음"이어야 한다.** 그래야 새 상태가 평범하게 동작하고, 제약이 필요한
상태만 명시적으로 꺼서 그 상태가 특별하다는 것이 코드에 드러난다. 기본이 `false` 면 모든
상태가 허용을 일일이 켜야 하고, 빠뜨리면 조용히 막힌다.

### 취소 수단의 비용이 리스크를 정한다

공격 중 점프를 막기로 했다. 후딜이 리스크로 남아야 W2 의 무기 스왑(대시 + i-frame +
쿨타임)이 유일한 탈출구가 되고, 그래야 스왑의 가치가 올라간다. 점프로 공짜로 빠져나갈 수
있으면 회피용으로 스왑을 쓸 이유가 줄어든다. GDD 가 무기 교체를 이 게임의 정체성으로
두고 있으므로 그쪽을 살렸다.

취소 수단마다 비용이 다르다는 것이 판단의 축이었다.

| 수단 | 비용 |
|---|---|
| 점프 · 이동 | 없음 |
| 콤보 | 계속 붙어 있어야 함 |
| 스왑 · 스킬 | 쿨타임 |

비용 없는 취소가 많을수록 후딜이 무의미해지고, 무기별 후딜 값으로 무게감을 표현하려던
계획도 같이 무너진다.

되돌리기 비용도 한 방향으로만 쌌다. 나중에 여는 것은 플래그 한 줄이지만, 열어뒀다가 닫는
것은 이미 익숙해진 감각을 뺏는 일이다. → [되돌리기 비용의 비대칭으로 결정한다](#되돌리기-비용의-비대칭으로-결정한다)

### 인스펙터에 둘 수 있는 것과 없는 것

`DamageInfo` 를 `[SerializeField]` 로 노출하려 했지만 인스펙터에 나타나지 않았다. 이유가
셋이다 — `[Serializable]` 이 없고, 매개변수 없는 생성자가 없고, **Unity 는 필드만
직렬화하는데 전부 프로퍼티**다.

특성을 붙이고 필드로 바꾸면 되긴 하지만, 그러면 읽기 전용으로 만든 설계가 무너진다.
직렬화는 "기본 생성자 + 쓰기 가능한 필드"를 요구하기 때문이다.

**성격이 반대다.** 인스펙터에 두는 것은 미리 정해둘 수 있는 값이고, `DamageInfo` 는 때리는
순간 정해지는 사건이다. `Source` 는 런타임에만 알 수 있고 넉백 방향은 매번 달라진다.

그래서 **값만 인스펙터에 두고 조합은 코드가 한다.** `damage` / `knockbackForce` /
`hitStopTime` 세 필드와, 그것들을 `facing` · `gameObject` 와 엮는 메서드 하나로 나눴다.
W2 에서 값의 출처가 무기 SO 로 바뀌어도 고칠 곳은 그 메서드뿐이다.

`Awake` 에서 한 번 만들어 재사용하는 것도 안 된다. 시작 시점의 방향이 박제된다.

### `static` 으로 갈 수 있는 이유가 UniTask 다

`HitStop` 은 씬에 오브젝트가 없다. 코루틴이었다면 `StartCoroutine` 을 불러줄
`MonoBehaviour` 가 필요해서 매니저 오브젝트를 두거나 `RuntimeInitializeOnLoad` 로 숨은
오브젝트를 만들어야 했다. UniTask 는 PlayerLoop 에 직접 붙으므로 소유자가 없어도 된다.

**"전역 상태 하나뿐이니 static 으로 하자"가 먼저가 아니라, 소유자 없이 시간을 기다릴 수단이
있어서 static 이 성립한 것이다.** #10 에서 코루틴 대신 UniTask 를 택한 판단이 여기서 배치
선택까지 바꿨다 — 도구를 고르면 쓸 수 있는 구조가 함께 정해진다.

배치는 `Gameplay/Feel/` 로 했다. 전투 판정이 아니라 연출이고 #14 화면 흔들림과 #15 깜빡임이
같은 성격으로 들어온다. `Game.Core` 에 두는 방법도 있었으나 Core 에 UniTask 참조를 새로
걸어야 하고 UI 가 쓸 일이 없다 — **어셈블리를 미리 넓히지 않는다.** 필요해지면 그때 옮긴다.

#### 대가 — 도메인 리로드를 끄면 `static` 이 플레이 세션을 넘어 남는다

프로젝트 설정을 보니 `m_EnterPlayModeOptionsEnabled: 1` · `m_EnterPlayModeOptions: 0` 이다.
**도메인 리로드와 씬 리로드를 둘 다 끈** 상태고, 플레이 진입이 빨라지는 대신 `static`
필드가 초기화되지 않는다.

`HitStop` 의 `remaining` · `running` 이 그 대상이다. `Play` 가 도는 도중에 플레이를 멈추면
`RunAsync` 의 `finally` 가 안 돌 수 있고, 그러면 **`running` 이 `true` 로 남는다.** 다음
플레이에서 `Play()` 가 `if (running) return;` 으로 즉시 빠져나가 **히트스탑이 영영 안
걸린다.**

`Time.timeScale` 은 Unity 가 플레이 종료 시 복구하므로 게임이 멈추지는 않는다.
**조용히 기능 하나만 죽는다** — 에러도 로그도 없다.

`Shake` 와 `Invincibility` 는 `MonoBehaviour` 라 씬과 함께 새로 만들어진다. **`static` 인
`HitStop` 만 해당한다.** 위 문단이 "소유자가 없어도 된다"를 장점으로 적었는데, 소유자가
없다는 건 **생명주기를 관리해줄 주체도 없다**는 뜻이다.

표준 처리는 `[RuntimeInitializeOnLoadMethod]` 로 두 필드를 리셋하는 것이다. 아직 겪지
않았으므로(히트스탑이 0.05~0.09초라 창이 좁다) 지금 넣지 않고, `Feel/` 근처를 건드리는
#50 에서 같이 본다.

### 감쇠를 누가 소유하는가

넉백을 `linearVelocityX` 에 넣기만 하면 `HandleHorizontal` 의 `groundDecel` 이 처리한다.
계산해보니 5 가 0.14초에 0 이 됐다 — 스텝당 `35 × 0.02 = 0.7`. **동작은 하지만 넉백으로
읽히지 않는 길이**다.

`groundDecel` 은 조작감용 값이다. 손을 떼면 얼마나 빨리 멈추는지를 정한 것이고, 외부에서
밀려나는 감쇠와 같은 값일 이유가 없다. **하나의 값이 두 가지를 통제하는 형태**라 5절에
이미 같은 항목이 있다.

그래서 `Knockback` 이 자기 곡선을 든다. 다만 적은 `HandleHorizontal` 을 갖고 있지 않으므로
이 충돌은 **플레이어가 넉백을 받는 #17 부터** 실제 문제가 된다. `IsActive` 는 그때
`HandleHorizontal` 이 대입을 건너뛰기 위한 것이고, 지금 소비자가 없다.

**소비자 없는 선언을 남긴 판단이다.** 5절 "선언만 있는 확장 지점은 소비자가 생겨야 산다"에
어긋나 보이지만, 여기서는 한 줄이고 의미가 코드에서 바로 읽히고 **#17 에서 확실히 쓰인다.**
`PlayerState` 의 권한 플래그를 배선 없이 선언만 남기고 주석으로 #10 을 적어둔 것과 같은
처리다 — 판단 기준은 "지금 안 쓰이는가"가 아니라 "쓰일 자리가 확정됐는가"다.

### 히트스탑과의 순서가 코드 없이 정해졌다

넉백을 히트스탑 중에 넣을지 끝난 뒤에 넣을지가 체감을 바꾼다. 정하려고 봤더니 **이미
정해져 있었다.**

`timeScale` 이 0 이면 `FixedUpdate` 가 돌지 않는다. `remaining` 도 안 줄고 속도도 안
걸리므로, 정지가 풀리는 순간 튀어나간다. 원하던 쪽이었다.

**반대쪽을 원했다면 오히려 코드가 필요했다.** `timeScale` 을 안 쓰는 대기(unscaled)로
넉백 시작을 미뤄야 한다. 어떤 선택은 기본 동작이 이미 답이고, 그걸 확인하는 게 구현보다
먼저다.

### 겹칠 때 정책은 대상마다 다르다

| | 정책 | 이유 |
|---|---|---|
| 히트스탑 (#12) | `Max` | 긴 정지가 짧은 정지를 포함한다. 짧은 쪽으로 덮으면 연출이 잘린다 |
| 넉백 (#13) | 덮어쓰기 | **마지막 타격 방향으로** 밀려야 하고 세기도 그 타격의 것이어야 한다 |
| 흔들림 (#14) | `Max` | 진폭뿐이라 방향 개념이 없다. 큰 흔들림이 작은 흔들림을 포함한다 |
| 무적 시간 (#15) | `Max` | 시간이라 포함 관계가 성립한다 |
| 깜빡임 여부 (#47) | `OR` | **불리언에는 크기가 없다.** "깜빡인다"가 "안 깜빡인다"를 포함한다 |

합산은 넷 다 아니다. 넉백을 합산하면 3타 콤보에서 누적돼 날아간다.

`OR` 가 새로 나온 건 값의 종류가 처음으로 불리언이었기 때문이다. `Max` 를 불리언에 쓰면
`true` 가 이기니 결과는 같지만, **왜 이기는지의 근거가 다르다** — 크기가 커서가 아니라
"맞았다"가 더 중요한 정보라서다. 스왑 무적 중에 맞으면 깜빡여야 하고, 피격 무적 중에
스왑해도 깜빡임이 유지돼야 한다.

**앞선 사례의 정책을 그대로 가져오면 틀린다.** `Max` 가 히트스탑에서 맞았던 이유(포함
관계)가 넉백에는 없었다. 흔들림에서 다시 `Max` 가 된 건 히트스탑을 따라서가 아니라
**방향이 없다**는 별개의 이유다.

가르는 질문은 "겹친 둘 중 하나가 다른 하나를 포함하는가"다. 시간과 진폭은 포함 관계가
성립하고, 방향이 있는 값은 성립하지 않는다.

### 원위치를 기억하지 않아도 되게 만들었다

화면 흔들림은 끝날 때 원위치로 돌아가야 한다. 카메라를 직접 흔들면 그 위치를 어딘가에
저장해야 하는데, **저장 시점이 두 가지고 둘 다 틀린다.**

| 시점 | 실패 |
|---|---|
| `Awake` | 카메라가 다른 이유로 움직이면 값이 낡는다. W3 방 전환 후 흔들림이 끝나면 레벨 시작 지점으로 튄다 |
| 흔들림 시작 | 겹치면 **이미 흔들린 위치**를 원위치로 저장한다. 겹칠 때마다 조금씩 밀려나 안 돌아온다 |

`Max` 중첩을 골랐으니 겹침은 정상 경로다. 적이 둘이면 바로 일어난다.

빈 `CameraRoot` 를 부모로 두고 카메라의 `localPosition` 을 흔들면 원위치가 `Vector3.zero`
다. **기억할 게 없으니 낡을 수도, 오염될 수도 없다.**

#35 에서 스프라이트 반전을 자식 `localScale` 로 처리한 것과 같은 모양이다. 부모의 의미를
지키려고 보정을 자식이 든다. 여기서는 `CameraRoot` = 어디를 보는가(world),
`Main Camera` = 어떻게 떨리는가(local) 로 갈라져서, 나중에 추적·방 전환이 붙어도
**같은 값을 두 스크립트가 덮어쓰는 상황이 생기지 않는다.**

이게 "미래 대비"가 아니라는 게 중요하다. 겹침 드리프트는 지금 발생 가능한 버그다.
그게 없었다면 리그는 나중으로 미뤘어야 한다 — 빈 오브젝트 하나라도 필요 없으면 안 만든다.

### `static` 이 값을 들었는지 참조를 들었는지

`HitStop` 은 `static bool running` 이 도메인 리로드에서 굳어 히트스탑이 영영 안 걸리는
문제가 있다(4절). `Shake` 는 같은 `static` 인데 그 문제가 없다.

**값은 아무도 되돌리지 않으면 굳는다.** 참조는 새 오브젝트가 `Awake` 에서 자기를
등록하면서 자연히 갱신된다. Unity 가 파괴된 오브젝트에 대해 `== null` 을 `true` 로
돌려주는 것도 이쪽을 돕는다.

`static` 을 쓸 때 위험한 쪽은 **상태를 담은 static** 이다. 진입점만 담은 static 은
같은 위험이 없다.

### 취향이 근거가 될 때와 안 될 때

화면 흔들림을 개인적으로 싫어한다는 게 판단에 들어갔다. 그 자체는 정당한 입력이지만,
**어디까지 근거가 되는지는 갈린다.**

- **피격 흔들림은 정보다.** "내가 맞았다"를 알리는 장치라 취향으로 뺄 수 없다
- **타격 흔들림은 연출이다.** 없어도 게임이 성립하므로 취향이 근거가 된다

그리고 지금 시점의 선호는 **관찰이 아니라 예측**이었다. 적이 공격하지 않으니 피격 흔들림을
느껴본 적이 없는 상태에서 "피격만 있으면 좋겠다"고 판단한 것이다. 그래서 결정을 #17 로
미루고 값만 넣어뒀다 — 바꾸는 비용이 값 두 개라 미루는 데 비용이 없다.

**"싫다"를 받아들이는 방식이 둘이다.** 기능을 빼거나, 강도를 값으로 만들어 0 을 고를 수
있게 하거나. 후자는 나중에 판단이 바뀔 여지를 남기고 설정 화면 항목이 되기도 한다.

### 에셋의 구현 방식이 게임 구조를 정했다

Pixem 을 무기 교체용으로 골랐는데, 정작 **런타임 무기 교체가 불가능한 에셋**이었다.
`PixemCharacter.cs` 의 본문 전체가 `#if UNITY_EDITOR` 로 감싸여 있고, 파츠 조립이
`AnimationUtility.SetObjectReferenceCurve` 로 **클립을 직접 편집**하는 방식이다. 이 API 는
에디터 전용이라 빌드에 존재하지 않는다.

그래서 무기 교체를 파츠 단위가 아니라 **프리팹 단위**로 가져가기로 했다. 무기별로 캐릭터를
미리 굽고 프리팹과 `AnimatorOverrideController` 를 교체한다. 대가는 "두 무기를 동시에
보여줄 수 없다"인데, 스컬식 슬롯 2개는 대기 무기가 화면에 없어도 되므로 지금 범위에서
잃는 게 없다.

**에셋 설명은 "무기를 독립적으로 장착 가능"이라고 읽혔지만 그건 에디터 도구의 이야기였다.**
스토어 페이지로는 이 구분이 드러나지 않는다. 다음에 에셋을 고를 때 볼 것은 기능 목록이
아니라 **런타임 코드가 있는지**다 — `#if UNITY_EDITOR` 하나가 게임 구조를 바꿨다.

에셋 탐색을 W1 중반까지 끌었던 대가도 같이 나왔다. #9~#12 를 임시 도형으로 진행해서
히트박스·히트스탑 값을 다시 잡게 됐다. 로드맵 W0 에 "에셋 탐색을 W1 이후로 넘기면 일정이
반드시 무너진다"고 적어두고 그대로 밀린 것이다.

### `internal` 과 `protected` 는 다른 축이다

상태 이름 상수를 어디에 둘지 정하면서 접근자를 두 번 틀렸다.

```
internal   →  같은 어셈블리 안이면 OK.  상속 여부는 안 본다
protected  →  나를 상속한 클래스면 OK.  어셈블리는 안 본다
```

`PlayerMovement` 에 `protected` 로 뒀더니 아무도 못 썼다. **`PlayerMovement` 를 상속하는
클래스가 프로젝트에 하나도 없어서 사실상 `private` 이었다.** `IdleState` 는 `PlayerMovement`
를 상속하지 않고 `Owner` 로 참조만 한다 — 관계가 상속이 아니라 합성이다.

`internal` 로 바꾸니 접근은 되는데 `clipIdle` 이라는 이름이 안 잡혔다. **접근자는 "접근해도
되는가"만 정하고 "어떻게 부르는가"는 안 바꾼다.** 접두어 없는 이름은 자기 클래스와 상속
계층에서만 찾으므로 `PlayerMovement.clipIdle` 로 써야 했다.

결국 상수를 `PlayerState` 로 옮겼다. 여기서는 상태들이 실제로 파생 클래스라 `protected` 가
의도대로 동작하고, 애니메이션 상태 이름은 물리 담당(`PlayerMovement`)보다 표현 담당
(`PlayerState`) 쪽 관심사다.

`public` 으로 열지 않은 이유가 실질적이다. `public` 이면 `Game.UI` 에서
`player.PlayClip("Death")` 를 부를 수 있게 되고, **상태머신이 애니메이션의 유일한 주인이
아니게 된다.** 어긋났을 때 원인을 찾을 곳이 두 배가 된다. 접근자는 문법이 아니라
"이건 누가 건드려도 되는 것인가"를 컴파일러에게 맡기는 장치다.

### 상수는 이름을 붙이는 게 아니라 틀릴 자리를 줄이는 것이다

상수를 선언하고 호출 지점은 리터럴로 남겨둔 단계가 있었다. 그 상태에서는 **관리할 곳이
오히려 늘었다** — 리터럴 5개 + 상수 4개. 게다가 상수 값 셋이 실제 상태 이름과 달랐는데
(`"Move"` `"Fall"` `"Attack"`) 아무도 안 쓰니 드러나지도 않았다.

`"Jupm"` 오타가 컴파일을 통과한 것도 여기에 걸린다. 상수를 실제로 썼다면 컴파일 에러였다.

**선언은 절반이고, 쓰는 순간부터 값을 낸다.** 5절 "선언만 있는 확장 지점은 소비자가 생겨야
산다"와 같은 형태인데, 이번엔 소비자를 안 만든 게 아니라 **만들 수 있는데 안 쓴** 경우다.

### 파생값을 리터럴로 저장하지 않는다

콤보 3타의 재생 속도를 `AttackData.speed` 에 `1.0 / 1.2 / 0.8` 로 넣었다. 값은 맞았는데
**"하드코딩 같다"는 느낌이 정확했다.**

세 값은 전부 `0.1167 / startup` 의 결과다. 그 관계가 어디에도 없어서

- `startup` 을 조정하면 speed 가 **조용히 틀려진다**
- 인스펙터를 봐도 왜 1.2 인지 알 수 없다

`clipWindup` 하나만 남기고 나눗셈을 코드로 옮겼다. 숫자가 3개에서 1개로 준 게 요점이
아니다. **성질이 달라진다.**

| | |
|---|---|
| `0.1167` | `.anim` 을 열면 확인되는 **사실** (두 번째 키프레임 시각) |
| `1.0 / 1.2 / 0.8` | 무엇으로부터 나왔는지 파일 어디에도 없는 **결과** |

검증 가능한 값만 데이터로 두고 나머지는 코드가 만든다. 이 프로젝트가 이미 쓰는 방식이다 —
`jumpHeight` 를 노출하고 속도를 `Mathf.Sqrt(2 * g * h)` 로 역산하는 것, 최소 점프 높이를
필드로 안 만들고 `jumpHeight / lowJumpGravityMult` 로 파생시킨 것과 같다.

**주석이 값의 출처를 적어야 이 이점이 유지된다.** 처음에 `// 프레임 길이` 라고만 썼는데,
그러면 반년 뒤에 보면 speed 세 개와 다를 게 없다. 어느 파일을 열어보면 되는지가 들어가야
"틀렸을 때 알아낼 수 있는 값"이 된다.

한계는 남는다. 키프레임 시각을 런타임에 읽을 방법이 없다 — `AnimationClip.length` 는
읽히지만 커브 내부는 `AnimationUtility` 뿐이고 그건 에디터 전용이다. 파츠 교체가 막혔던
것과 같은 벽이라, **완전 자동화가 아니라 "손으로 넣는 숫자를 검증 가능한 하나로 줄이는
것"이 도달점**이다.

### 허트박스는 부위고 체력은 개체다

체력을 `HurtBox` 안에 두면 보스처럼 머리·몸통·꼬리에 허트박스를 따로 두는 순간 **체력이
셋으로 갈린다.** 물어야 할 단위가 다르다.

`HurtBox` 는 판정만 받고 반응은 위임한다. #13 의 `Knockback` 이 이미 그 형태였고, 그 옆에
한 줄이 나란히 붙었다.

```
knockback?.Apply(info.Knockback);
health?.TakeDamage(info.Damage);
```

같은 이유로 파일을 `Combat/` 에 두고 이름도 `Health` 로 했다. `Player/` 에 두거나
`EnemyHealth` 로 지으면 반대쪽이 쓸 때 클래스를 새로 파게 된다.

**다만 지금은 적에게만 붙였다.** 플레이어 최대 체력은 적 공격 데미지가 정해져야 "몇 대
맞고 죽는가"가 나온다. 지금 숫자를 넣으면 근거 없이 굳는다 — 클래스를 범용으로 만드는
것과 지금 배선하는 것은 다른 결정이다.

### 2D 액션에서 적을 통과시키는 이유

플레이어와 적 몸통을 충돌시킬지 정해야 했다. 통과가 표준이다.

**2D 에는 우회로가 없다.** 3D 라면 옆으로 돌아가면 되지만 축이 하나라 막히면 그대로
봉쇄가 된다. 좁은 통로에 적 두 마리면 설계자가 의도하지 않은 난이도가 생긴다.

더 결정적인 건 **스왑 대시([GDD 3장](GDD.md))가 적을 뚫고 지나가야 성립**한다는 것이다.
뒤를 잡는 게 기술의 목적인데 몸통이 막으면 기술 자체가 없어진다. 핵심 시스템이 물리
설정에 걸려 있었다.

대신 "다가가면 위험하다"를 **물리가 아니라 규칙으로** 표현해야 한다 — 접촉 피해. 통과를
고른 순간 따라오는 숙제이고 #17 에서 정한다.

예외가 하나 남는다. **대형 보스는 몸통이 지형처럼 서는 편이 나을 수 있다.** `Enemy`
레이어 전체를 통과시키면 그게 안 되므로 W5 에서 보스 전용 레이어가 필요해질 수 있다.
보스 크기를 정하기 전에는 필요한지조차 알 수 없어 지금 만들지 않는다.

### 미루는 비용이 0 이면 관찰이 쌓일 때까지 미룬다

화면 흔들림을 피격에만 둘지를 #14 에서 정하지 않고 #17 까지 끌었다.

#14 시점에는 적이 공격하지 않아서 **피격 흔들림을 겪어본 적이 없었다.** 그 상태의 선호는
관찰이 아니라 예측이다. 예측으로 정하면 나중에 실제와 다를 때 "그때 왜 그렇게 정했지"가
남는다.

미룰 수 있었던 건 **바꾸는 비용이 값 두 개**였기 때문이다. 강도를 `DamageInfo` 가 실어
나르게 설계해서 코드 변경이 없었다. 설계가 판단을 미룰 여지를 만든 셈이다.

반대로 2단 점프(12.1)는 **되돌리기 비용이 비대칭**이라 미루지 않고 싼 쪽을 먼저 택했다.
두 경우의 기준이 다르다.

| | 판단 |
|---|---|
| 되돌리기 비용이 **비대칭** | 싼 쪽을 먼저 택한다. 미루면 비싼 쪽이 굳을 수 있다 |
| 되돌리기 비용이 **대칭이고 낮다** | 관찰이 쌓일 때까지 미룬다. 지금 정할 이유가 없다 |

### 근거가 사라져도 결정이 유지될 수 있다

지상 공격 전진은 "**넉백 누적으로 3타가 사거리 밖으로 나간다**"가 근거였다. 그런데 #16 에서
1·2타 넉백을 5 → 3 으로 낮춰 3타가 사거리 안에 남게 만들면서 **그 근거가 사라졌다.**

그래도 넣기로 했다. 근거가 사라진 건 "**필수**"쪽이고, 남은 건 "**감각**"이다 — 콤보 도중
제자리에 박혀 있는 것보다 조금 따라붙는 편이 리듬이 이어진다.

**둘을 구분하지 않으면 판단이 흐려진다.** 필수라면 값을 크게 잡아야 하고, 감각이라면
"조금"이면 된다. 근거가 바뀌었는데 값을 그대로 두면 필요 이상으로 넣게 된다.

### 이름은 조건과 정확히 같아야 한다

`InRange()` 에 체력 검사를 넣을지 논의하다 이름을 `CanAttack()` 으로 바꿨는데, **내용은
사거리만 보는 채로 뒀다.**

이름이 조건보다 넓으면 "여기서 다 검사하겠지"라고 믿고 다른 조건을 안 넣게 된다. 반대로
좁으면 실제로 하는 일을 놓친다.

결국 `InRange()` 로 되돌리고 체력 검사는 넣지 않기로 했다. **그러면 `health` 필드도 같이
지워야 한다** — 대입만 남고 소비자가 없으면 "검사하고 있겠지"로 읽힌다. 이름과 필드가
둘 다 실제 동작을 정직하게 가리켜야 한다.

### 프레임 수에서 타이밍을 추론했다

"`clipWindup` 은 무기마다 다르다"를 GDD 와 이슈 두 곳에 적어뒀다. 근거는
**`AttackSlash` 는 3장이고 `AttackPrick` 은 4장**이라는 것이었다.

#46 에서 실제로 재보니 틀렸다. 두 번째 키프레임이 **검·창·활 전부 `0.1167`** 이다.
프레임 수가 다른 건 맞지만 **프레임은 뒤에 붙지 앞이 늘어나지 않는다.** Pixem 이 같은
타이밍 템플릿으로 굽고 스프라이트만 갈아끼우기 때문이다.

**총량이 다르다고 각 구간이 다른 건 아니다.** 재보면 5초에 끝날 확인이었는데 그럴듯한
추론이 있어서 재지 않았다.

같은 이슈에서 한 번 더 났다. "상태 이름은 6종이 공유한다"를 확인하면서 **컨트롤러의
상태 목록을 세지 않았다.** 열었으면 공격 상태가 넷인 게 바로 보였다 (4절).
**두 번 다 "확인했다"고 적었지만 실제로 본 건 다른 것이었다.**

값 자체보다 **판단이 딸려 있었다는 게 문제다.** "무기마다 여섯 번 재야 한다"가
자동화 도구를 고민한 이유였는데, 상수 하나면 그 고민이 성립하지 않는다. **틀린 전제 위에
설계 논의가 얹혀 있었다.**

필드는 그대로 무기 SO 에 둔다. 근거만 "무기마다 다르니까"에서 "**클립에 종속되니까**"로
바뀐다 — 다시 구우면 초기화되고 후속 무기의 템플릿이 다를 수 있다. **결론이 같아도 근거가
틀렸으면 고친다.** 다음 판단이 그 근거 위에 서기 때문이다.

### ScriptableObject 는 플레이 모드를 넘어 남는다

무기를 SO 하나로 끝내지 않고 `WeaponData` + `WeaponInstance` 로 나눈 이유다.

**SO 는 에셋이라 인스턴스끼리 공유된다.** 쿨타임 남은 시간을 SO 에 넣으면 같은 무기를
든 모두가 그 값을 공유하고, 더 나쁜 건 **에디터를 껐다 켜도 값이 남는다는 것**이다.
플레이 모드에서 0 이 된 쿨타임이 에셋 파일에 기록된다.

기준은 "**안 변하는 것과 변하는 것**"이다. 데이터는 SO, 상태는 래퍼.

`MonoBehaviour` 는 씬 인스턴스마다 따로라 이 문제가 없다. **SO 로 옮기는 순간 생기는
제약**이고, 데이터 주도 설계로 갈 때 처음 만난다.

### 필드를 닫지 않고 프로퍼티만 더하면 오히려 나빠진다

`WeaponData` 의 필드가 `public` 인 걸 지적받고 **읽기 전용 프로퍼티를 더했는데 필드는
그대로 뒀다.** 고치기 전보다 나쁜 상태가 됐다.

접근 경로가 둘이 되면 **읽는 사람이 어느 쪽이 정본인지 모른다.** 그리고 프로퍼티가
있다는 사실이 "닫혀 있다"는 인상을 줘서 오히려 검사를 안 하게 된다.

필드를 `private` 으로 닫자 **`WeaponInstance` 가 `Data.swapCooldown` 을 직접 읽던 곳이
컴파일 에러로 드러났다.** 닫는 행위 자체가 남은 직접 접근을 전부 찾아준다 — 프로퍼티를
더하는 것만으로는 그게 안 된다.

`combo` 배열도 프로퍼티로 내보내지 않았다. **`private` 이어도 반환하면 받은 쪽이 원소를
바꿀 수 있다.** `ComboCount` 와 `GetAttack(i)` 로만 노출한다.

### 빌드는 마감 작업이 아니라 검증 수단이다

로드맵은 빌드를 **W6** 에 뒀다. "빌드 + README / 시연 영상" 한 줄이다. 결과물을 넘기는
행위로만 본 것이다.

W1 이 끝난 김에 눌러봤더니 **컴파일에서 깨졌다.** 유료 에셋의 `using UnityEditor;` 세 줄
때문인데, 에디터에서는 증상이 전혀 없어서 W6 까지 몰랐을 것이다. **마감 주에 처음
만났다면 남은 시간이 아니라 버퍼 자체가 사라진다.**

고치는 데 든 시간은 10분이다. **비용이 아니라 발견 시점이 문제였다.**

빌드가 검증하는 건 컴파일만이 아니다 — 에디터 전용 API, `Resources` 로딩, Addressables
콘텐츠 빌드, 셰이더 스트리핑이 전부 여기서 처음 돈다. 이 축은 에디터에서 아무리 오래
돌려도 안 드러난다.

**주차가 끝날 때마다 한 번 누른다.** 깨지면 그 주 안에서 고치고, 안 깨지면 10분이 든다.

### 한 값이 두 역할을 동시에 만족시키지 못하면 역할을 줄인다

스왑 대시에 공격 판정을 줄지가 [GDD](GDD.md) 미결정 항목이었다. 굴려보고 **주지 않기로**
정했는데, 결정을 가른 건 취향이 아니라 **값 하나가 두 요구를 못 맞춘다**는 사실이었다.

```
회피로 쓰려면    적 공격을 피할 만큼만. 지금 1.2유닛
판정을 주려면    적을 관통할 만큼. 훨씬 길어야 한다
```

길이를 늘리면 회피 거리로 과해지고, 두면 판정이 안 맞는다. **한 값에 두 역할을 얹으면
어느 쪽으로 튜닝해도 다른 쪽이 나빠진다.**

역할을 하나로 줄이자 값이 정해졌다 — 대시 거리는 **"피할 수 있는가"만 보고** 맞추면 된다.
튜닝할 때 볼 지표가 하나면 판단이 빠르다.

같은 형태를 12.2(화면 흔들림)에서도 한 번 겪었다. 흔들림을 타격과 피격 양쪽에 두면
"맞았다"의 신호가 흐려져서 **피격에만** 뒀다. **역할이 겹치는 값은 갈라놓는 게 아니라
한쪽을 버리는 쪽이 깔끔하다.**

### 일반화할 때 무엇을 남길지가 무엇을 바꿀지보다 어렵다

`Knockback` 을 `VelocityImpulse` 로 일반화하면서 **이름에 "넉백"이 든 것을 전부 바꿀 뻔했다.**

| | 바꿈 | 이유 |
|---|---|---|
| `Knockback` 클래스 | ✅ `VelocityImpulse` | 통로다. 넉백·대시·전진이 다 지나간다 |
| `knockbackTime` 필드 | ✅ `defaultDuration` | 위와 같은 이유 |
| 참조 필드명 (`knockback`) | ✅ `impulse` | 타입이 바뀌었으니 |
| `AttackData.knockbackForce` | ❌ | **실제로 넉백이다.** 타격이 미는 힘 |
| `DamageInfo.Knockback` | ❌ | 같음 |

전부 바꿨다면 **"때렸을 때 미는 힘"을 부를 이름이 사라졌을 것이다.** 통로가 일반화됐다고
그 통로를 지나는 것들까지 이름을 잃을 이유는 없다.

일반화의 판단 기준은 **"이 이름이 지금 하는 일을 정확히 말하는가"** 지 "같은 단어가
들어갔는가"가 아니다.

### 상태의 지속시간이 남의 설정에 묶였다

`SwapState` 의 `dashTime` 을 `0.2` 로 뒀다. 고른 값이 아니라 **`Knockback.knockbackTime` 이
0.2 라서** 맞춘 것이다.

대시 속도를 `Knockback.Apply` 로 주므로 감쇠 시간도 거기서 정해진다. 상태만 먼저 끝나면
`IsActive` 가 남아 `HandleHorizontal` 이 계속 막히고, 늦게 끝나면 대시가 멈춘 뒤에도 상태가
남는다. **두 값이 같아야만 어긋나지 않는다.**

`Knockback` 이 모든 임펄스에 하나의 지속시간을 쓰기 때문이다. 소비자가 하나(피격 넉백)일
때는 안 보였고, **넷(피격·적·대시·공격 전진)이 되자 병목이 됐다.**

**값을 맞춰서 피한 것이지 해결한 게 아니다.** #50 이 이름 변경만이 아니라
`Apply(impulse, duration)` 로 시그니처를 넓히는 작업이 된 이유다. 공유 설정은 소비자가
늘어나는 순간 파라미터가 되어야 한다.

**#50 에서 풀었다.** `remaining` 만 두면 감쇠 분모가 여전히 고정값이라, `total` 을 함께
기록해야 `t = remaining / total` 이 그 호출의 길이를 따른다. 안 그러면 대시(0.3)를 넣었을 때
`0.3 / 0.2 = 1.5` 로 시작해 **속도가 1.5배로 튄다** — 에러 없이 값만 틀린다.

그리고 파라미터가 되자 **지속시간을 파생시킬 수 있게 됐다.** 지상 공격 전진은 그 타의
`startup` 을 그대로 넘긴다. 새 필드가 안 생기고, 치켜드는 동안 들어가고 판정이 나갈 때
멈춘다. **고정값이었으면 1타(`startup` 0.12)가 0.2 동안 밀려 판정 중에도 전진했을 것이다.**

### 무효 처리를 호출자가 알 수 없으면 연출이 따로 논다

무적 가드를 `HurtBox.TakeHit` 초입에 넣었더니 넉백·데미지는 막혔는데 **히트스탑과 화면
흔들림은 그대로 터졌다.** `HitBox` 가 `TakeHit` 뒤에서 둘을 부르는데, `void` 라 무시당했다는
걸 알 방법이 없었다.

`TakeHit` 을 `bool` 로 바꿔 호출자가 결과를 보게 했다.

대안은 `CanBeHit` 같은 걸 밖에 노출해 미리 묻는 것이다. 그러면 **묻는 곳과 막는 곳이
갈라진다** — 조건이 하나 늘 때 한쪽만 고치게 된다. 판단은 한 곳에 두고 결과만 밖으로 낸다.

이 버그는 적이 하나일 땐 안 보인다. 적 사이클이 `0.4 + 0.15 + 0.6 = 1.15초` 라 무적 0.6초
안에 같은 적이 다시 못 때린다. **완료 조건이 "적 두 마리"였던 이유가 여기 있었다** —
조건이 재현 환경까지 지정하고 있었다.

### 같은 스위치를 두 명이 만지면 나중에 터진다

이슈 본문은 "무적 중 허트박스 비활성"이었다. 콜라이더를 끄는 방식이다. 그런데
`Health.Die()` 가 이미 `hurtBox.SetEnable(false)` 를 쓰고 있다.

죽인 타격도 무적을 유발하므로, 무적이 끝나는 순간 **시체의 허트박스가 다시 켜진다.**
지금은 적이 0.35초에 `Destroy` 되고 플레이어엔 `Health` 가 없어서 안 터진다. W4 에서
플레이어 사망이 들어오면 터진다.

두 방식의 결과는 거의 같았다 — 콜라이더를 꺼도 가드를 둬도, 무적이 끝날 때 이미 겹쳐
있던 히트박스는 `OnTriggerEnter2D` 가 다시 안 와서 무시된다. **결과가 같으면 기준은
"한 값을 몇 명이 소유하는가"가 된다.** 카메라 원위치를 `Main Camera` 로 분리한 것과 같은
판단이다.

이슈 본문의 체크리스트는 **목표 서술이지 구현 지정이 아니다.** 다르게 구현했으면 PR 에
근거를 남긴다.

### 출처가 하나면 컴포넌트에 두고 여럿이면 밖으로 뺀다

깜빡임을 `Invincibility` 안에 뒀다. `HitStop` · `Shake` 는 `static` 으로 뺐는데 왜 이건
아닌가.

**부르는 곳의 수가 다르다.** 히트스탑과 흔들림은 플레이어 공격도 적 공격도 부른다.
깜빡임은 무적 하나뿐이고, 무적 없이 홀로 의미가 없다.

나눴다면 `Blink` 가 `Invincibility.IsActive` 를 매 프레임 폴링해야 한다. 얻는 게 없다.
나중에 다른 이유로 깜빡일 일이 생기면 그때 분리한다 — **소비자가 둘이 되는 순간이
분리 신호다.**

**#47 에서 그 순간이 왔다.** 스왑 i-frame 이 두 번째 소비자인데, 깜빡이면 안 된다 —
깜빡임은 "맞았다"의 신호로 만든 것이라 **스왑에 쓰면 피격으로 오독된다.** 대시가 앞으로
나가는 동작이라 "맞아서 밀렸나"로 읽히기 더 쉽다.

다만 **컴포넌트를 쪼개지는 않았다.** `Begin(time, blink)` 로 인자를 하나 늘렸을 뿐이다.
예상했던 "분리"는 클래스를 나누는 것이었는데 실제로 필요했던 건 **파라미터 하나**였다.

가른 기준은 여전히 같다 — 깜빡임은 무적 없이 홀로 의미가 없다. 무적의 **출처**가 둘이
됐을 뿐 깜빡임의 **소유자**는 하나다. 소비자가 늘었다고 반드시 클래스를 쪼개는 게 아니라,
**무엇이 늘었는지를 봐야 한다.** 여기서 늘어난 건 "무적을 시작하는 이유"였다.

### 선택적 협력자에 폴백을 두면 "없음"과 "실수"가 구별되지 않는다

`HurtBox` 는 `knockback` · `health` · `invincibility` 를 전부 `?.` 로 부른다. 없어도
정상이다 — 플레이어엔 `Health` 가 없고 적엔 `Invincibility` 가 없다.

`invincibility` 에만 `GetComponent` 폴백을 넣었더니 **배선을 빠뜨린 걸 조용히 덮었다.**
게다가 `HurtBox` 는 자식이고 `Invincibility` 는 루트라 폴백의 방향 자체도 틀렸다
(4절 — 자식에 붙은 컴포넌트는 `GetComponent` 로 안 잡힌다의 반대 방향).

폴백은 "반드시 있어야 하는데 사람이 빠뜨렸을 수 있다"일 때만 쓴다. **없는 게 정상인
협력자에는 폴백을 두지 않는다** — 두면 의도적 공백과 실수가 같은 모양이 된다.

### 같은 단어를 쓴다고 같은 코드 경로가 아니다

#15 에 들어가기 전에 "무적을 넣으면 `AttackState` 를 밖에서 끊는 첫 경로가 생긴다"고
예상했다. **안 생겼다.**

`HurtBox.TakeHit` 은 넉백과 데미지만 걸지 상태머신을 건드리지 않는다. 피격 경직도, 공격
취소도 이 이슈에 없다. "피격"이라는 단어를 공유할 뿐 코드 경로가 겹치지 않았다.

`AttackState` 의 `cts.Cancel()` 과 `finally` 는 #10 에서 넣은 뒤로 **아직 한 번도 실제로
쓰이지 않았다.** 검증 시점이 또 미뤄졌다.

### 조건 부호 뒤집힘

`>= 0f` vs `> 0f`, `<= 0f` vs `> 0f`, `&&` 로 덧붙이기 vs 별도 줄로 분리.

#7 에서는 종류가 조금 달랐다. `IdleState` 에서 이동 입력을 `MoveInput > 0` 으로 검사해
**왼쪽 이동(`-1`)을 놓쳤다.** 오른쪽으로 걸으면 `Move` 로 가고 왼쪽으로 걸으면 `Idle` 에
머문다. 방향이 있는 값을 "있는가"로 물을 때는 `Mathf.Abs` 가 필요하다.

`float` 을 `> 0` 으로 검사하는 습관 자체가 원인이다. 원점 대칭인 값에는
"양수인가"와 "0이 아닌가"가 다른 질문이다.

**교훈** 거부 조건에 `&&` 로 덧붙이면 드모르간을 머릿속에서 돌려야 한다.
"허용하기 위한 요구사항"은 앞에서 **별도 줄로 먼저 거부**하는 편이 읽기 쉽다.

```
if (상승 중) return false;              // 요구사항
if (!접지 && 코요테 만료) return false;  // 기존 조건 그대로
```

경계값(`=` 포함 여부)이 지상 점프를 살리고 죽였다. `y == 0` 이 지상 정지 상태라는
것을 기억해야 한다.

### 새 `[SerializeField]` 의 기본값이 0 이라 조용히 안 돌았다

`AttackData.clipSpeed`(#37)에서는 `animator.speed = 0` 이 되어 애니메이션이 멈췄고,
`Knockback.knockbackTime`(#13)에서는 `remaining = 0` 이 되어 넉백이 아예 발동하지 않았다.
**둘 다 경고 없이 조용히**였다.

`float` 필드의 기본값은 1 이 아니라 0 이다. 그리고 0 은 대개 "그 기능을 끈다"는 뜻이 된다 —
속도 0, 지속시간 0, 배율 0. 새로 만드는 필드가 **곱하거나 나누는 값이거나 지속시간**이면
초기값을 반드시 준다.

기존 컴포넌트에 필드를 추가할 때와 새 컴포넌트를 만들 때가 다르다. 전자는 인스펙터에서
채울 기회가 있지만, **후자는 붙이는 순간의 값이 곧 기본값**이라 코드에 없으면 0 으로 시작한다.

### 계산 순서가 값과 체감을 어긋나게 했다

```
remaining -= Time.fixedDeltaTime;          // 먼저 줄이면
float t = remaining / knockbackTime;       // 첫 프레임이 1 이 아니다
```

첫 `FixedUpdate` 의 `t` 가 `(0.2 - 0.02) / 0.2 = 0.9` 라 **최고 속도가 `knockbackForce` 의
90%** 였다. `knockbackTime` 을 0.1 로 줄이면 80% 가 된다.

동작은 하고 눈에도 안 보인다. 문제는 **인스펙터의 5 가 실제로 5 가 아니게 된다**는 것이다.
값을 조정하는데 결과가 비례하지 않으면 원인을 계산식이 아니라 곡선이나 물리에서 찾게 된다.

"돌아가는가"와 "값이 의미대로 쓰이는가"는 별개다.

### 설정값 필드에 상태값을 넣었다

`jumpBufferTime` 은 인스펙터에서 조절하는 **버퍼 길이**인데 거기에 `Time.time` 을
대입했다. 튜닝값이 런타임에 파괴되고, 정작 시각을 담아야 할 `jumpPressedTime` 은
계속 0이었다.

`[SerializeField]` 로 노출한 값은 **설정**이고 런타임에 바뀌지 않는다. 매 프레임 변하는
것은 **상태**이고 별도 필드다. 이름이 비슷하면(`jumpBufferTime` / `jumpPressedTime`)
더 헷갈린다 — 설정은 "얼마나", 상태는 "언제"를 담는다.

### `MonoBehaviour` 가 아닌 것에 `GetComponent`

| 대상 | 실제 정체 |
|---|---|
| `InputSystem_Actions` | `IInputActionCollection2, IDisposable` — 일반 C# 객체 |
| `StateMachine<TOwner>` | 일반 C# 객체 |
| `PingState` / `PongState` | `IState` 구현체 — 일반 C# 객체 |
| `GameObject` | 컴포넌트가 아니라 **컴포넌트를 담는 그릇** |

`GameObject` 는 #9 에서 나왔다. `HurtBox` 의 소유자를 채우려고 `GetComponentInParent<GameObject>()` 와
`GetComponent<GameObject>()` 를 썼다. 개념적으로도 성립하지 않는다 — 모든 오브젝트가
GameObject 이므로 "부모에서 GameObject 를 찾는다"는 무엇을 찾겠다는 것인지가 정해지지
않는다. 어느 GameObject 인지는 **다른 기준**으로 골라야 한다.

**GameObject 는 컴포넌트를 통해 얻는다.** 모든 컴포넌트가 `.gameObject` 로 자기 그릇을
알려주므로, 계층을 타고 올라갈 때는 `Transform` 을 징검다리로 쓴다
(`transform.parent.gameObject`). `parent`, `root`, `GetChild()` 가 전부 `Transform` 에
있는 것도 같은 이유다.

`GetComponent<T>` 는 `null` 을 반환하고, 그걸 쓰는 다음 줄에서
`NullReferenceException` 이 난다. **`new` 로 만들어야 한다.**

판별법: **`MonoBehaviour` 를 상속하는가.** 아니면 GameObject에 붙지 않고, 붙을 필요도
없다. 상태 6개를 만들어도 GameObject 6개가 필요하지 않다 — 그게 오히려 장점이다
(할당이 가볍고 씬 없이 테스트 가능).

그래서 `InputSystem_Actions` 에 `Dispose` 가 필요하다. 컴포넌트라면 GameObject 파괴
시 Unity가 정리했겠지만, 코드가 소유한 객체는 만든 쪽이 해제해야 한다.

### 파일 위치와 네임스페이스가 어긋남

`Game.Gameplay` 네임스페이스 파일을 `Scripts/Core/` 에 뒀다. 컴파일은 된다 —
**네임스페이스와 어셈블리는 별개**다. 하지만 그 파일은 `Game.Core` 어셈블리 소속이라,
`Game.Gameplay` 의 다른 타입을 참조하려는 순간 막힌다 (의존 방향이 반대).

폴더가 어셈블리를 결정한다. 네임스페이스는 그걸 따라가는 표기일 뿐이다.

### 복사한 코드의 문자열을 안 바꿈

`PongState` 를 `PingState` 에서 복사하고 `Debug.Log("Ping Enter")` 를 그대로 뒀다.
로그로 상태를 구분하는 검증이었으므로 **검증 자체가 무의미해질 수 있었다.**
로그 문자열이 곧 판정 근거일 때는 문자열이 코드다.

### 전환 후에도 이전 상태가 계속 판단했다

`IdleState.FixedTick` 을 이렇게 썼다.

```
if (!접지)        Change(Fall);      // return 없음
if (이동 입력)    Change(Move);      // 위에서 Fall 로 갔어도 이 줄이 실행된다
```

**공중 + 이동 입력이면 `Fall` 로 갔다가 같은 프레임에 `Move` 로 다시 바뀐다.** 낙하
중인데 `Move` 상태가 된다.

더 근본적인 문제는 `Machine.Current` 가 이미 `Fall` 인데 **`Exit()` 을 끝낸 `Idle` 이
아직 판단을 계속한다**는 것이다. `Change` 는 `Current` 를 바꾸는 것이지 지금 실행 중인
함수를 멈추는 게 아니다.

**원칙: `Change` 는 그 함수의 마지막 행동이어야 한다.** `else if` 로 묶거나 직후에
`return` 한다.

### 배선 누락이 조용히 넘어갔다

상태 4개를 `new` 하고 `machine.Change(Idle)` 을 빼먹었다. `Current` 가 `null` 인 채로
시작했고 — **예외도 안 나고 로그도 안 찍혔다.** `StateMachine.Tick`/`FixedTick` 의
`if (Current == null) return;` 가드가 조용히 통과시켰기 때문이다.

#1 에서 그 가드를 넣기로 한 판단의 대가다. 5절 "접근자에 null 가드를 넣지 않는다"와
같은 문제인데, 이번엔 **내가 직접 넣은 가드에 걸렸다.**

가드를 뺄 문제는 아니다 — 초기화 전 한 프레임이 `null` 인 것은 정상 경로일 수 있다.
다만 **"아무 일도 일어나지 않음"이 증상일 때 가드를 먼저 의심**해야 한다는 걸 알았다.

#17 에서는 `EnemyDummy` 의 `Run().Forget()` 을 `Awake` 에 넣지 않았다. `async` 메서드는
**아무도 부르지 않으면 그냥 안 돈다** — 경고도 예외도 없다. #28 의 `machine.Tick()` 과
정확히 같은 형태이고, 이번에도 증상은 "적이 가만히 있네" 하나뿐이었다.

`private async UniTaskVoid Run()` 은 선언만으로 완결돼 보인다. **비동기 메서드는 호출부가
눈에 안 띄어서** 더 잘 빠진다 — 동기 메서드는 보통 다른 코드 흐름 안에 있지만, 이건
`Awake` 에 한 줄로 얹히는 게 전부다.

### 같은 임계값을 네 곳에 적었다

이동 입력 판정 `0.01f` 이 네 곳에 흩어졌고, 그중 한 곳만 경계값 포함 여부가 달랐다.

| 파일 | 조건 |
|---|---|
| `IdleState` | `> 0.01f` |
| `MoveState` | `<= 0.01f` |
| `FallState` | `>= 0.01f` |
| `PlayerMovement.HandleHorizontal` | `> 0.01f` |

지금은 아무 차이가 없다. 값을 조정할 때 한 곳을 빼먹는 것이 문제고, 그때 나는 버그는
"특정 상태에서만 미세하게 다르게 동작한다"라서 재현이 어렵다.

→ `PlayerMovement.HasMoveInput` 하나로 모았다. `if (Owner.HasMoveInput)` 이 읽기도 쉽다.

**상수가 아니라 판정을 공유해야 한다.** `0.01f` 를 `const` 로 빼는 것으로는 부족하다 —
부등호 방향과 경계값 처리까지 같아야 하니까.

### 배타 조건을 두 번 검사했다

```
if (Mathf.Abs(x) >= 0.01f) { ... }
if (Mathf.Abs(x) <  0.01f) { ... }   // 위가 거짓이면 무조건 참
```

두 번째는 `else` 다. 조건을 다시 쓰면 나중에 한쪽 임계값만 고쳤을 때 **양쪽 다 거짓이
되는 구멍**이 생긴다.

### IDE 가 넣은 엉뚱한 `using`

| 파일 | 자동 추가된 것 | 결과 |
|---|---|---|
| `IdleState.cs` | `using System.Diagnostics;` | `Debug` 가 모호해져 `UnityEngine.Debug` 로 풀네임을 써야 했다 |
| `GroundChecker.cs` | `using Unity.VisualScripting.YamlDotNet.Core.Tokens;` | **컴파일 에러** |
| `HurtBox.cs` | `using Codice.Client.BaseCommands;` | 조용히 통과 |
| `HitBox.cs` | `using static Codice.Client.Common.EventTracking...;` | 조용히 통과 |
| `HitBoxTestDriver.cs` | `using PlasticGui.Help.Conditions;` | 조용히 통과 |
| `Invincibility.cs` | `using System.Security.Cryptography;` | 조용히 통과 |

자동완성이 같은 이름을 가진 엉뚱한 네임스페이스를 골라서 생긴다. 첫 번째는 조용히
불편해지고, 두 번째는 컴파일이 아예 안 된다.

**두 번째가 컴파일 시점에 잡힌 건 asmdef 덕분이다.** `Game.Gameplay` 는
`Unity.VisualScripting` 을 참조하지 않고 `autoReferenced: false` 이므로 그 네임스페이스가
보이지 않는다. asmdef 없이 `Assembly-CSharp` 하나였다면 조용히 통과했을 것이다.

**#9 에서는 그 방어가 통하지 않았다.** `Codice` 와 `PlasticGui` 는 Unity Version Control
패키지 것인데 auto-referenced 라 `Game.Gameplay` 에서도 보인다. 그래서 컴파일러가 잡아주지
않고 조용히 통과했다 — 위에 적어둔 "asmdef 없이 하나였다면 조용히 통과했을 것"이 실제로
일어난 셈이다. asmdef 는 방어선이지 울타리가 아니다.

한 이슈 안에서 파일마다 되풀이됐다. 컴파일러가 안 잡아주는 종류라
**저장 전에 파일 맨 윗줄을 훑는 것**말고는 막을 방법이 없다.

#35 에서는 `using` 이 아니라 **식별자**에서 같은 일이 났다. `clipIdle` 을 못 찾는 `CS0103`
을 자동완성이 `PlayerMovement.clipIdle` 로 채웠다. 컴파일 에러는 사라졌지만 상수는 곧
`PlayerState` 로 옮겨질 예정이었으므로 **다시 에러가 될 코드**였고, 다섯 곳 중 그 한 줄만
형태가 달라져서 눈에 띄지도 않았다.

**오류를 없애는 제안과 의도에 맞는 제안은 다르다.** 자동완성은 "지금 컴파일되게" 만들 뿐
어디에 둘 것인지는 모른다. 옮기는 작업 중에는 특히 위험하다 — 옮기는 도중의 코드는 원래
컴파일이 안 되는 게 정상이다.

### 표를 인스펙터로 옮기다 한 칸씩 밀렸다

`PlayerMovement` 의 콤보 3타를 무기 SO 로 옮기는데 3타 행이 밀렸다.

```
표        damage 15 · 넉백 8 · 히트스탑 0.09
1차 입력   damage 15 · 넉백 0.09 · 히트스탑 0        넉백 8 을 통째로 건너뜀
2차 입력   damage 15 · 넉백 0.8  · 히트스탑 0.09     소수점이 붙음
3차 입력   damage 15 · 넉백 8    · 히트스탑 0.09     맞음
```

**같은 칸이 두 번 연속 틀렸다.** 3타만 값이 크고(8) 옆 칸이 소수(0.09)라, 옆을 보면서
자릿수를 맞추게 되는 자리였던 것 같다.

`AttackData` 는 필드가 전부 숫자라 **컴파일러도 인스펙터도 안 잡아준다.** "위치 인자로
넘겨 자리가 어긋났다"와 같은 뿌리인데, 그건 코드였고 이건 인스펙터다. 열 이름이 화면에
붙어 있는데도 밀렸다.

같은 라운드에 `clipWindup` 은 아예 안 채워져 0 으로 남았다. 이쪽은 애니메이션이 멈춰서
바로 보였지만, **넉백은 안 보였다** — 값이 틀렸을 뿐 동작은 하니까.

**옮긴 뒤 원본 표와 나란히 놓고 한 번 훑는 절차**가 필요하다. W2 에 창·활 + 스킬로
같은 작업이 다섯 번 남았다.

### 스테이징한 뒤에 생긴 변경이 커밋에서 빠졌다

에셋 저장소에서 폴더 이름 변경을 `add -A` 로 스테이징하고, 그 뒤에 클립의 루프 플래그를
끈 다음 `commit` 만 불렀다. **루프 변경은 스테이징되지 않아 커밋에 안 들어갔는데 커밋
메시지에는 적혀 있었다.**

`git status` 가 이미 알려주고 있었다 — `RM` 은 "스테이징된 이름 변경 + 스테이징되지 않은
수정"이다. `R` 만 세고 `M` 을 안 봤다.

**커밋 직전에 `git status` 를 다시 보는 것**말고는 막을 방법이 없다. 특히 검증을 위해
사용자가 값을 만지는 동안 대화가 오가면, 스테이징 시점과 커밋 시점 사이가 벌어진다.
`git diff --cached --stat` 으로 **커밋에 들어갈 것만** 확인하는 편이 확실하다.

메시지가 내용보다 앞선 커밋은 나중에 히스토리를 믿을 수 없게 만든다. 이미 푸시했으므로
고치지 않고 다음 커밋에 사실을 적었다.

### 두 가지 안의 절반씩을 섞었다

상수 배치에 두 가지 안이 있었다.

| | 상수 위치 | 호출 형태 |
|---|---|---|
| 1안 | `PlayerMovement` 에 `internal` | `Owner.PlayClip(PlayerMovement.clipIdle)` |
| 2안 | `PlayerState` 에 `protected` | `Owner.PlayClip(clipIdle)` |

접근자는 1안(`internal`)을 택하고 호출은 2안(접두어 없음)으로 써서 컴파일이 안 됐다.
각각은 맞는데 조합이 틀렸다.

"고칠 때 기존 줄을 지우지 않고 새 줄만 추가했다"와 같은 뿌리다. 그쪽은 **삭제를 안 해서**,
이쪽은 **한쪽만 바꿔서** 생겼다. 둘 다 변경을 "무엇을 추가할까"로만 보고 **어디까지가 한
덩어리인지**를 안 정한 결과다. 두 안을 비교했을 때는 표의 한 행이 통째로 한 덩어리다.

### 위치 인자로 넘겨 자리가 어긋났다

```
PlayClip(string stateName, float normalizedTime = 0f, float speed = 1f)

Owner.PlayClip(clipAttack, data.speed);      // speed 가 normalizedTime 으로 들어간다
```

`speed` 0.79 가 `normalizedTime` 이 되어 **클립이 79% 지점부터 시작**했다. 속도는 1 로 남았다.

인자 셋이 다 `float` 이고 전부 기본값이 있어서 **컴파일러가 절대 안 잡아준다.** 게다가 이때
씬 저장이 안 돼서 `speed` 가 0 이었고, `normalizedTime = 0` · `speed = 1` 이 되어 **우연히
정상처럼 보였다.** 두 버그가 서로를 가려서 "speed 를 넣었는데 변화가 없네"로 읽혔다.

기본값이 있는 동종 타입 인자가 둘 이상이면 **이름을 붙여 호출한다.** 자리를 세지 않아도
되고, 나중에 인자 순서를 바꿔도 호출부가 안 깨진다.

### 고칠 때 기존 줄을 지우지 않고 새 줄만 추가했다

```
if (bodyCollider == null)
    bodyCollider = GetComponent<Collider2D>();          // ← 지워야 했던 줄
return bodyCollider != null ? bodyCollider : GetComponent<Collider2D>();   // 추가한 줄
```

새 `return` 을 넣었지만 기존 대입이 남아 **문제가 전혀 해결되지 않았다.** 게다가 위에서
이미 채워지므로 새로 쓴 삼항 연산자는 항상 왼쪽만 고른다 — 의미 없는 코드가 됐다.

같은 라운드에 `Awake` 의 `LogWarning` 을 실수로 지워서 **안전장치가 후퇴**하기도 했다.
고치려던 것(경고가 무력화됨)의 반대 방향이었다.

**교훈: "무엇을 추가할지"보다 "무엇을 지울지"를 먼저 정한다.** 동작을 바꾸는 수정은
추가가 아니라 교체인 경우가 많다.

#6 에서도 같은 형태였다. `jumpRequested` 를 시각 기록으로 대체하면서 필드는 지웠는데
그 필드를 쓰던 `JumpBufferTimer()` 를 남겨 **컴파일이 깨졌다.** 여기서는 컴파일러가
잡아줬지만, 위 사례처럼 문법이 성립하면 조용히 통과한다.

#9 의 `HitBox` 에서도 같았다. `OnTriggerEnter2D` 에서 해야 할 일은 `hurtbox.TakeHit(...)`
호출인데, 그것을 추가하면서 그 자리에 있던 `HitBoxActivate` / `HitBoxDeactivate` 호출을
지우지 않았다. 컴파일도 되고 로그도 찍혀서 **동작하는 것처럼 보였다.** 실제로는
`HitBoxActivate` 안의 `Clear()` 가 매번 캐시를 비워 중복 방지가 무력화됐고,
`Deactivate` 는 첫 적을 맞추는 순간 콜라이더를 꺼버렸다.

그다음 라운드에서는 `Clear()` 를 지우는 대신 `OnTriggerEnter2D` 안으로 **옮겨서** 같은
문제가 형태만 바꿔 남았다. 옮기기도 교체의 일종이라 "어디서 지울지"를 같이 정해야 한다.

반대 방향도 있었다. #10 에서 `Exit()` 에 `cts = null` 을 추가하면서 **직전에 넣은
`cts.Cancel()` 을 같이 지웠다.** 고치는 과정에서 이미 맞게 되어 있던 줄이 사라진 것이라,
추가만이 아니라 **한 번에 여러 곳을 손댈 때** 생기는 문제다. 지적받은 항목이 여럿이면
하나씩 넣고 그때마다 확인하는 편이 낫다.

#12 에서는 아예 같은 줄이 두 번 남았다. `Time.timeScale = 0f;` 아래에
`Time.timeScale = 0;` 이 붙어 있었다. 동작이 같아 컴파일도 실행도 통과한다 — **무해한 중복은
아무도 잡아주지 않는다.** 반대로 같은 이슈에서 `Play` 의 반환 타입을 바꾸고 호출부의
`.Forget()` 을 안 뗀 것은 컴파일러가 즉시 잡았다. 시그니처를 바꾸는 교체는 안전하고,
**본문 안에서 일어나는 교체가 위험하다.**

#16 에서는 폴백을 경고로 **교체**하라고 한 것을 **추가**로 받았다. `GetComponent<HurtBox>()`
위에 `LogWarning` 을 얹고 원래 줄을 남겼다. 그 줄은 반환값을 안 받아 아무 일도 안 하고,
받았어도 `HurtBox` 가 자식에 있어 `null` 이었다. **값을 버리는 호출은 컴파일러가 경고하지
않는다** — 문법적으로 정상이기 때문이다.

같은 이슈에서 지적 3개를 받아 1~2개만 반영하는 일이 여러 라운드 반복됐다. 위에 적어둔
"하나씩 넣고 그때마다 확인한다"가 지켜지지 않은 것이고, **여러 개를 한 번에 처리하면
빠진 것을 자기가 알아채지 못한다.** 고친 뒤 목록을 다시 읽는 절차가 없으면 매번 난다.

#15 에서는 `invincibility?.Begin()` 한 줄을 넣는 과정에서 위의 두 줄이 함께 복제됐다.
`knockback?.Apply` 와 `health?.TakeDamage` 가 각각 두 번 불려 **넉백과 데미지가 2배**였다.
한 줄을 추가하는 수정인데도 블록 단위로 손대면 이렇게 남는다.

여기서 새로운 건 **왜 눈에 안 띄었는가**다. 데미지가 2배면 적이 훨씬 빨리 죽는데, 기준으로
삼을 "정상적인 처치 속도"를 아직 몸에 익히지 않은 단계였다. **밸런스가 안 잡힌 시기에는
수치 버그가 이상하게 보이지 않는다** — 값이 임시라는 걸 알고 있으니 전부 임시로 읽힌다.
이 시기에는 눈이 아니라 코드가 판정 기준이어야 한다.

### 인스펙터 슬롯이 컴포넌트의 위치를 말해주지 않는다

`HurtBox.hurtBoxCollider` 슬롯에 **루트의 몸통 콜라이더**가 들어갔다. 슬롯 이름이
`Hurt Box Collider` 이니 허트박스가 잡힐 것 같지만, `HurtBox` 컴포넌트는 자식에 있고
부모를 선택한 채 드래그하면 부모 것이 잡힌다.

그대로 죽으면 **몸통이 꺼져 지면을 뚫고 떨어지고 허트박스는 살아남는다** — 고치려던 것과
정확히 반대다. 컴파일도 되고 인스펙터에도 정상으로 보인다.

**참조 필드는 "무엇을 가리키는가"를 값으로 확인해야 한다.** 씬 YAML 에서 `fileID` 를 따라가
어느 오브젝트의 어느 컴포넌트인지 보는 게 확실하다.

### `catch` 를 반사적으로 붙였다

#12 의 `RunAsync` 에 `catch (Exception ex)` 를 넣었다. 필요한 것은 "무슨 일이 있어도
`timeScale` 을 되돌린다"뿐이고 그건 `finally` 가 한다. **`try/finally` 는 `catch` 없이도
유효한 문법이다.**

게다가 여기서는 잡을 예외가 아예 없었다. `UniTask.Yield()` 에 토큰을 넘기지 않았으니 취소가
일어나지 않는다. #10 의 `catch (OperationCanceledException)` 은 **토큰을 넘겼기 때문에**
필요했던 것인데, 그 사정이 아니라 모양만 따라왔다.

`ex` 를 쓰지도 않아 경고까지 났다. `catch` 는 "이 예외를 내가 처리한다"는 선언이지 정리
코드를 담는 자리가 아니다. 정리는 `finally` 다.

이전 내용이 남아 있었다. 그중 한 번은 컴파일 에러가 난 상태였는데
`check_compile_errors` 가 통과로 나와 혼선을 키웠다 — Unity 가 아직 재컴파일하지 않아서였다.

### 복사한 오브젝트가 레이어까지 가져왔다

플레이어의 `HitBox` 를 복사해 적에게 붙였더니 **레이어가 `PlayerHitbox` 인 채로** 왔다.

"복사한 코드의 문자열을 안 바꿈"의 오브젝트 판이다. 그쪽은 로그 문자열이 검증을 무의미하게
만들었고, 이쪽은 **`OnTriggerEnter2D` 가 아예 안 불리게** 만든다. 레이어가 틀리면 물리
엔진이 콜백을 보내지 않으므로 **코드를 아무리 읽어도 원인이 안 보인다.**

복사한 오브젝트는 컴포넌트 값만 보지 말고 **레이어와 이름을 먼저 확인**한다. 인스펙터
맨 위 두 줄이다.

### 구조를 바꾼 뒤 옛 참조가 남았다

적을 `Enemy` 래퍼 아래로 옮긴 뒤 `HurtBox.owner` 가 **옛 루트(스프라이트 오브젝트)** 를
그대로 가리키고 있었다.

`HitBox` 는 `hurtbox.Owner == damageInfo.Source` 로 자기 자신을 거른다. `Source` 는 새
래퍼인데 `Owner` 는 옛 오브젝트라 **같지 않아서 못 거른다.** 지금은 `EnemyHitbox × EnemyHurtbox`
가 매트릭스에서 꺼져 있어 드러나지 않는다 — **레이어가 우연히 막아주고 있는 상태**다.

계층을 바꾸면 "무엇이 논리 루트인가"가 바뀐다. 그 루트를 가리키던 참조를 전부 다시 봐야
하는데, 인스펙터에는 `{None}` 이 아니라 **여전히 유효한 옛 오브젝트**가 들어 있어서
눈으로는 정상으로 보인다. 배선 누락보다 찾기 어렵다.

### 컴포넌트가 두 개 붙었다

`Enemy` 에 `Knockback` 이 설정까지 똑같이 두 개 붙어 있었다. `HurtBox` 는 그중 하나만
가리키므로 나머지는 죽은 컴포넌트다.

지금은 무해하다 — `Apply` 를 못 받은 쪽은 즉시 반환한다. 하지만 **둘 다 `linearVelocityX`
에 대입하는 코드**를 갖고 있고, `GetComponent<T>()` 는 첫 번째를 반환한다(5절). 어느 쪽이
걸릴지 모르는 상황이 만들어져 있었다.

컴포넌트를 옮기는 작업(Add → 값 복사 → 옛 것 Remove) 중에 마지막 단계를 빠뜨리면 이렇게
된다. "고칠 때 기존 줄을 지우지 않고 새 줄만 추가했다"와 같은 뿌리다.

### 경고는 진행을 막지 않는다

`WeaponHolder.Awake` 의 배선 가드가 세 라운드에 걸쳐 세 가지 모양으로 틀렸다.

```
1라운드   if (null) { 경고; Equip(...); }      본문이 가드 안 → 정상 경로에서 아무 일도 안 함
2라운드   if (null) { 경고; }  Equip(...);     본문은 밖으로 나왔는데 return 이 없음
3라운드   if (null) { 경고; return; }  Equip(...);   맞음
```

1라운드가 가장 나빴다. 배선이 **정상일 때** `current` 가 `null` 로 남고, `Awake` 에서는
에러가 안 나며 **처음 공격할 때** 터진다. 원인 지점과 증상 지점이 멀어진다.

2라운드가 진짜 함정이다. **경고를 찍었으니 막았다고 느끼는데 `Debug.LogWarning` 은 로그
한 줄일 뿐이다.** 실행은 그대로 다음 줄로 간다.

거부 조건은 `return` 으로 끝내야 뒤 코드가 "여긴 정상"이라는 전제 위에 설 수 있다.
4절의 "허용하기 위한 요구사항은 앞에서 별도 줄로 먼저 거부한다"와 같은 이야기인데,
거기서는 `if` 를 나누는 문제였고 여기서는 **나눈 뒤 끝내지 않은** 문제다.

`NullReferenceException` 은 무엇이 `null` 인지 안 알려주고 `LogWarning` 은 알려준다.
**둘 중 먼저 뜬 쪽이 진단을 정하므로** 가드가 먼저 끝내야 한다.

### 오버로드를 만들고 호출부를 안 바꿨다

`Invincibility.Begin()` 이 `duration`(0.6)을 쓰는데 스왑 i-frame 은 0.3 이라
`Begin(float)` 오버로드를 만들었다. 그런데 `BeginIFrame()` 은 **인자 없는 쪽을 그대로
부르고 있었다.**

```csharp
internal void BeginIFrame() => invincibility.Begin();          // 0.6 이 들어간다
internal void BeginIFrame() => invincibility.Begin(iframeTime); // 0.3
```

**컴파일도 되고 무적도 걸린다.** 테스트하면 "잘 된다"로 보이고, `iframeTime` 필드만 아무도
안 읽는 채로 남는다.

기본값 0 이 조용히 기능을 끄는 사례는 여러 번 겪었는데 이건 **반대 방향**이다 — 다른 값이
조용히 들어온다. 꺼지면 눈에 띄지만 **다른 값이 들어오면 안 띈다.**

오버로드는 **기존 호출부를 문법적으로 유효하게 남겨두는** 변경이다. 컴파일러가 아무 말도
안 한다. 이름을 바꾸거나 인자를 필수로 만들면 전부 에러로 드러나는 것과 정반대다.
**오버로드를 추가할 때는 기존 호출부를 하나씩 다시 봐야 한다.**

### 이름을 손으로 바꿔 선언과 사용이 갈렸다

`Invincibility` 필드를 `invincibility` 로 고치면서 **선언 한 줄만 바꾸고 쓰는 세 곳을
남겼다.** 그 이름은 이제 필드가 아니라 타입을 가리키므로 `Invincibility != null` 이
CS0119 가 된다.

컴파일러가 잡아준 건 **필드명이 타입명과 겹쳤기 때문**이다. 겹치지 않는 이름이었다면
그냥 "그런 이름 없음"으로 똑같이 막혔겠지만, 겹치는 이름이라 에러 메시지가 "타입은 여기
쓸 수 없다"로 나와 원인이 한 번 더 꼬였다. 애초에 필드명을 타입명과 같게 두지 않는 이유다.

이름 변경은 F2(Rename)로 한다. 손으로 고치면 **선언은 바뀌고 사용은 안 바뀌는 중간
상태**가 만들어진다.

그리고 Unity 는 **필드 이름으로 직렬화**하므로, 이름을 바꾸면 씬에 저장된 참조가 끊긴다.
코드가 컴파일되는 것과 배선이 살아 있는 것은 별개다 — 이름을 바꿨으면 인스펙터를 다시
봐야 한다.
