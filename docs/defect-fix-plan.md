### #150 — 예고 순간 `SpriteRenderer.Color` 를 본다

에디터에서 보스전을 띄우고 **예고 구간(0.4~0.8초)에 `Body` 의 `SpriteRenderer.Color` 값이
바뀌는지** 인스펙터로 본다.

| 관측 | 원인 | 고치는 크기 |
|---|---|---|
| 값이 **안 바뀐다** | 애니메이션 클립의 `m_Color` 커브가 덮어쓴다 | 코드 — 매 프레임 적용하거나 커브를 뺀다 |
| 값은 **바뀌는데 화면이 그대로** | 대비 부족 | **데이터만** — `telegraphColor` 를 밝은 쪽으로 |

**지금까지의 근거는 아래쪽을 가리킨다.** 보스 몸 평균색 `RGB(73,170,75)` 에 보스
`telegraphColor(1, 0.30, 0.20)` 을 곱하면 `RGB(73,51,15)` — 어두운 갈색이고 동굴 배경과
비슷하다. 잡몹은 `(1, 0.78, 0.78)` 이라 **밝아지는** 쪽인데 보스만 어두워진다.
사용자가 *"가끔 때릴 때 색이 바뀌긴 한다"* 고 한 것도 `SetTint` 경로가 살아 있다는 뜻이다.

> 이 확인이 30초짜리인데 **수정 규모가 데이터 한 줄과 코드 수정으로 갈린다.**

### #152 — 시작 화면 설정에서도 같은지 본다

시작 화면 설정에서 해상도를 바꿔 **설정창이 똑같이 어긋나는지** 본다.

| 관측 | 원인 | 묶이는 곳 |
|---|---|---|
| 시작 화면도 어긋난다 | 스케일러(`Match = 1`) · 중앙 앵커 + 고정 오프셋 | 3단계 레이아웃 묶음 |
| 일시정지에서만 | 열린 창이 바뀐 캔버스를 다시 계산 안 함 | 따로 — 코드 |

같은 프리팹을 두 씬에 놓은 구조([#140](../../issues/140))라 이 한 번으로 원인이 반으로 준다.

## 1단계 — 판단이 걸린 것 · #149 + #148

**먼저 정할 것 하나. 숫자키 `1`·`2`·`3` 을 기능으로 남길 것인가?**

```
A. 폴링을 지운다      StageRunner.Update 의 digit1~3 분기 삭제
                     → #103 의 원래 의도로 돌아간다
                     → #148 이 같이 사라진다 (안내에 없는 조작이 없어지므로)
                     → 싸다. 브랜치 하나

B. 정식 기능으로 남긴다  RewardRoomHandler.Cleared 를 RewardView 가 구독해 닫는다
                     → 입력 경로가 늘어도 안 깨진다
                     → #148 은 안내 문자열 추가로 남는다 (2단계로)
                     → 구조적으로 옳다. 브랜치 둘
```

**구조로는 B 가 옳다.** 지금은 "패널을 닫는다"가 입력 처리에 붙어 있어서 경로가 하나 늘
때마다 같은 실수가 난다. 닫을 시점을 아는 이벤트(`Cleared`)가 이미 핸들러에 있는데 뷰가
그것을 안 듣는 것이 진짜 문제다.

**포트폴리오로는 B 가 할 말이 많다.** "입력 경로가 둘인데 정리는 한쪽에만 있었다"는
**클라이언트 관점의 설계 이야기**이고, A 는 "지웠다"로 끝난다.

> **2026-09-28 — B 로 정했다.** 입력 경로가 둘인데 정리가 한쪽에만 있던 것이 이 결함의
> 실체이고, 그것을 고치는 것이 "지웠다"보다 남는 게 많다. 숫자키는 정식 기능으로 남고
> #148 은 안내 문자열 추가로 2단계에 합류한다.

이 단계가 먼저인 이유는 **우선순위가 가장 높고(Major · High) 다른 이슈를 없애거나 남기기
때문**이다. 뒤로 미루면 2단계에서 쓸 문자열이 정해지지 않는다.

## 4단계 — #150 보스 예고 (0단계 결과에 달림)

| 0단계 결과 | 할 일 |
|---|---|
| 대비 부족 | `telegraphColor` 를 **밝아지는 쪽**으로. 잡몹처럼 `(1, 0.78, 0.78)` 계열 |
| 애니메이션이 덮어씀 | `SetTint` 를 `Enter` 한 번이 아니라 예고 구간 동안 유지되게 |

**어느 쪽이든 색만으로 끝내지 않는 편이 낫다.** 색은 스프라이트 원본색에 곱해지는 값이라
적이 늘어날 때마다 같은 문제가 난다. 깜빡임이나 외곽선처럼 **원본색과 무관한 신호**를 얹으면
한 번으로 끝난다 — 다만 그건 기능 추가라 범위가 다르다. 1차 수정은 색으로 하고, 판단은
남겨 둔다.

**고친 뒤 잡몹 예고와 나란히 캡처한다.** 덱 8쪽의 대표 결함 자료가 "고치기 전/후"로 바뀐다.

## 5단계 — #154 오탐 경고 (15분)

`GameSettings.Verify()` 가 드롭다운 셋을 한 조건으로 묶어 검사해서, 언어를 일부러 뺀
전투 씬이 **항상** 걸린다.

```
A. 드롭다운별로 조건을 나누고 언어는 선택적으로 취급한다     ← 작다
B. 씬 구성을 표현하는 값을 둔다 (languageOptional 같은)    ← 의도가 드러난다
```

**A 를 고르면 "언어는 없어도 되는 항목"이라는 판단이 코드에 박힌다.** 시작 화면에서 언어
드롭다운이 진짜로 빠진 경우는 못 잡게 된다. 그 대가를 받을지가 판단이고, 학습 로그 5절의
*"선택적 협력자에 폴백을 두면 '없음'과 '실수'가 구별되지 않는다"* 가 정확히 이 자리다.

**동작에는 영향이 없지만 한 번은 치워야 한다.** 매 실행마다 뜨는 경고가 있으면 진짜 배선
누락이 생겨도 같은 줄에 섞여 안 보인다. W3 에서 `HurtBox.health` 미배선을 놓친 것이 그
종류였다.

## #143 은 따로 — 2회전과의 순서를 정해야 한다

**나머지 일곱과 성격이 다르다.**

| | |
|---|---|
| 출처 | 1회전 산출물이 **아니다**. 자동화 작업(#141) 중에 코드에서 나왔다 |
| 크기 | 조건을 선택기 안으로 모으는 **구조 변경**. 견적 1시간 |
| 부작용 | **밸런스가 바뀐다.** 지금은 점프 회피에 착지 후 안전 시간이 딸려 있는데, 고치면 착지하자마자 공격이 들어온다 |
| 완료 조건 | `test-cases.md` 에 항목 추가가 들어 있다 |

그래서 순서가 문제가 된다.

```
2회전 전에 고친다   2회전이 "고쳐진 것"과 "바뀐 밸런스"를 같이 본다
                  TC 를 먼저 추가해야 회전에 포함된다
                  회귀 대상이 아니라 신규 검증이 섞인다

2회전 뒤에 고친다   2회전이 순수 회귀 확인으로 남는다
                  3회전이 필요해진다
```

> **2026-09-28 — 2회전 뒤로 정했다.** 2회전의 값어치는 *"1회전에서 찾은 것이 고쳐졌는지"* 를
> 같은 절차로 다시 보는 데 있다. 여기에 밸런스 변경이 섞이면 "무엇을 확인한 회차인가"가
> 흐려진다. #143 은 라벨도 `후속` 이고 1차 범위 밖이다.

**다만 고치기 전에 TC 는 지금 넣어 둔다.** 완료 조건에 있고, 2회전 스텝을 확정하는 김에
같이 적으면 한 번에 끝난다. 2회전에서 그 TC 는 **고치기 전 동작**으로 기록된다 — 수정 후
3회전이나 부분 확인에서 뒤집히는 것이 정상이다.
